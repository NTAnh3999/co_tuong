# Environment notes (discovered during T0.0 pre-flight)

Operational quirks on this machine that affect how tasks are briefed/dispatched. Read before writing new briefs.

1. **Codex's Windows `workspace-write` sandbox denies writes to any dot-prefixed DIRECTORY** (`.agents/`, `.github/`, `.claude/`, `.vscode/`, etc.) even though it's inside the cd'd workspace — confirmed across PowerShell `Set-Content`, `cmd echo`, and Node `fs.writeFileSync`. Dot-prefixed *files* at a normal (non-dot) directory level (e.g. `./.gitignore`, `./.nvmrc`) write fine. **Consequence: never brief a Codex task to write inside a dot-directory.** CI config, agent config, and anything under `.agents/` are Haiku/orchestrator-only. Codex's own stdout and `--output-last-message` output are written by the unsandboxed host CLI process, so redirecting those into `.agents/runs/...` from the orchestrator's shell is fine — it's only the *sandboxed guest commands* that are blocked.
2. **Codex's sandbox has no network access** (confirmed: `curl.exe` fails silently inside the sandbox). All `pnpm install`/`pnpm add` must happen on the orchestrator's side before dispatch.
3. **Codex spawns commands via native Windows PowerShell** (`powershell.exe -Command ...`), not bash, even though Git Bash is available on this machine. PowerShell's `CurrentUser` execution policy is `RemoteSigned`; scripts npm/corepack writes that get marked as from a remote zone (e.g. `pnpm.ps1`) will fail with "not digitally signed" until `Unblock-File` is run once. Already fixed for `pnpm`/`pnpx`/`npm`/`npx`/`corepack` shims under `C:\Program Files\nodejs\`. If a brief's gate command fails with a PSSecurityException about an unsigned script, that's this issue — not a real test failure; `Unblock-File` the relevant `.ps1` and retry.
4. **`@openai/codex` and other global npm packages were installed under the old Node v20.11.1 (per-nvm-version global folder)** and vanished when the user switched the system default to Node 22 via `nvm use 22`. Reinstalled `@openai/codex` globally under Node 22. Other previously-global tools (`pm2`, `win-node-env`, `ui-ux-pro-max-cli`) were NOT reinstalled — out of scope for this project, flagged to the user once, not tracked further here.
5a. **`rtk` (the user's global token-saving CLI hook) mishandles `npx prisma ...` / `prisma --version`** — it tries to resolve `prisma` as a direct program and fails ("[rtk: program not found]"), or silently garbles the real command's output (`prisma migrate dev`/`migrate status` printed truncated nonsense like "Changes:" with nothing after, even though the migration WAS actually applied correctly underneath). **Workaround: invoke the local binary directly**, e.g. `./node_modules/.bin/prisma.cmd migrate status` from `apps/api/`, which bypasses whatever rtk does to `npx`/`prisma` and shows real output. Use this pattern for any future Prisma CLI invocation from the orchestrator shell.
5. **Pikafish binary verified working**: `tools/pikafish/Pikafish-Windows-x86-64-universal.exe` + `pikafish.nnue` (not committed, gitignored — see root `.gitignore`). `go perft 4` from startpos returned `3290240`, matching the reference value used to derive ADR-018's coordinate/FEN convention — the convention is confirmed compatible with the real engine, no translation layer needed.
6a. **Codex can occasionally write mojibake'd Vietnamese text** (first observed in T4.7's `apps/web/app/game/[id]/page.tsx`): a UTF-8-encoded string gets round-tripped through something that reads/writes it as a different codepage (consistent with the `.ps1`/`Set-Content` default-codepage gotcha already noted in item 3, but confirmed here on a file `.tsx` write, not a shell script), producing byte sequences like `Ä‘á»‘i` instead of `đối`. Not every non-ASCII string in a dispatch is affected — in this case only 2 of ~10 new Vietnamese strings in one file were corrupted, the rest were fine. **When reviewing any Codex-written file with Vietnamese (or other non-ASCII) text, grep for `Ã` and `â€` as a quick corruption smell test** before trusting it's correct — don't rely on it "looking right" in a quick scroll. Fix by rewriting the specific line(s) with Python using explicit `encoding='utf-8'` (the Edit tool's exact-string match can fail on these lines since the garbled bytes don't match what a Read tool render shows character up).
6b. **Multiplayer E2E (`apps/web/e2e/multiplayer.spec.ts`) needs `NEXT_PUBLIC_API_BASE_URL` on the SAME hostname as Playwright's web server, and a non-stale Next.js dev server.** Two gotchas discovered running T4.8 for real: (1) Playwright's `webServer`/`baseURL` serve the web app at `127.0.0.1:4173`; if the API base URL instead points at `localhost:3001` (a different hostname, even though it's the same machine), the browser treats them as different sites and the session cookie (`SameSite=Lax`) set by `POST /sessions/guest` never gets sent back on the next request — every subsequent authenticated call 401s, and the symptom looks like "the app is silently broken" rather than an obvious auth error unless you watch network responses. Always export `NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:3001/api/v1` (matching `127.0.0.1`, not `localhost`) when running this spec. (2) If a Next.js dev server from an EARLIER test run is still listening on the webServer's port (Playwright's `reuseExistingServer` happily reuses it), and the app's source has changed since that server last compiled, it can serve 404s for its own JS chunk files — the page never hydrates, so every interactive assertion just hangs until timeout with no useful error. If a run inexplicably hangs on a simple click with no actionability error, check for and kill a stale dev server on the config's port and delete `apps/web/.next` before retrying.
6a. **Running `multiplayer.spec.ts` with real concurrency (default `fullyParallel`/multiple workers) can intermittently hit `429` on `POST /sessions/guest`** — ROOM-02's own rate limiter (10/60s per IP) is deliberately strict, and multiple parallel browser contexts/projects creating guest sessions in the same short window can exceed it. Confirmed: all 9 cases (3 scenarios × 3 projects) pass reliably with `--workers=1`; this is an acceptable CI consideration (serialize this spec, or run it with reduced parallelism), not a bug to fix by loosening the limiter.
7. **`packages/content`'s `loadLessons`/`loadPuzzles` use `import.meta.url` to find their default `data/` directory, which is empty in this package's own CJS build output** (`import.meta` isn't available in CJS — tsup/esbuild warns about this at build time, doesn't fail the build). Currently harmless: every real caller (`content:validate`/`content:seed`, run via `tsx`; this package's own vitest tests) runs under ESM, and M6's content API design serves already-seeded DB rows rather than re-reading these files per-request, so the CJS path is dormant. If anything ever imports `@xq/content`'s CJS build and calls `loadLessons()`/`loadPuzzles()` without overriding `dataDirectory`, it will break — worth a real fix (e.g. threading the directory in some other way) before that happens, not before.
8. **Docker Desktop's engine can quietly stop between orchestrator sessions/long idle periods** (observed once already during M4, again during M5/M6) — `docker ps`/`docker info` fail with "failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine". Fix: `Start-Process "C:\Program Files\Docker\Docker\Docker Desktop.exe"` (PowerShell), then poll `docker info` until it succeeds (can take ~30-60s), then `docker compose -f infrastructure/docker/docker-compose.dev.yml up -d` to bring Postgres back. Any task needing real Postgres (most of `apps/api`'s own test suite) will fail with `P1001: Can't reach database server` until this is done — check for that specific error before assuming a real regression.
11. **The official Pikafish Linux release binary needs `GLIBC_2.38`, which `node:22-bookworm-slim` (Debian 12, glibc 2.36) doesn't have** — running it fails with `version 'GLIBC_2.38' not found`. `node:22-trixie-slim` (Debian 13, glibc 2.41) works. Any Dockerfile that runs this binary on a Node base image needs the `trixie` variant, not `bookworm`.
9. **Prisma's CLI refuses `migrate reset --force` when it detects it's being invoked by an AI coding agent** (checks for an env var the harness sets) — this fired when running `vitest run <file>` directly from the orchestrator's shell (which triggers `test/setup/global-setup.cjs`'s `resetTestDatabase()`), but NOT when running the same suite via `pnpm turbo run test --filter=@xq/api` (turbo's task env isolation apparently doesn't pass through whatever variable the guard checks for). The guard only ever targets `xq_test` (hardcoded check in `reset-test-db.cjs`), never a real database, so this isn't a close call — but to avoid the prompt entirely, run API tests via `pnpm turbo run test --filter=@xq/api` (or `pnpm --filter @xq/api test` from repo root), not a bare `vitest run` invoked directly.
10. **A stray empty migration directory with no `migration.sql` inside it will make `prisma migrate deploy` fail with `P3015`** ("Could not find the migration file"). Git doesn't track empty directories, so `git status` won't show it even though it's sitting right there in `prisma/migrations/`. Seen once this session (`20261024000000_add_ai_difficulty`, alongside a real, fully-formed `20261024160000_add_ai_difficulty` from the same dispatch) — likely a leftover from an earlier interrupted `prisma migrate dev` run. Fix: confirm the directory is genuinely empty and untracked (`ls` it, `git log -- <path>` returns nothing), then just `rmdir` it and retry.
6. **`apps/api/src/modules/games/game.gateway.test.ts` has a known intermittent flake** (first observed during T4.6's review, not caused by it — the test file wasn't touched): the "broadcasts the accepted move..." test occasionally throws `Cannot read properties of undefined (reading 'id')` at `GameGateway.joinGame`'s `client.data.user!.id` line. Root cause: the test's `connect()` helper resolves as soon as the client sees Socket.IO's own `'connect'` event, but `GameGateway.handleConnection` (which sets `client.data.user` via an async `resolveSessionFromCookieHeader` call) can still be in flight at that point — if the test's very next line emits `game:join` fast enough, it can race ahead of `handleConnection`'s completion. Reruns reliably pass (confirmed twice). Not fixed yet since it's pre-existing and outside every M4 task's scope so far; a real fix would likely involve an `io.use()` auth middleware (resolves before the socket is considered connected) instead of doing auth inside `handleConnection`. Worth a small dedicated task if it starts failing CI runs.
