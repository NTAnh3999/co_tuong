# Environment notes (discovered during T0.0 pre-flight)

Operational quirks on this machine that affect how tasks are briefed/dispatched. Read before writing new briefs.

1. **Codex's Windows `workspace-write` sandbox denies writes to any dot-prefixed DIRECTORY** (`.agents/`, `.github/`, `.claude/`, `.vscode/`, etc.) even though it's inside the cd'd workspace — confirmed across PowerShell `Set-Content`, `cmd echo`, and Node `fs.writeFileSync`. Dot-prefixed *files* at a normal (non-dot) directory level (e.g. `./.gitignore`, `./.nvmrc`) write fine. **Consequence: never brief a Codex task to write inside a dot-directory.** CI config, agent config, and anything under `.agents/` are Haiku/orchestrator-only. Codex's own stdout and `--output-last-message` output are written by the unsandboxed host CLI process, so redirecting those into `.agents/runs/...` from the orchestrator's shell is fine — it's only the *sandboxed guest commands* that are blocked.
2. **Codex's sandbox has no network access** (confirmed: `curl.exe` fails silently inside the sandbox). All `pnpm install`/`pnpm add` must happen on the orchestrator's side before dispatch.
3. **Codex spawns commands via native Windows PowerShell** (`powershell.exe -Command ...`), not bash, even though Git Bash is available on this machine. PowerShell's `CurrentUser` execution policy is `RemoteSigned`; scripts npm/corepack writes that get marked as from a remote zone (e.g. `pnpm.ps1`) will fail with "not digitally signed" until `Unblock-File` is run once. Already fixed for `pnpm`/`pnpx`/`npm`/`npx`/`corepack` shims under `C:\Program Files\nodejs\`. If a brief's gate command fails with a PSSecurityException about an unsigned script, that's this issue — not a real test failure; `Unblock-File` the relevant `.ps1` and retry.
4. **`@openai/codex` and other global npm packages were installed under the old Node v20.11.1 (per-nvm-version global folder)** and vanished when the user switched the system default to Node 22 via `nvm use 22`. Reinstalled `@openai/codex` globally under Node 22. Other previously-global tools (`pm2`, `win-node-env`, `ui-ux-pro-max-cli`) were NOT reinstalled — out of scope for this project, flagged to the user once, not tracked further here.
5a. **`rtk` (the user's global token-saving CLI hook) mishandles `npx prisma ...` / `prisma --version`** — it tries to resolve `prisma` as a direct program and fails ("[rtk: program not found]"), or silently garbles the real command's output (`prisma migrate dev`/`migrate status` printed truncated nonsense like "Changes:" with nothing after, even though the migration WAS actually applied correctly underneath). **Workaround: invoke the local binary directly**, e.g. `./node_modules/.bin/prisma.cmd migrate status` from `apps/api/`, which bypasses whatever rtk does to `npx`/`prisma` and shows real output. Use this pattern for any future Prisma CLI invocation from the orchestrator shell.
5. **Pikafish binary verified working**: `tools/pikafish/Pikafish-Windows-x86-64-universal.exe` + `pikafish.nnue` (not committed, gitignored — see root `.gitignore`). `go perft 4` from startpos returned `3290240`, matching the reference value used to derive ADR-018's coordinate/FEN convention — the convention is confirmed compatible with the real engine, no translation layer needed.
6. **`apps/api/src/modules/games/game.gateway.test.ts` has a known intermittent flake** (first observed during T4.6's review, not caused by it — the test file wasn't touched): the "broadcasts the accepted move..." test occasionally throws `Cannot read properties of undefined (reading 'id')` at `GameGateway.joinGame`'s `client.data.user!.id` line. Root cause: the test's `connect()` helper resolves as soon as the client sees Socket.IO's own `'connect'` event, but `GameGateway.handleConnection` (which sets `client.data.user` via an async `resolveSessionFromCookieHeader` call) can still be in flight at that point — if the test's very next line emits `game:join` fast enough, it can race ahead of `handleConnection`'s completion. Reruns reliably pass (confirmed twice). Not fixed yet since it's pre-existing and outside every M4 task's scope so far; a real fix would likely involve an `io.use()` auth middleware (resolves before the socket is considered connected) instead of doing auth inside `handleConnection`. Worth a small dedicated task if it starts failing CI runs.
