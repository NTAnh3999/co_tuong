# Brief: T0.3 — NestJS API skeleton

## Goal

Create `apps/api`: a minimal but correctly-wired NestJS 11 application skeleton that will host the REST+Socket.IO backend in later milestones (M3+). This task is scaffolding only — no game/room/auth logic yet.

## Acceptance-criteria IDs

None directly (infra enabler for M3+). Gate: app builds, starts, `/api/v1/health` returns 200, test suite passes.

## Allowed paths

- `apps/api/**` (new)
- Nothing outside `apps/api/`. If you think the root `turbo.json`/`tsconfig.base.json` needs a change, STOP and report it in QUESTIONS instead of editing it.

## Conventions (read root `AGENTS.md` too)

- Follow the exact per-package shape established in `packages/xiangqi-core` (already scaffolded in T0.2 — look at `packages/xiangqi-core/package.json`, `tsconfig.json`, `vitest.config.ts` for the turbo-task-script conventions: `build`, `lint`, `typecheck`, `test` scripts must exist and work the same way, since `turbo run build lint typecheck test` at the root already orchestrates all packages generically).
- Package name `@xq/api`, `private: true` (it's an app, not a published package — no dual ESM/CJS build needed, just a normal NestJS CJS build via `nest build` or `tsc`).
- Node engines `>=22`, uses `tsconfig.base.json` from repo root via `extends`.
- Use `unplugin-swc` + `@swc/core` with Vitest so NestJS decorator metadata (reflect-metadata based DI) works correctly under Vitest — NestJS's `@Injectable()`/`@Controller()` decorators need `emitDecoratorMetadata`, which plain esbuild/SWC-without-config doesn't emit by default; `unplugin-swc`'s Nest-specific plugin handles this. If you're unsure of the exact current API for wiring `unplugin-swc` into a Vitest config for NestJS, it's fine to also keep a plain `tsc`-based `nest build` for the `build`/`typecheck` scripts and only use the Vitest+SWC path for `test` — prioritize getting it actually working over matching one specific tutorial's exact syntax.

## What to build

1. `package.json` with dependencies: `@nestjs/core`, `@nestjs/common`, `@nestjs/platform-express`, `@nestjs/config`, `reflect-metadata`, `rxjs`, `zod` (for env validation), plus `@xq/xiangqi-core` as a workspace dependency (`"@xq/xiangqi-core": "workspace:*"`) — this is required specifically to prove CJS interop with the dual-built core package (see step 5). Dev deps: `@nestjs/cli` or just `typescript`/`ts-node` as needed, `vitest`, `supertest`, `@types/supertest`, `unplugin-swc`, `@swc/core`.
2. `src/main.ts`: bootstraps the app, sets the global route prefix `api/v1` (`app.setGlobalPrefix('api/v1')`), listens on `process.env.PORT ?? 3001`.
3. `src/app.module.ts`: root module. Import `@nestjs/config`'s `ConfigModule.forRoot({ isGlobal: true, validate })` where `validate` is a Zod-based validator function (define a small `src/config/env.schema.ts` with a Zod schema for at least `NODE_ENV` and `PORT`, parse `process.env` and throw a clear error on failure — this is the pattern later tasks like T3.8/T3.2 will extend, so keep it simple and readable).
4. `src/health/health.controller.ts`: a `GET /health` endpoint (resolves to `GET /api/v1/health` once the global prefix applies) returning `{ status: 'ok', timestamp: <ISO string> }`. Register it via a small `HealthModule` imported into `AppModule`.
5. **CJS interop proof**: somewhere reasonable (e.g. log a line in `main.ts`, or expose it via the health response as an extra field like `{ status: 'ok', timestamp, core: '@xq/xiangqi-core' }`), `import` something from `@xq/xiangqi-core` (e.g. its exported `packageName` constant from T0.2's placeholder) and use the value, to prove the dual-built package's CJS entry point (`require`/`import` under Nest's CommonJS compilation) resolves correctly. This doesn't need to be elaborate — the point is a real import + real usage, not a comment.
6. `test/health.e2e-spec.ts` (or `src/health/health.controller.spec.ts`, your call) using `supertest` against a bootstrapped Nest app (via `@nestjs/testing`'s `Test.createTestingModule`) asserting `GET /api/v1/health` returns 200 and a body with `status: 'ok'`.
7. `tsconfig.json` extending `../../tsconfig.base.json` with whatever `compilerOptions` NestJS needs (e.g. `experimentalDecorators`, `emitDecoratorMetadata`, `target`/`module` overrides if NestJS's CJS build needs something different from the base's `NodeNext` — NestJS conventionally builds to CommonJS; override `module`/`moduleResolution` in this package's own tsconfig if `NodeNext` causes friction with Nest's decorator/DI patterns, and say so in KNOWN GAPS if you do).
8. `package.json` scripts: `build` (compiles to `dist/`), `start` (runs `node dist/main.js` — not required to work for this task, just wire it for later use), `lint` (`tsc --noEmit` is fine for now, same as T0.2's packages — real ESLint arrives in T0.5), `typecheck` (`tsc --noEmit`), `test` (`vitest run`).
