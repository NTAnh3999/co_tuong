## Background: what a UCI engine conversation looks like

Pikafish speaks the standard UCI protocol used by chess/Xiangqi engines: you spawn the binary as a subprocess, write newline-terminated commands to its stdin, and read newline-terminated responses from its stdout. Key commands you need to support:

- `uci` → engine replies with `id name ...`, `id author ...`, a list of `option` lines, then `uciok`.
- `isready` → engine replies `readyok` once ready (also used to synchronize after sending commands).
- `position startpos` or `position startpos moves <uci1> <uci2> ...` or `position fen <fen> moves ...` → sets the current position, no reply.
- `go perft <depth>` → engine prints one line per legal move at the root in the form `<uci-move>: <count>`, then a blank line, then `Nodes searched: <total>`. This is the "divide" format — per-move subtree counts plus the grand total.
- `d` (Pikafish-specific debug command) → prints a human-readable board plus a line containing `Fen: <fen>` — useful for round-trip-checking your own FEN serialization against the engine's.
- `go movetime <ms>` → engine thinks for the given time and eventually prints `bestmove <uci-move>` (possibly with a `ponder` field you can ignore).
- `quit` → terminate the engine process cleanly.

You already proved this works manually during T0.0 (see `.agents/NOTES.md`): piping `uci\nisready\nposition startpos\ngo perft 4\nquit\n` into the binary produced a valid divide output ending in `Nodes searched: 3290240`.

## What to build

### 1. `src/uci/engine-process.ts`

A class/function wrapping `node:child_process.spawn` for the engine binary:
- Constructor/factory takes the binary path (from `process.env.PIKAFISH_PATH`, no default/fallback — if unset, document that callers must check for this before using it).
- Writes commands to stdin (one per call, newline-terminated).
- Exposes a way to await a specific terminal line pattern (e.g. `waitFor(predicate: (line: string) => boolean, timeoutMs): Promise<string[]>` that buffers lines until the predicate matches or times out, returning all buffered lines).
- Handles process exit/error events, kills the process on `dispose()`/`close()`.
- No global/module-level singleton — each instance owns one subprocess, so tests and later the worker pool (M5) can create independent instances.

### 2. `src/uci/commands.ts`

Small, focused helper functions built on `engine-process.ts`:
- `initEngine(engine): Promise<void>` — sends `uci`, waits for `uciok`, sends `isready`, waits for `readyok`.
- `setPosition(engine, { fen?: string, moves?: string[] }): void` — sends the appropriate `position ...` command (default to `startpos` if no `fen` given).
- `perft(engine, depth: number): Promise<{ moves: Record<string, number>; total: number }>` — sends `go perft <depth>`, parses the per-move divide lines and the `Nodes searched:` total line into the shape above.
- `getFen(engine): Promise<string>` — sends `d`, parses out the line containing `Fen: ` and returns everything after it, trimmed.
- `bestMove(engine, movetimeMs: number): Promise<string>` — sends `go movetime <ms>`, waits for and parses the `bestmove <uci>` line (ignore any `ponder` suffix).

### 3. `src/uci/index.ts` — re-export the above; update `services/pikafish-worker/src/index.ts` to re-export from `./uci/index.js` too (keep the existing placeholder export from T0.2 alongside it, don't remove it).

### 4. Tests against a **fake/stub engine**, not the real binary

`src/uci/*.test.ts`: since CI and most dev machines won't have `PIKAFISH_PATH` set, write a tiny stub "engine" for these unit tests — e.g. a small Node script fixture (or an in-process fake implementing the same stdin/stdout line-based contract via a `Transform`/`PassThrough` stream, your choice) that responds to `uci`/`isready`/`position`/`go perft N`/`d`/`go movetime` with scripted canned output, so `engine-process.ts` and `commands.ts` are tested without depending on the real engine or network. Cover: `initEngine` resolves on `uciok`+`readyok`; `perft` parses a multi-move divide block correctly including the total; `getFen` extracts the FEN from a `d`-command-style block; `bestMove` parses a `bestmove` line.

### 5. Live smoke test against the real binary — **skipped by default**

One additional test file, e.g. `src/uci/live.smoke.test.ts`, that:
- Uses Vitest's `describe.skipIf(!process.env.PIKAFISH_PATH)` (or equivalent) to skip entirely when `PIKAFISH_PATH` isn't set.
- When it *is* set: spawns the real engine, runs `perft(engine, 4)` from the start position, and asserts `total === 3290240` (the exact value verified manually in T0.0) — this is a regression guard that the UCI client's own parsing is correct, not just the stub.

### 6. `packages/xiangqi-core/fixtures/schema.ts`

A small TypeScript module (no Zod dependency needed here — `xiangqi-core` must stay dependency-free per its own `AGENTS.md`, pure `interface`/`type` declarations are fine) defining the shape M1's oracle fixtures will use:
```ts
export interface PositionFixture {
  id: string;
  fen: string;
  source: 'curated' | 'random-playout';
  description?: string;
  // depth -> expected perft divide result at that depth from this position
  perft?: Record<number, { moves: Record<string, number>; total: number }>;
}

export interface FixtureFile {
  generatedAt: string;
  engine: { path: string; perftBaseline: number }; // perftBaseline = startpos depth-4 total, sanity marker
  positions: PositionFixture[];
}
```
Put this under `packages/xiangqi-core/fixtures/schema.ts` (plain `.ts`, not compiled/bundled as part of the package's public API — it's test/tooling infrastructure, not part of `src/`). Do not add a build step for this directory; it's consumed directly by test/tooling scripts via `ts-node`/Vitest's native TS support, not imported by the package's published `dist/`.

### 7. `services/pikafish-worker/scripts/generate-golden-fixtures.ts` + a root-callable script

A script that:
- Checks `process.env.PIKAFISH_PATH`; if unset, logs a clear message ("PIKAFISH_PATH not set, skipping golden fixture generation") and exits 0 (success) — this must NOT fail CI or a dev machine without the engine installed.
- If set: spawns the engine, runs `perft` at depths 1–3 (depth 4 only if an env flag like `SLOW=1` is also set, since it's slower) from the start position, and writes a `FixtureFile` (per the schema above) to `packages/xiangqi-core/fixtures/golden/startpos.json`, with `engine.perftBaseline` set to the depth-4 total if computed, else the depth-3 total — just document clearly in the file which depth `perftBaseline` reflects.
- Add a root-level convenience: a `"golden:gen"` script in `services/pikafish-worker/package.json` that runs this script (e.g. via `tsx` — add it as a dependency if needed, or use Node's native `--experimental-strip-types`/whatever is simplest given Node 22 is in use — your call, note what you picked).
