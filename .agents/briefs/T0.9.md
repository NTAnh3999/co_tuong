## Content for each ADR (orchestrator-authored decisions — write these up in the template, in Vietnamese, do not change the substance)

### ADR-017 — RuleSet `xq-casual-1.0.0` (resolves Q-001)

Decision: a casual beta RuleSet, not an official AXF-certified ruleset (the baseline docs explicitly allow shipping a documented casual ruleset as long as it isn't marketed as "official competitive rules" — see `docs/spec/v1.0/01_PRD_Product.md` section 5, "Ranh giới chất lượng").

Adjudication order, applied after every move:
1. No legal moves for the side to move → that side loses. Reason `CHECKMATE` if in check, else `STALEMATE` (in Xiangqi this is a loss, not a draw — different from international chess).
2. Repetition: position key = board + side-to-move (first two FEN fields). On a key's 3rd occurrence, inspect the plies between its 1st and 3rd occurrence: if exactly one side gave check on every one of its own moves in that span, that side loses (reason `PERPETUAL_CHECK`); otherwise it's a draw (reason `REPETITION`).
3. No-capture limit: 120 plies (60 full moves) without a capture → draw, reason `MOVE_LIMIT` (matches Pikafish's internal rule60 counter, so FEN halfmove-clock field means the same thing in both systems).
4. Insufficient material: if neither side has any Chariot, Horse, Cannon, or Soldier left → draw, reason `INSUFFICIENT_MATERIAL`.
5. External terminal events: `RESIGNATION`, `DRAW_AGREEMENT`, `TIMEOUT` (or `TIMEOUT_INSUFFICIENT_MATERIAL` if the opponent has no attacking material), `ABANDONMENT`, `ABORTED` (no result).

Explicitly simplified / NOT implemented: perpetual chase (truy đuổi liên tục) detection. A chase-repetition situation resolves as a draw under rule 2 above, same as any other repetition. This must be disclosed to users (UI disclaimer on `/rules` and in the result dialog): "Luật giản lược (casual) — không phải luật thi đấu chính thức AXF."

Every game stores a `ruleSetVersion` field so historical games remain reproducible if the ruleset changes later. The adjudicator is designed to be pluggable (a future `axf-*` ruleset with full chase detection could be added later) — that work is explicitly NOT scheduled in the current M0–M7 plan.

### ADR-018 — Coordinates, FEN, UCI (resolves Q-002)

Decision: adopt the Pikafish/UCCI convention directly, with no translation layer.

- Files `a`-`i` (left to right from Red's viewpoint), ranks `0`-`9`, Red's own back rank = rank `0`. Board array index = `rank * 9 + file`. Rotating the visual board never changes logical coordinates.
- FEN: rows emitted from rank 9 down to rank 0 (top to bottom as conventionally printed), piece letters `K A B N R C P` (uppercase = Red), side-to-move field `w` (Red) or `b` (Black), fields 3–4 always `- -`, then halfmove-clock (plies since last capture) and fullmove number. Starting position FEN: `rnbakabnr/9/1c5c1/p1p1p1p1p/9/9/P1P1P1P1P/1C5C1/9/RNBAKABNR w - - 0 1`.
- Moves: 4-character UCI coordinate form, e.g. `h2e2` — identical to Pikafish's own move format.
- Verification performed during this ADR's drafting: the real Pikafish engine binary was run locally (`go perft 4` from the start position) and returned `3290240`, matching the expected reference value for this exact convention — confirming no translation layer is needed between `xiangqi-core` and the Pikafish adapter.

### ADR-019 — Clock and disconnect policy (resolves Q-003)

Decision:
- Time control presets: 5+3, **10+5 (default)**, 15+10 (minutes + increment in seconds). Local and AI games are untimed.
- A game becomes ACTIVE once both seats are filled. Each side's very first move is untimed but must be submitted within 60 seconds or the game ends with reason `ABORTED`. Red's clock starts counting down after Black's first move (i.e., after both sides have moved once... clarify: actually after each side's own first move, their own clock starts for their second move onward — the first move of each side is free).
- Clock accounting uses server receipt time only (no client-reported latency compensation). On an accepted move: `remaining[mover] -= serverNow - turnStartedAt`; if this would be ≤0, the move is rejected with reason `TIME_EXPIRED` and the game finishes with reason `TIMEOUT`. Otherwise the increment is added and `activeColor` flips.
- A server-side timer plus a lazy check on every move/sync enforces timeout; the game is finished exactly once via a conditional database update (`WHERE status='ACTIVE' AND gameVersion=?`), so a race between a timeout-firing and a move-arriving can't double-finish a game.
- No pausing is supported in MVP; disconnecting does not stop the clock.
- If the side to move has had no connected socket for ≥60 seconds, the opponent may claim a win (reason `ABANDONMENT`), or choose to keep waiting.
- The client re-syncs the full game snapshot on reconnect and on the browser tab becoming visible again (`visibilitychange`); the displayed clock uses a server-time offset, not local wall-clock time alone.
- Only one draw offer may be pending at a time; it's cleared when the opponent moves or declines; after a decline, the same player must wait 10 plies before offering again.

### ADR-020 — Guest sessions (resolves Q-004)

Decision: an opaque, randomly generated 32-byte session token, stored SHA-256-hashed server-side, delivered to the client as an httpOnly cookie (`Secure` in production, `SameSite=Lax`) — not a JWT. 30-day sliding expiry. Game seats are bound to the internal `userId`, never to a Socket.IO `socket.id` (which can change across reconnects). The same cookie reused in multiple browser tabs is treated as the same player; losing the cookie means losing the seat (an accepted tradeoff for a casual MVP).

### ADR-021 — Data retention (resolves Q-005)

Decision: guest accounts inactive for 90 days are purged. Finished games are retained for 180 days. Server logs are retained for 14 days and must not contain personal data beyond a chosen nickname and IP address (for abuse investigation only).

### ADR-022 — Rematch (resolves Q-006)

Decision: a rematch creates a new game in the same room, with colors swapped and the same time control as the original game. Both players must explicitly accept the rematch offer; the offer expires after 60 seconds or if either player leaves the room.

### ADR-023 — Pikafish GPLv3 license handling (resolves Q-007)

Decision: Pikafish runs only server-side, as an unmodified upstream binary built from a specific pinned release tag, inside its own container, communicated with over UCI via the worker service (never shipped to the browser as WASM or otherwise distributed to end users). A `/licenses` page in the product must link to the exact Pikafish source tag used and reproduce its GPLv3 notice. **This ADR explicitly flags that final legal/user sign-off is required before the AI feature can go to a public release — this does not block development work in M5, only the public-release gate in M7.**

### ADR-024 — AI difficulty levels (resolves Q-008)

Decision: three difficulty levels implemented via engine search-time and MultiPV sampling (not an artificially weakened engine):
- **Dễ (Easy):** 50ms per move, MultiPV 5, pick uniformly at random among the candidate moves within 300 centipawns of the best move found.
- **Vừa (Medium):** 200ms per move, MultiPV 3, pick (weighted) among candidates within 80 centipawns of best.
- **Khó (Hard):** 1000ms per move, MultiPV 1 (always the engine's best move).
Worker pool size 2 concurrent engine instances, queue length cap 20, hard timeout = movetime + 1.5 seconds before falling back.

### ADR-025 — Tooling conventions (housekeeping, no corresponding Q-number)

Decision: internal package scope `@xq/*`; internal packages build dual ESM+CJS output (NestJS requires CJS, Next.js/modern tooling prefers ESM); Zod is the sole runtime validation/schema library across the stack; Vitest is the sole unit/integration test runner, Playwright the sole E2E runner; `unplugin-swc` is used so NestJS decorator metadata works correctly under Vitest.
