## The exact contract (ADR-018 — read `docs/adr/ADR-018-coordinates-fen-uci.md` in full before starting)

- **Files**: `a`–`i` (9 files), left to right from Red's own viewpoint.
- **Ranks**: `0`–`9` (10 ranks). **Red's own back rank is rank 0.** Black's back rank is rank 9.
- **Board array**: flat array of length 90. `index = rank * 9 + file`, where `file` is 0-8 for `a`-`i` and `rank` is 0-9. So `a0` → index 0, `i0` → index 8, `a9` → index 81, `i9` → index 89.
- **`Square`**: a branded/validated string type matching `/^[a-i][0-9]$/` (e.g. `"e4"`). Do not allow a plain `string` to be assignable without going through a parsing/validation function — use a branded type (e.g. `type Square = string & { readonly __brand: 'Square' }`) with a `toSquare(input: string): Square` function that throws on invalid input, plus `squareToIndex(sq: Square): number` and `indexToSquare(index: number): Square` conversions. Round-trip (`indexToSquare(squareToIndex(sq)) === sq`) must hold for all 90 valid squares.
- **`Color`**: `'red' | 'black'`.
- **`PieceType`**: `'GENERAL' | 'ADVISOR' | 'ELEPHANT' | 'HORSE' | 'CHARIOT' | 'CANNON' | 'SOLDIER'`.
- **`Piece`**: `{ color: Color; type: PieceType }`.
- **`Position`**: `{ board: readonly (Piece | null)[]; turn: Color; halfmoveClock: number; fullmoveNumber: number }` — length of `board` is always 90. `halfmoveClock` = plies since the last capture (matches Pikafish's "rule60" counter — needed later for ADR-017's 120-ply no-capture draw rule). `fullmoveNumber` starts at 1 and increments after Black's move (standard FEN convention).
- **`createInitialPosition(): Position`**: the standard starting layout, 32 pieces, Red at ranks 0-2 area (General on `e0`, Advisors `d0`/`f0`, Elephants `c0`/`g0`, Horses `b0`/`h0`, Chariots `a0`/`i0`, Cannons `b2`/`h2`, Soldiers on `a3`,`c3`,`e3`,`g3`,`i3`), Black mirrored at the top (rank 9 back rank, Cannons rank 7, Soldiers rank 6). `turn: 'red'`, `halfmoveClock: 0`, `fullmoveNumber: 1`.

## FEN format (Pikafish/UCCI convention — exact)

- Piece-placement field: 10 rows separated by `/`, **emitted from rank 9 down to rank 0** (i.e. the top of the printed board, Black's side, comes first — this is the opposite order from the internal rank-0-at-index-0 array layout, so `toFen`/`fromFen` must explicitly reverse rank order, don't just iterate the array in index order).
- Each row: run-length-encode empty squares as digits (1-9), pieces as single letters, read left-to-right as files `a`→`i`.
- Piece letters: `K`=General, `A`=Advisor, `B`=Elephant, `N`=Horse, `R`=Chariot, `C`=Cannon, `P`=Soldier. **Uppercase = Red, lowercase = Black.**
- Side-to-move field: `w` (Red) or `b` (Black).
- Fields 3 and 4 are always literal `-` `-` (castling/en-passant equivalents don't exist in Xiangqi; these fields exist purely for UCI/FEN format compatibility with chess tooling like Pikafish).
- Field 5: halfmove clock (matches `Position.halfmoveClock`).
- Field 6: fullmove number (matches `Position.fullmoveNumber`).
- **Exact starting FEN** (verify your `toFen(createInitialPosition())` produces exactly this string, character-for-character): `rnbakabnr/9/1c5c1/p1p1p1p1p/9/9/P1P1P1P1P/1C5C1/9/RNBAKABNR w - - 0 1`

Note the letter casing above: the FEN spec traditionally uses `rnbakabnr` for pieces, but your `PieceType`→letter mapping should use `R`=Chariot (not Rook), `N`=Horse (not Knight), `B`=Elephant (not Bishop), `A`=Advisor, `K`=General, `C`=Cannon, `P`=Soldier — this is Xiangqi notation, not international chess notation, even though it reuses chess's letters for compatibility with UCI engines. Double check against the exact starting FEN string above, letter by letter, to make sure your mapping is right (e.g. the back rank `rnbakabnr` reading left to right as files a-i is: Chariot, Horse, Elephant, Advisor, General, Advisor, Elephant, Horse, Chariot).

### `toFen(position: Position): string` and `fromFen(fen: string): Position`

Must round-trip exactly: `fromFen(toFen(p))` deep-equals `p` for any valid `Position`, and `toFen(fromFen(fen)) === fen` for any well-formed FEN string (modulo FEN strings that have redundant-but-equivalent empty-square run-length encoding — e.g. `11` vs `2` for two empty squares in a row; your `toFen` should always emit the canonical maximal-run-length form, and `fromFen` should accept any valid encoding, canonical or not).

`fromFen` must validate strictly and throw a clear `Error` (not silently produce a broken position) on: wrong number of rows, a row that doesn't sum to exactly 9 files, an invalid piece letter, missing/malformed side-to-move field, non-numeric halfmove/fullmove fields. Validate (and throw if violated): exactly one General per side, and both Generals inside their own palace (files d-f, Red's palace ranks 0-2, Black's palace ranks 7-9 — palace *squares* don't need to be enforced by this task's move-legality logic yet, just validate the *starting*/*parsed* position has each General in a structurally sane palace location — if this feels like scope creep for a pure codec task, it's fine to implement it as a focused structural check here since `fromFen` is also the main gate against malformed game state entering the system later).

## `encodeMove` / `decodeMove`

Move text format is 4-character UCI: `fromSquare + toSquare`, e.g. `"h2e2"` — identical to Pikafish's own move notation, verified against the real engine in T0.8 (see `.agents/NOTES.md` and `packages/xiangqi-core/fixtures/golden/startpos.json`, generated by running `go perft` against the real binary — the move strings in that file's `moves` keys are the exact format `encodeMove`/`decodeMove` must produce/accept).

```ts
interface Move { from: Square; to: Square }
function encodeMove(move: Move): string;   // e.g. { from: 'h2', to: 'e2' } -> "h2e2"
function decodeMove(text: string): Move;   // "h2e2" -> { from: 'h2', to: 'e2' }
```
`decodeMove` must validate the string is exactly 4 characters forming two valid squares, throwing a clear error otherwise. No promotion suffix handling needed (Xiangqi has no pawn promotion).
