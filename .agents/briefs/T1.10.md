# Brief: T1.10 — Independent adversarial review of the rules engine

## Goal

You are a SEPARATE reviewer, not the original author, of `packages/xiangqi-core`. Your job is to find real bugs in the move-generation, legality, and game-adjudication logic by reading the code critically against the authoritative rules — not to re-run the existing test suite (it already passes) and not to trust that passing tests mean the implementation is correct (tests can share the same blind spot as the code they test). Think adversarially: what board configuration would break this code in a way none of the existing ~135 tests happen to cover?

**You are in a READ-ONLY sandbox. You cannot and must not edit any file.** Your deliverable is a written list of findings in your final message.

## Scope

Review these files against the authority documents listed:
- `packages/xiangqi-core/src/moves.ts` (pseudo-legal movement + attack detection) against `docs/spec/v1.0/03_Technical_Architecture.md` §4.4 and the piece-movement rules recapped in `.agents/briefs/T1.2.md`.
- `packages/xiangqi-core/src/legality.ts` (check detection, flying-general, legal-move filtering, `applyMove`, `perft`/`divide`) against `.agents/briefs/T1.3.md`'s algorithm description.
- `packages/xiangqi-core/src/game.ts` (`evaluateGame`, repetition/perpetual-check adjudication) against `docs/adr/ADR-017-ruleset-casual-v1.md` **in full** — this is the ground truth for game-ending rules, read it directly rather than relying on any brief's paraphrase.
- `packages/xiangqi-core/src/fen.ts` (FEN codec) against `docs/adr/ADR-018-coordinates-fen-uci.md`.

You may also read any test file to understand what's already covered (useful for knowing where NOT to waste time re-finding already-caught bugs), and `packages/xiangqi-core/fixtures/golden/oracle.json`/`startpos.json` to see what's already been verified against the real Pikafish engine (225+ positions have been cross-checked — treat move-generation bugs that would show up in a basic perft comparison as already well-covered; focus your scrutiny on logic that ISN'T perft-checkable, especially: the repetition/perpetual-check window logic in `game.ts` (perft doesn't test this at all), the flying-general check-detection logic in `legality.ts`, and interactions between multiple rules).

## Specific things worth checking carefully

- Does `isSquareAttacked`'s Cannon handling correctly distinguish "attacking" (through exactly one screen) from "could slide to" in EVERY caller context, or could there be a path where a Cannon's non-capturing slide destination gets treated as if it attacks that square?
- In `legality.ts`'s flying-general check: does the file-matching logic correctly handle BOTH Generals being compared, with no off-by-one in the "squares strictly between them" range? Consider a case where the Generals are adjacent on the same file (zero squares between) — is that correctly detected as facing?
- In `game.ts`'s repetition window logic: what happens if a key occurs a 4th or 5th time (not just exactly 3) by the time `evaluateGame` is called — does the window computation (`firstPly` to `final.ply`) still produce a sensible, ADR-017-consistent result, or could a caller that doesn't call `evaluateGame` after every single move get confused? (This may be a documented/acceptable caller-contract assumption rather than a bug — if so, say that explicitly rather than flagging it as broken.)
- Does `evaluateGame`'s priority ordering (checkmate/stalemate > repetition > move-limit > insufficient-material > external event) ever produce a WRONG result when two conditions are simultaneously true in a way the existing tests don't cover (e.g., a position that's both at the move-limit AND has insufficient material — does the order between those two matter, and does the code match ADR-017's stated order)?
- Horse/Elephant board-edge interactions: are there any (file, rank) combinations near the board edge where the leg/eye-blocking check could read an out-of-bounds array index instead of correctly treating it as "off-board, so blocked by boundary rather than by a piece"?
- `applyMove`'s halfmove-clock reset logic: does it correctly detect "no capture occurred" using the position BEFORE the move (checking what was at the destination square prior to the move), not some other signal that could be fooled by edge cases?

## What NOT to do

- Do not re-verify things the oracle fixtures already cover (basic per-piece move generation, basic legality) — that's redundant with 225 Pikafish-cross-checked positions.
- Do not nitpick code style, naming, or performance — this review is about correctness bugs only.
- Do not report a "finding" you haven't actually traced through with a concrete FEN/position and specific expected-vs-actual behavior — vague suspicions aren't actionable. If you're not sure whether something is actually a bug, say so explicitly and give your best read, but clearly distinguish "confirmed bug, here's the exact failing case" from "possible concern, unverified."

## Final message format

For each finding (if any): a concrete FEN or position description, the move/query that exposes the issue, what the CURRENT code does, what it SHOULD do per the authority document, and which file/function is responsible. If you find zero real bugs, say so plainly and briefly summarize what you checked — don't manufacture findings to seem thorough.

```
FINDINGS: <list, or "none found" with a brief summary of what was checked>
AREAS REVIEWED:
CONFIDENCE NOTES: <anything you weren't able to fully verify given the read-only constraint>
```
