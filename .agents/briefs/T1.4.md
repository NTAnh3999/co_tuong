# Brief: T1.4 — Engine-oracle fixtures (curated + random-playout, cross-checked against real Pikafish)

## Goal

T1.3's start-position perft match against the golden fixture is strong evidence the engine is correct, but it only exercises the OPENING position. This task broadens that evidence across a wide range of positions — including ones specifically designed to exercise tricky interactions (cannon screens, horse-leg blocks, pins, near-facing-generals, palace edges, crossed soldiers, mate/stalemate-adjacent positions) and a batch of positions reached via random legal self-play — by cross-checking `xiangqi-core`'s own `divide()` against the real Pikafish binary's `go perft` for every one of them. Any mismatch is a real bug in T1.1/T1.2/T1.3, found before it could hide in a corner case nobody thought to test by hand.

## Acceptance-criteria IDs

CORE-02, CORE-03 (broad correctness evidence), CORE-06 (FEN round-trip across many positions, not just the start position)

## Allowed paths

- `packages/xiangqi-core/fixtures/**` (new curated-position data file, new golden fixture output)
- `packages/xiangqi-core/src/oracle.test.ts` (new — loads and checks fixtures, no live engine dependency)
- `services/pikafish-worker/scripts/**` (extend or add alongside T0.8's `generate-golden-fixtures.ts` — your call whether to extend that script or add a new one; a new one is probably cleaner since this is a meaningfully different job)
- `services/pikafish-worker/src/uci/live.smoke.test.ts` MAY be extended, or add a new live test file under `services/pikafish-worker/src/` or `packages/xiangqi-core/src/` (your call) for the live cross-check — must be skipped by default per the existing `PIKAFISH_PATH` pattern from T0.8.
- `services/pikafish-worker/package.json` (add a script entry only, e.g. `"oracle:gen"`, following T0.8's `golden:gen` pattern)

## Forbidden

- Do not add `Math.random()` or any nondeterminism inside `packages/xiangqi-core/src/**` — per its `AGENTS.md`, that package must stay pure. Random-playout generation (picking random legal moves to reach test positions) belongs in the GENERATOR SCRIPT under `services/pikafish-worker/scripts/`, which may import and call `xiangqi-core`'s pure functions (`createInitialPosition`, `getAllLegalMoves`, `applyMove`) to do the random walk, using `Math.random()` itself since it's tooling, not engine code.
- Do not modify `packages/xiangqi-core/fixtures/golden/startpos.json` (T1.3's existing fixture) — add new fixture file(s) alongside it.
- Do not touch `packages/xiangqi-core/src/{types,square,position,fen,move,moves,legality}.ts` — if you believe one of them has a bug (a real mismatch against the oracle), STOP and report the exact FEN + move + expected-vs-actual in QUESTIONS rather than fixing it yourself; the orchestrator will create a dedicated fix task so the fix gets the same scrutiny the original implementation did.

## What to build

### 1. Curated tricky positions (~25)

A data file, e.g. `packages/xiangqi-core/fixtures/curated-positions.ts`, exporting an array of `{ id: string; fen: string; description: string }`. Construct FENs (by hand, reasoning about the board, or by taking short move sequences from the start position and computing the resulting FEN) covering at least:
- A Cannon with exactly one screen threatening a capture, and a near-miss (zero screens, or two screens) in the same position.
- A Horse with its leg blocked in one direction but free in another.
- A pinned piece: moving it would expose the General to a Chariot/Cannon/Horse attack.
- A near-facing-Generals position: one piece away from illegal (moving it would create the facing condition) — NOT the illegal position itself (that wouldn't be a valid position to feed the engine as "the position to search from", since it's only illegal as a RESULT of a move, not as a starting point to analyze from — the fixture positions themselves must be legal/reachable positions).
- Elephant near the river boundary (one valid retreat, one blocked-by-river option).
- Soldiers that have crossed the river for both colors, including a case with two Soldiers adjacent on the same rank (crossed-soldier interactions).
- At least 2-3 positions one move away from checkmate or stalemate (i.e., the side to move has very few or zero legal moves) — these are valuable because move-generation bugs often show up exactly at the boundary of "no moves left".
- Make sure every curated FEN is itself a **valid, legal-reachable** position (exactly one General per side, no existing facing-Generals condition unless that's specifically what you're testing via `isInCheck` elsewhere — for the oracle fixtures specifically, stick to normal legal positions since you're comparing move generation, not check-detection in isolation).

### 2. Random-playout positions (~200)

A generator script, e.g. `services/pikafish-worker/scripts/generate-oracle-fixtures.ts`, that:
- Imports `createInitialPosition`, `getAllLegalMoves`, `applyMove`, `toFen` from `@xq/xiangqi-core`.
- Runs ~200 independent random self-play games from the start position, each for a random number of plies (e.g. uniformly between 4 and 40), picking a uniformly random legal move at each step (stop early if no legal moves remain — that's fine, it's still a valid position to test). Collect the resulting position's FEN after each playout.
- Dedupe identical FENs if you like (not required, but avoids wasted engine calls).

### 3. Cross-check against the real engine

Reusing T0.8's UCI client (`services/pikafish-worker/src/uci/`): spawn **one** engine instance for the whole batch (not one per position — that would be slow and wasteful), and for each position (curated + random-playout):
- `setPosition(engine, { fen })`
- Run `perft` via the `commands.ts` helper at **depth 2** for curated positions and **depth 1** for random-playout positions (depth 1 is enough to validate move generation breadth at scale; depth 2 on the smaller curated set gives stronger coverage of multi-ply interactions like discovered checks). If performance allows depth 2 for everything within a reasonable total run time (a couple of minutes), prefer that — your call based on what you observe when you run it.
- Compare the engine's per-move divide breakdown against `divide(fromFen(fen), depth)` from `xiangqi-core`. They must match EXACTLY (same move set, same per-move subtree counts).
- Write the full result set to `packages/xiangqi-core/fixtures/golden/oracle.json` conforming to the existing `FixtureFile`/`PositionFixture` schema in `packages/xiangqi-core/fixtures/schema.ts` (reuse it, don't redefine).
- The script should check `PIKAFISH_PATH` and exit 0 with a clear message if unset — same pattern as T0.8's `generate-golden-fixtures.ts`. Add a `"oracle:gen"` script entry to `services/pikafish-worker/package.json`.
- **If you find any real mismatch between `xiangqi-core` and the engine while building this**, do NOT silently fix `xiangqi-core` yourself (see Forbidden above) — isolate the minimal failing FEN + depth, note it precisely in QUESTIONS, and continue generating the rest of the fixture set (exclude only the confirmed-mismatching position from the committed fixture file, with a comment explaining why, so the fixture file itself stays 100%-verified-correct).

### 4. Fixture-backed regression test (always runs, no engine needed)

`packages/xiangqi-core/src/oracle.test.ts`: loads `packages/xiangqi-core/fixtures/golden/oracle.json` (same JSON-loading approach T1.3 used for `startpos.json`) and asserts `divide(fromFen(fixture.fen), depth)` matches the recorded result, for every position in the fixture file, at whatever depth(s) were recorded for it. This is the test that actually runs in CI/every dev machine — it doesn't need `PIKAFISH_PATH`, it just replays the already-verified fixture data.

### 5. Live cross-check test (skipped without `PIKAFISH_PATH`)

A smaller live test — e.g. 5-10 of the curated positions, not all 225 — that actually spawns the real engine (same `describe.skipIf(!process.env.PIKAFISH_PATH)` pattern as T0.8) and re-verifies live, as a guard against the committed fixture going stale relative to the UCI client's own parsing logic. Put this wherever makes sense given your file organization (`packages/xiangqi-core/src/` can't easily spawn a subprocess engine without importing from `pikafish-worker`, which would violate the core package's purity rule — so this live test almost certainly belongs in `services/pikafish-worker/src/`, importing `@xq/xiangqi-core`'s `divide`/`fromFen` for the comparison; make sure `@xq/xiangqi-core` is already a dependency there from earlier tasks, or add it).

If you do, report the exact counts (e.g. "225/225 positions matched exactly") in your final message.

## Stop-and-report conditions

- Any confirmed mismatch between `xiangqi-core` and the real engine — report precisely (FEN, depth, move, expected count, actual count) rather than patching `xiangqi-core` yourself.
- If spawning the engine for 225 positions in one run is too slow in practice, reduce the random-playout count (document the actual number used and why) rather than silently timing out or giving up.
