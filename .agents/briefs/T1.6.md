# Brief: T1.6 — GameRecord, replay, RuleSet, evaluateGame (ADR-017)

## Goal

Implement the game-level layer on top of T1.1-T1.3's position/legality engine: a `GameRecord` representing a full game's move history, a pure `replay()` function reconstructing every intermediate position, and `evaluateGame()` — the adjudicator that decides whether/why a game has ended, implementing `docs/adr/ADR-017-ruleset-casual-v1.md`'s rules **exactly**, in the **exact order** specified there. This is the most rule-sensitive task in the project after T1.1-T1.3 — read ADR-017 in full before starting, it is the authority, not this brief's paraphrase of it (though this brief's API design decisions below ARE authoritative, since they resolve some implementation details ADR-017 doesn't specify at the type level).

## Acceptance-criteria IDs

CORE-04 (game result classification), CORE-05 (repetition/perpetual-check adjudication)

## Allowed paths

- `packages/xiangqi-core/src/**` (new files; do not modify T1.1-T1.3's existing files' behavior, only import from them)
- `packages/xiangqi-core/src/index.ts` (extend exports)

## Forbidden

- Do not implement perpetual-chase detection — ADR-017 explicitly excludes it from this ruleset version. A chase situation must resolve via the plain repetition rule (item 2 below), nothing more specific.
- Do not add runtime dependencies, `Date.now()`, or `Math.random()` to anything in `src/`.
- Do not touch `moves.ts` or `legality.ts`.

## Design decision: no `clocks` parameter — core stays clock-ignorant

The original architecture sketch in `docs/spec/v1.0/03_Technical_Architecture.md` §4.3 proposed `evaluateGame(gameRecord, clocks, ruleSet)`. **This brief overrides that detail**: clock/timer state is a server-session concern (M3/M4, NestJS layer), not something `xiangqi-core` should know about — the package must stay pure and clock-ignorant (no `Date.now()`, no timer logic). Instead, `GameRecord` carries an optional `terminalEvent` field (defined below) that the FUTURE server layer will attach once it decides externally that a game ended via resignation/draw-agreement/timeout/abandonment/abort. `evaluateGame` just needs to know THAT such an event occurred and who it affected — not compute timing itself.

## Required types and API

```ts
type ResultReason =
  | 'CHECKMATE' | 'STALEMATE'                          // board-derived, no legal moves
  | 'PERPETUAL_CHECK' | 'REPETITION'                   // board-derived, 3rd repetition of a position
  | 'MOVE_LIMIT'                                        // board-derived, 120-ply no-capture limit
  | 'INSUFFICIENT_MATERIAL'                             // board-derived, neither side has Chariot/Horse/Cannon/Soldier
  | 'RESIGNATION' | 'DRAW_AGREEMENT'
  | 'TIMEOUT' | 'TIMEOUT_INSUFFICIENT_MATERIAL'
  | 'ABANDONMENT' | 'ABORTED';                          // external events

interface GameResult {
  readonly winner: Color | null;   // null for a draw, or for ABORTED (no result)
  readonly reason: ResultReason;
}

type TerminalEvent =
  | { readonly type: 'RESIGNATION'; readonly loser: Color }
  | { readonly type: 'DRAW_AGREEMENT' }
  | { readonly type: 'TIMEOUT'; readonly loser: Color }
  | { readonly type: 'ABANDONMENT'; readonly loser: Color }
  | { readonly type: 'ABORTED' };

interface GameRecord {
  readonly initialFen: string;         // typically the standard start FEN, but must support any legal starting FEN (for puzzles, later)
  readonly moves: readonly Move[];     // the full move sequence played so far
  readonly ruleSetVersion: string;     // e.g. 'xq-casual-1.0.0'
  readonly terminalEvent?: TerminalEvent; // present only if the game ended via an event NOT derivable from the board state alone
}

interface ReplayStep {
  readonly ply: number;                // 0 for the initial position, 1 for after the first move, etc.
  readonly position: Position;         // the position AT this ply
  readonly move: Move | null;          // the move that produced this ply (null for ply 0)
  readonly isCheck: boolean;           // true if `position.turn` (whoever moves next) is currently in check
  readonly captured: Piece | null;     // the piece captured by `move`, if any (null for ply 0 or a non-capture)
}

// Pure: reconstructs every position from initialFen by applying moves in order.
// Throws if initialFen is malformed or any move in the sequence is illegal at
// the point it's applied (use isLegalMove from T1.3 to validate each step).
function replay(record: GameRecord): readonly ReplayStep[];

// The repetition key: board placement + side-to-move only (NOT halfmove/fullmove
// counters, which change every ply and would make repetition undetectable).
// Use this for ADR-017's "position key" concept. Exported as a standalone
// utility too, not just an internal helper.
function positionKey(position: Position): string;

interface RuleSet {
  readonly version: string;            // 'xq-casual-1.0.0'
  readonly noCaptureLimitPlies: number; // 120, per ADR-017
}

const CASUAL_RULESET: RuleSet; // { version: 'xq-casual-1.0.0', noCaptureLimitPlies: 120 }

// Returns null if the game recorded by `record` has not yet ended (no
// terminal condition applies given its current moves/terminalEvent).
// Otherwise returns the GameResult per ADR-017's adjudication order (see below).
function evaluateGame(record: GameRecord, ruleSet: RuleSet): GameResult | null;
```

## `evaluateGame` algorithm — implement this exact order (ADR-017)

Let `steps = replay(record)` and `final = steps[steps.length - 1]` (the last reached position; `final.position.turn` is whoever would move next).

1. **No legal moves for `final.position.turn`** (`getAllLegalMoves(final.position, final.position.turn).length === 0`): that side loses.
   - `reason = isInCheck(final.position, final.position.turn) ? 'CHECKMATE' : 'STALEMATE'`
   - `winner` = the OTHER color.
   - Return immediately — this takes priority over everything else, including any `terminalEvent` (a resignation recorded on an already-checkmated position should still be reported as the checkmate, not the resignation — checkmate is what actually happened).

2. **Repetition**: compute `positionKey` for every step in `steps`. If `positionKey(final.position)` is the SAME key as two earlier steps (i.e. this is the 3rd time this exact board+side-to-move has occurred across the whole game), let `i1` = the ply index of the 1st occurrence and `i3` = the ply index of this (3rd) occurrence. Consider the window of moves from ply `i1 + 1` through `i3` inclusive (i.e. `steps[i1+1..i3]`, using each step's `move`-that-produced-it and `isCheck`-after-it). Partition that window's moves by which color made each move (the mover of `steps[p]` is the color whose turn it was in `steps[p-1].position`, i.e. the OPPOSITE of `steps[p].position.turn`). For each color, check whether EVERY one of that color's moves in the window has `isCheck === true` (i.e. every move that color made in the window delivered check).
   - If exactly one color's moves were ALL checks in the window (and the other color's weren't all checks): that color loses. `reason = 'PERPETUAL_CHECK'`, `winner` = the other color.
   - Otherwise (both colors' moves were all checks, or neither was): `reason = 'REPETITION'`, `winner = null`.
   - Return immediately.
   - (If there's no 3rd-occurrence repetition, continue to step 3.)

3. **No-capture limit**: if `final.position.halfmoveClock >= ruleSet.noCaptureLimitPlies`: `reason = 'MOVE_LIMIT'`, `winner = null`. Return.

4. **Insufficient material**: if NEITHER side has any piece of type `CHARIOT`, `HORSE`, `CANNON`, or `SOLDIER` remaining on `final.position.board` (Advisors/Elephants/General alone can't force a result in this ruleset): `reason = 'INSUFFICIENT_MATERIAL'`, `winner = null`. Return.

5. **External terminal event** (`record.terminalEvent`), only reached if none of 1-4 applied:
   - `RESIGNATION`: `winner` = the color OTHER than `terminalEvent.loser`, `reason = 'RESIGNATION'`.
   - `DRAW_AGREEMENT`: `winner = null`, `reason = 'DRAW_AGREEMENT'`.
   - `TIMEOUT`: check whether the color OTHER than `terminalEvent.loser` has any `CHARIOT`/`HORSE`/`CANNON`/`SOLDIER` on the board (same material check as step 4, but for the potential WINNER's side specifically) — if that side has NO such attacking material, it can't realistically convert the win, so `winner = null`, `reason = 'TIMEOUT_INSUFFICIENT_MATERIAL'`; otherwise `winner` = that other color, `reason = 'TIMEOUT'`.
   - `ABANDONMENT`: same as RESIGNATION but `reason = 'ABANDONMENT'`.
   - `ABORTED`: `winner = null`, `reason = 'ABORTED'`.
   - Return the corresponding `GameResult`.

6. If none of the above applied and there's no `terminalEvent`: return `null` (the game is still in progress).

## Required tests

Title prefix `CORE-04` for result-classification tests, `CORE-05` for repetition/perpetual-check tests specifically. **One scenario per `ResultReason` value is the minimum bar** — construct a `GameRecord` (you can build these either as hand-written FEN + move sequences, or by constructing positions directly the way `legality.test.ts`/`moves.test.ts` do and wrapping them in a single-position `GameRecord` with `moves: []` for the board-derived cases that don't need move history, like CHECKMATE/STALEMATE/MOVE_LIMIT/INSUFFICIENT_MATERIAL) for each of:

- `CHECKMATE`, `STALEMATE` (zero legal moves, with/without check)
- `PERPETUAL_CHECK` (construct an actual repeating move sequence where one side checks every move across a 3rd-occurrence window — you'll need a real `moves: Move[]` sequence here, not just a static position, since this rule is about move history)
- `REPETITION` (a repeating sequence where neither side continuously checks, or both do)
- `MOVE_LIMIT` (a position with `halfmoveClock` already at/above 120 — you can construct this directly as a starting position with a high `initialFen` halfmove field, with `moves: []`)
- `INSUFFICIENT_MATERIAL` (a position with only Generals/Advisors/Elephants left)
- `RESIGNATION`, `DRAW_AGREEMENT`, `TIMEOUT`, `TIMEOUT_INSUFFICIENT_MATERIAL`, `ABANDONMENT`, `ABORTED` (any ordinary ongoing position + the matching `terminalEvent`)
- **Priority test**: a position that is simultaneously checkmate AND has a `terminalEvent` (e.g. a recorded resignation) attached — confirm `evaluateGame` returns the `CHECKMATE` result, not the resignation (step 1 takes priority over step 5).
- **In-progress test**: an ordinary non-terminal position with no `terminalEvent` — confirm `evaluateGame` returns `null`.
- `replay()`: confirm it reconstructs the correct sequence of positions/captures/check-flags for a short hand-verified move sequence (e.g. 4-6 plies from the start position, including at least one capture).
- `positionKey()`: confirm two positions with identical board+turn but different `halfmoveClock`/`fullmoveNumber` produce the SAME key (the key must ignore those fields), and two positions differing only in `turn` produce DIFFERENT keys.
