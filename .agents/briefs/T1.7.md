## Scenarios to add

### Repetition / perpetual-check (at least 5 new scenarios beyond T1.6's existing 2)

1. **Perpetual check by the OTHER color** (T1.6's existing test has Red delivering perpetual check — add the mirror case where Black delivers it, to make sure the adjudicator isn't accidentally color-asymmetric).
2. **Perpetual check broken by a capture**: a sequence that LOOKS like it's heading toward a repeating check pattern, but one move captures a piece partway through — assert this does NOT trigger `PERPETUAL_CHECK` (because the position's `halfmoveClock` resets and, more importantly, the captured piece changes the board so the position never actually repeats a 3rd time) — i.e., confirm `evaluateGame` returns `null` (ongoing) or some other reason entirely, not a repetition-based one.
3. **Mutual perpetual check** (both sides check on every one of their own moves throughout the window) — confirm this resolves as `REPETITION` (a draw), not `PERPETUAL_CHECK` for either side, per ADR-017 ("nếu... cả hai bên đều chiếu... ngược lại hòa").
4. **A 2nd occurrence is NOT enough** — construct a sequence where a position repeats exactly twice (not three times) and confirm `evaluateGame` does NOT return a repetition-based result (it should return `null` if nothing else applies, or whatever other reason is independently true).
5. **Repetition key ignores irrelevant history** — confirm that visiting a position, leaving it, and returning to a DIFFERENT position that merely happens to have the same piece layout but the OTHER side to move is treated as a distinct key (i.e., build a case where the board repeats 3 times from each side's perspective but interleaved — or more simply, just add a direct test: two otherwise-identical positions differing only in `turn` must never be confused by the repetition counter; you can test this via `positionKey` directly if that's clearer, or via a full `evaluateGame` scenario, your choice).

### No-capture limit (at least 2 new scenarios)

6. **Just under the limit**: `halfmoveClock = 119` (one less than `ruleSet.noCaptureLimitPlies`) does NOT trigger `MOVE_LIMIT` (assuming nothing else applies — construct the position so it's otherwise a normal ongoing game).
7. **A custom ruleSet with a different limit**: pass a `RuleSet` with `noCaptureLimitPlies: 10` and a position with `halfmoveClock: 10` — confirm `MOVE_LIMIT` triggers at the CONFIGURED threshold, not a hardcoded 120 (this guards against the implementation accidentally hardcoding 120 instead of reading `ruleSet.noCaptureLimitPlies`).

### Insufficient material (at least 3 new scenarios)

8. **Only Generals left on both sides** — the most extreme case.
9. **One side has attacking material, the other doesn't** — confirm the rule requires BOTH sides to lack attacking material (if even one side still has a Chariot/Horse/Cannon/Soldier, it's NOT an automatic draw by this rule — the game continues normally). This is an important boundary: re-read ADR-017's exact wording ("nếu cả hai bên đều không còn...") to confirm this reading, and construct the test accordingly.
10. **Advisors and Elephants don't count as attacking material** — a position with several Advisors/Elephants but zero Chariot/Horse/Cannon/Soldier on either side still triggers `INSUFFICIENT_MATERIAL` (this overlaps somewhat with scenario 8, but specifically exercises the "defensive pieces don't count" boundary with more pieces present, not just bare Generals).
