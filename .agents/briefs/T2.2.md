# Brief: T2.2 — `Board2D` SVG renderer

## Goal

Build the 2D SVG Xiangqi board component. It only ever talks to the `GameController` contract from T2.1 (via props) — it has no rules knowledge, no `@xq/xiangqi-core` logic beyond reading `Position`/`Square`/`Move`/`Color` types. Interaction (tap-to-tap AND drag-and-drop) must both work; the parent decides what's legal, this component just renders and reports gestures.

## Acceptance-criteria IDs

WEB-01

## Allowed paths

- `apps/web/src/features/game/board/**` (new)
- `apps/web/package.json` (add dependencies only if genuinely needed — report why)

## Forbidden

- Do not call any `@xq/xiangqi-core` rule functions (`getLegalMoves`, `applyMove`, `isLegalMove`, etc.) from inside this component — legality is the `GameController`'s job (T2.1), not the renderer's. Only import TYPES (`Position`, `Square`, `Move`, `Color`, `Piece`) from `@xq/xiangqi-core`, via `import type`.
- Do not touch `apps/web/src/features/game/controller/**` (T2.1, already built and tested).

## Props contract

```ts
export interface Board2DProps {
  readonly position: Position;
  readonly orientation: Color;          // which color's side renders at the bottom
  readonly selectedSquare: Square | null;
  readonly legalTargets: readonly Square[]; // destination squares to highlight (from GameControllerState)
  readonly lastMove: Move | null;
  readonly interactive: boolean;        // false for pure display (e.g. a finished/replayed game) — no pointer/keyboard handling when false
  readonly onSquareClick: (square: Square) => void;  // tap-to-tap: call on every square tap/click, let the parent's GameController decide what it means
  readonly onMove: (move: Move) => void;             // drag-and-drop: call ONLY when a drag ends on a square in `legalTargets`
}
```
This intentionally differs slightly from the `legalMoves: Move[]` sketch in `docs/spec/v1.0/03_Technical_Architecture.md` §5 — `legalTargets: Square[]` matches what `GameControllerState` (T2.1) actually exposes, so the page component (T2.4) can pass it straight through with no conversion.

## Board geometry (ADR-018 coordinates — get this exactly right, it's the part most likely to have a subtle bug)

- 9 files (`a`-`i`) × 10 ranks (`0`-`9`) = 90 intersection points; pieces sit ON the intersections/lines, not inside cells (traditional Xiangqi board, not a checkerboard).
- Red's rank 0 is Red's own back rank. When `orientation === 'red'`, rank 0 renders at the BOTTOM of the SVG (so Red's pieces are nearest the viewer) and rank 9 at the top. When `orientation === 'black'`, flip vertically: rank 9 at the bottom, rank 0 at top. Files always run left-to-right as `a`→`i` regardless of orientation (no horizontal flip — only ranks flip with orientation; confirm this matches how a real Xiangqi board looks when you walk around the table, and get it right, since players write it off as obviously broken if files mirror too).
- The river is the gap between rank 4 and rank 5 — render some visual distinction there (a wavy line, different fill band, or similar — your call on exact styling).
- The palace is files `d`-`f` (3 of the 9 files), ranks 0-2 for Red and ranks 7-9 for Black — render the diagonal "X" lines characteristic of a Xiangqi palace in both palace zones.
- Use a `viewBox` sized to the 9×10 grid plus a small margin for piece radius and any edge labels; let CSS size the actual rendered `<svg>` to its container (`width="100%" height="100%"` or similar) so the page layout (T2.4) controls final size — don't hardcode pixel dimensions.

## Pieces

Traditional Xiangqi characters (not Western chess glyphs): Red — 帥(General) 仕(Advisor) 相(Elephant) 馬(Horse) 車(Chariot) 炮(Cannon) 兵(Soldier); Black — 將(General) 士(Advisor) 象(Elephant) 馬(Horse) 車(Chariot) 砲(Cannon) 卒(Soldier). Render each piece as a circle (traditional disc) with its character centered, Red pieces visually distinct from Black (e.g. red vs. black/dark text and/or a border color) — don't rely on color alone per the UX accessibility checklist in `docs/spec/v1.0/02_UX_Flows_Sitemap.md` §5 ("không chỉ dựa vào màu nền"), so also vary something structural (e.g. disc border style/thickness, or a small color-blind-safe accent) between the two sides.

## Visual state

- **Selected square**: a visible highlight ring/background on `selectedSquare`.
- **Legal targets**: a small dot on empty squares in `legalTargets`; a ring/outline around the piece on OCCUPIED squares in `legalTargets` (i.e. a capture target looks different from a quiet-move target).
- **Last move**: a subtle highlight on both `lastMove.from` and `lastMove.to`.
- **Check indicator**: NOT required in this task (no check-state prop exists yet) — skip it, don't invent a prop for it.

## Interaction — BOTH of these must work, and must not conflict with each other

1. **Tap-to-tap** (works via mouse click or touch tap, no drag needed): every square gets a tap/click handler that calls `onSquareClick(square)`. Use Pointer Events (`onPointerDown`/`onPointerUp`, not legacy mouse/touch-specific handlers) so this one code path covers mouse, touch, and pen uniformly.
2. **Drag-and-drop** (optional enhancement per the architecture doc, but required by this brief as a real interaction, not just tap): `onPointerDown` on a square with a piece belonging to... actually you don't know whose turn it is at this layer — just start a drag whenever pointerdown occurs on any occupied square, track pointer position via `onPointerMove` (visually move/follow the piece, e.g. via a transform on a dragged copy, or by repositioning the piece element — your call), and on `onPointerUp`: if the release point is over a square in `legalTargets`, call `onMove({ from: <drag-start square>, to: <release square> })`; otherwise snap back (no move, no `onSquareClick` call either — a drag that doesn't land on a legal target is just cancelled, not reinterpreted as a tap).
3. **Distinguishing a tap from a drag**: a pointerdown+pointerup with negligible movement (e.g. <5px) and no square-to-square transition should be treated as a TAP (call `onSquareClick`), not a (trivial, zero-distance) drag. A pointerdown+move+up across squares is a DRAG (call `onMove` if valid, nothing otherwise). Implement this distinction explicitly — don't call both `onSquareClick` AND `onMove` for the same gesture.
4. When `interactive` is `false`: no pointer handlers fire at all (board is for display only — e.g. a finished game's final position, or someone else's puzzle solution), but it still renders the position/last-move/etc. correctly.

## Keyboard accessibility

- The board should be reachable and operable via keyboard: a focused "cursor" square (component-local state, independent of `selectedSquare`), moved with arrow keys (wrapping or clamping at board edges — your call, clamping is simpler and fine), with `Enter`/`Space` triggering the equivalent of tapping the focused square (calling `onSquareClick` on it).
- Each square element should have `data-square="<square>"` (for testability — T2.5's E2E tests will click by this attribute) and a meaningful `aria-label` describing its content (e.g. "e4, empty" or "e0, Red General").
- Use a sensible ARIA structure (e.g. `role="grid"`/`role="row"`/`role="gridcell"`, or a simpler scheme if that fits better with an SVG-based layout — your call, just make it genuinely operable by a screen reader/keyboard user, not just technically labeled).

## Required tests

Use `@testing-library/react` (already a dependency) with `jsdom`. Since full drag gesture simulation is awkward in `jsdom`, focus tests on:
- Renders all 32 pieces at the correct squares for the starting position (query by `data-square`, check the rendered character/aria-label).
- `orientation='red'` vs `orientation='black'` actually changes which rank renders at the top/bottom (assert on relative DOM/visual ordering or computed position, not just that the prop was received — verify the actual geometry flipped).
- Clicking (via `fireEvent.pointerDown` + `fireEvent.pointerUp` on the SAME square with no movement) a square calls `onSquareClick` with that square.
- `legalTargets` squares render the dot/ring indicator; squares not in `legalTargets` don't.
- `selectedSquare` renders its highlight.
- `interactive={false}` means pointer events on a square do NOT call `onSquareClick`.
- Keyboard: focusing the board and pressing an arrow key then Enter calls `onSquareClick` for the resulting focused square.
