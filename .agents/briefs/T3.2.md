## Required schema (implement this directly — it's been fully designed; adapt field TYPES/NAMES only if Prisma syntax requires it, but keep the entities, relations, and unique constraints exactly as specified)

```prisma
enum UserType { GUEST REGISTERED }
enum Color { RED BLACK }
enum RoomStatus { WAITING READY STARTED CLOSED }
enum GameMode { LOCAL AI ONLINE }
enum GameStatus { WAITING ACTIVE FINISHED ABORTED }

model User {
  id              String        @id @default(cuid())
  nickname        String
  type            UserType
  createdAt       DateTime      @default(now())
  guestSession    GuestSession?
  hostedRooms     Room[]        @relation("RoomHost")
  roomMemberships RoomMember[]
  redGames        Game[]        @relation("RedPlayer")
  blackGames      Game[]        @relation("BlackPlayer")
  gameMoves       GameMove[]
}

model GuestSession {
  id        String   @id @default(cuid())
  userId    String   @unique
  user      User     @relation(fields: [userId], references: [id])
  tokenHash String   @unique   // SHA-256 hex of the opaque session token (ADR-020) — never store the raw token
  createdAt DateTime @default(now())
  expiresAt DateTime            // 30-day sliding expiry, extended by the session module (T3.3), not here
}

model Room {
  id          String       @id @default(cuid())
  code        String       @unique   // human-shareable join code
  hostId      String
  host        User         @relation("RoomHost", fields: [hostId], references: [id])
  status      RoomStatus   @default(WAITING)
  initialMs   Int
  incrementMs Int
  gameId      String?      @unique
  game        Game?        @relation(fields: [gameId], references: [id])
  expiresAt   DateTime?
  createdAt   DateTime     @default(now())
  members     RoomMember[]
}

model RoomMember {
  id       String   @id @default(cuid())
  roomId   String
  room     Room     @relation(fields: [roomId], references: [id])
  userId   String
  user     User     @relation(fields: [userId], references: [id])
  color    Color?
  isHost   Boolean  @default(false)
  joinedAt DateTime @default(now())

  @@unique([roomId, userId])
}

model Game {
  id               String      @id @default(cuid())
  mode             GameMode
  redId            String?
  red              User?       @relation("RedPlayer", fields: [redId], references: [id])
  blackId          String?
  black            User?       @relation("BlackPlayer", fields: [blackId], references: [id])
  initialFen       String
  ruleSetVersion   String
  status           GameStatus  @default(WAITING)
  gameVersion      Int         @default(0)
  initialMs        Int?
  incrementMs      Int?
  redRemainingMs   Int?
  blackRemainingMs Int?
  activeColor      Color?
  turnStartedAt    DateTime?
  resultWinner     Color?
  resultReason     String?     // ResultReason from @xq/xiangqi-core, stored as a plain string (Prisma has no cross-package enum import)
  finishedAt       DateTime?
  drawOfferBy      Color?
  drawOfferPly     Int?
  createdAt        DateTime    @default(now())
  moves            GameMove[]
  snapshots        GameSnapshot[]
  room             Room?
}

model GameMove {
  id           String   @id @default(cuid())
  gameId       String
  game         Game     @relation(fields: [gameId], references: [id])
  ply          Int
  uci          String   // 4-char UCI move string, ADR-018
  moveId       String   @unique   // client-supplied idempotency key (SYNC-02)
  playerId     String?
  player       User?    @relation(fields: [playerId], references: [id])
  clockAfterMs Int?
  acceptedAt   DateTime @default(now())

  @@unique([gameId, ply])
}

model GameSnapshot {
  id         String   @id @default(cuid())
  gameId     String
  game       Game     @relation(fields: [gameId], references: [id])
  ply        Int
  fen        String
  clocksJson Json?
  version    Int
  createdAt  DateTime @default(now())

  @@unique([gameId, ply])
}
```

The `@@unique([gameId, ply])` on `GameMove` and the `@unique` on `moveId` are the database-level backing for SYNC-01 (concurrent-move race) and SYNC-02 (duplicate-move idempotency) — a later task (T3.5) relies on these constraints actually existing and being enforced by Postgres, not just application logic, so get them right.

## Test-DB harness

Set up something that, once per test run (not once per file), does the equivalent of `prisma migrate reset --force --skip-seed` against a `xq_test` database (NOT `xq_dev`), before any integration test that touches the DB runs. Concretely:
- Add a `DATABASE_URL_TEST` to `.env.example`: `postgresql://xq:xq_dev_password@localhost:5432/xq_test`.
- A Vitest `globalSetup` (referenced from `apps/api/vitest.config.ts`) that runs the reset programmatically (e.g. shelling out to the `prisma` CLI with `DATABASE_URL` temporarily overridden to the test DB, or using `execSync('npx prisma migrate reset --force --skip-generate --schema=./prisma/schema.prisma', { env: { ...process.env, DATABASE_URL: process.env.DATABASE_URL_TEST } })` — your call on the exact mechanism, but it must target `xq_test`, never `xq_dev`).
- A small helper (e.g. `apps/api/test/setup/test-db.ts`) exporting a `PrismaClient` instance constructed with the TEST database URL, for integration tests (T3.5+) to import and use directly.
- Add `package.json` scripts: `"db:generate": "prisma generate"`, `"db:migrate": "prisma migrate dev"`, `"db:reset:test": "<your reset command targeting xq_test>"`.

You likely won't be able to actually RUN any of this against a live Postgres in your own sandbox (no network, and Postgres may not be reachable from inside your sandboxed shell even if it's running on the host) — that's expected. Write it correctly per the spec above, and the orchestrator will run `prisma migrate dev` (to generate the actual migration SQL) and the reset harness afterward, reporting back if anything doesn't work as designed.
