# Brief: T3.3 — Guest session module (ADR-020)

## Goal

Build the guest identity system: create a session, read/update the current user, and a reusable guard/resolver other modules (rooms T3.6, the Socket.IO gateway T4.2) will depend on to know who's making a request. **This is the main defense against room hijack / move impersonation in the whole system** — treat it with the scrutiny that implies, even though individual pieces look like simple CRUD.

## Acceptance-criteria IDs

ROOM-02

- `apps/api/src/modules/sessions/**` (new)
- `apps/api/src/main.ts` (add `cookie-parser` middleware only — don't touch the helmet/CORS/filter wiring T3.8 already did)
- `apps/api/package.json` (add `cookie-parser`, `@types/cookie-parser`, `@nestjs/throttler`)

## Forbidden

- Do not build rooms or the Socket.IO gateway (T3.6/T4.2) — just expose what they'll need (see "for later tasks" below).
- Do not change `packages/shared-contracts` — `userSummarySchema`/the `/sessions/guest`, `/me` REST shapes already exist there (T3.1); reuse them.

## What to build

### Token mechanics (exactly per ADR-020)

- Generate a 32-byte cryptographically random token (`crypto.randomBytes(32)`, base64url-encoded for the cookie value).
- Store ONLY `sha256(rawToken)` hex digest in the DB (`GuestSession.tokenHash`) — never the raw token.
- Cookie name `xq_sid`: `httpOnly: true`, `secure: <true in production, false in dev — read from NODE_ENV>`, `sameSite: 'lax'`, `maxAge` = 30 days in ms, `path: '/'`.
- 30-day SLIDING expiry: every successful authenticated request extends `GuestSession.expiresAt` to `now + 30 days` (don't wait for near-expiry — sliding on every use is simpler and matches the ADR's intent; update it in the guard itself, fire-and-forget is NOT acceptable here since a subsequent request in the same test needs to see the extension — await it, but it doesn't need to block the response if you're careful about ordering... simplest: just `await` it before calling `next()`/returning from the guard).

### Endpoints (NestJS controller `SessionsController`, request/response bodies from `packages/shared-contracts`)

- `POST /sessions/guest` — body `{ nickname }` (validate with T3.8's `ZodValidationPipe` against `packages/shared-contracts`'s schema). Creates a `User` (`type: GUEST`), a `GuestSession` row, sets the `xq_sid` cookie, returns `UserSummary`. **Throttle this endpoint** (via `@nestjs/throttler`'s `@Throttle()`) to something like 10 requests/minute per IP — this is the one unauthenticated, state-creating endpoint in the system, don't leave it open to trivial abuse.
- `GET /me` — protected by `SessionGuard` (below). Returns the current `UserSummary`.
- `PATCH /me` — protected. Body `{ nickname }`. Updates and returns `UserSummary`.

### `SessionGuard` + `@CurrentUser()` decorator

A NestJS `CanActivate` guard that: reads `req.cookies.xq_sid` (requires `cookie-parser` middleware, wire it into `main.ts`); if absent, throws `UnauthorizedException`. Hashes it, looks up `GuestSession` by `tokenHash` (include the related `User`); if not found OR `expiresAt < now`, throws `UnauthorizedException`. Otherwise: extends `expiresAt` (sliding window, see above), attaches the user to the request (e.g. `req.user = { id, nickname, type }`), returns `true`. A `@CurrentUser()` param decorator that pulls `req.user` back out for controller methods to use type-safely.

### For later tasks: a reusable resolver, not just the HTTP guard

Export a standalone function (not tied to the NestJS request/response cycle) that T4.2's Socket.IO gateway will need for handshake auth:
```ts
export async function resolveSessionFromCookieHeader(cookieHeader: string | undefined, prisma: PrismaService): Promise<UserSummary | null>;
```
Parses the raw `Cookie:` header text (Socket.IO handshakes give you the raw header, not pre-parsed `req.cookies`) to find `xq_sid`, then does the same hash-lookup-check-expiry logic as `SessionGuard` (factor the shared lookup logic into one internal helper both the guard and this function call, don't duplicate the hashing/expiry logic twice). Returns `null` (not a thrown error) for a missing/invalid/expired cookie — the caller (a future Socket.IO gateway) decides what to do with "unauthenticated," this function just answers the question.

## Required tests

- `POST /sessions/guest`: creates a user, sets a cookie, response matches `UserSummary` shape. Verify the DB only stores the HASH, not the raw token (fetch the `GuestSession` row directly and confirm `tokenHash !== <the raw cookie value>`).
- `GET /me` with no cookie → 401 (through the full exception-filter envelope from T3.8, not a raw Nest error).
- `GET /me` with a forged/random cookie value → 401.
- `GET /me` with an EXPIRED session's cookie (manually set `expiresAt` in the past in a test fixture) → 401.
- `GET /me` with a valid cookie → 200, correct user, and confirm `expiresAt` in the DB was extended (sliding window) compared to before the request.
- `PATCH /me` updates the nickname and the change is reflected in a subsequent `GET /me`.
- `resolveSessionFromCookieHeader`: parses a raw multi-cookie header string correctly (e.g. `"other=1; xq_sid=<token>; another=2"`), returns `null` for a missing/invalid/expired token, returns the right `UserSummary` for a valid one.
- Throttle: this one's awkward to test precisely without real timing — a lightweight test that fires requests past the configured limit and confirms a 429 at some point is enough; don't over-engineer a flaky timing-sensitive test here.

These need the real `xq_test` Postgres (same pattern as T3.2/T3.5's tests) — try running them yourself; if your sandbox can't reach `localhost:5432`, note that in KNOWN GAPS and the orchestrator will verify.
