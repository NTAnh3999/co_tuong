# Brief: T3.5 — `GamesService`: transactional, idempotent move persistence

## Goal

Wrap T3.4's pure `submitMove`/`createGameAggregate` logic in a real, transactional, DB-backed NestJS service. This is where SYNC-01 (two concurrent move submissions must never both be accepted) and SYNC-02 (resubmitting the same `moveId` must never write a duplicate row) actually get their teeth — T3.4 proved the pure decision logic is correct for a single call; this task proves the PERSISTENCE layer can't be raced or double-written even under concurrency.

## Design

### Reconstructing in-memory state from the DB

For a given `gameId`, load the `Game` row and ALL its `GameMove` rows (ordered by `ply`), decode each `uci` string back to a `Move` via `decodeMove` (`@xq/xiangqi-core`), and replay from `game.initialFen` through all moves using `@xq/xiangqi-core`'s pure functions to reconstruct the current `Position`. Build a `GameAggregateState` (T3.4's shape) from this: `status`, `initialFen`, the reconstructed `position`, `moves`, `moveIds` (from each `GameMove.moveId`), `gameVersion` (`Game.gameVersion`), `timeControl`/`clock` (built from the `Game` row's clock columns, or `null` if `Game.initialMs` is null). Full replay-from-start is intentionally simple and correct for MVP game lengths (a few hundred plies at most) — don't try to optimize via `GameSnapshot` reads for this task; `GameSnapshot` writes (below) exist for recovery/DATA-01, not as the primary read path.

### `submitMove(gameId: string, command: SubmitMoveCommand): Promise<SubmitMoveOutcome>`

1. Open a Prisma **interactive transaction** (`prisma.$transaction(async (tx) => { ... })`).
2. Inside the transaction, load the `Game` row with a row-level lock that serializes concurrent calls for the SAME `gameId` — Prisma doesn't have first-class `SELECT ... FOR UPDATE` syntax, so use `tx.$queryRaw` with a raw `SELECT ... FROM "Game" WHERE id = $1 FOR UPDATE` (or the Prisma-recommended equivalent for your Prisma version — check with the context7 MCP if unsure) to acquire the lock before reading the rest of the state. This is the mechanism that makes SYNC-01 actually hold under real concurrency, not just in a single-threaded test.
3. Reconstruct `GameAggregateState` as described above (within the same transaction, so it sees the locked, up-to-date row).
4. Call T3.4's pure `submitMove(state, command, Date.now())` — this is the ONE place in this service where `Date.now()` is appropriate, since this service IS the I/O boundary (T3.4's purity rule is about the domain logic itself, not about every caller everywhere).
5. On `'duplicate'`: commit the transaction with no writes (or just return early — a read-only transaction is fine), return the outcome.
6. On `'rejected'`: same — no writes, return the outcome with its `reason`.
7. On `'accepted'`: within the SAME transaction, insert a new `GameMove` row (`gameId`, `ply` = `moves.length - 1` of the NEW state, `uci` = `encodeMove(command.move)`, `moveId` = `command.moveId`, `playerId` if resolvable, `clockAfterMs` from the new clock state for the mover's color), update the `Game` row (`gameVersion`, clock columns, `status`, `resultWinner`/`resultReason`/`finishedAt` if the new state's `result` is non-null). Every 10 plies (or on the game finishing), ALSO write a `GameSnapshot` row (`ply`, `fen` via `toFen`, `clocksJson`, `version`) — this is DATA-01's recovery mechanism. Commit, return the outcome.
8. Rely on the DB's own `@@unique([gameId, ply])` and `@unique` on `moveId` (from T3.2's schema) as a LAST-RESORT guard: if two transactions somehow both pass the application-level version check (shouldn't happen given the row lock, but the unique constraints are cheap insurance) and both try to insert, the second insert will throw a Prisma unique-constraint error — catch that specific error and translate it to a `{ type: 'rejected', reason: 'VERSION_CONFLICT' }` outcome rather than letting a raw DB error escape.

### Other methods needed for later tasks to build on (keep minimal — just enough surface, no extra features)

- `createGame(initialFen: string, timeControl: TimeControl | null, redId: string | null, blackId: string | null): Promise<{ gameId: string }>` — creates a `Game` row via T3.4's `createGameAggregate` shape, status `'WAITING'`. (Seat-filling/activation is T3.6's job — this method just creates the row; T3.6 will call something to transition it to `'ACTIVE'`, which can be as simple as a direct Prisma update you expose, e.g. `activateGame(gameId, now)`, your call on the exact shape.)
- `getSnapshot(gameId: string): Promise<GameSnapshot>` — the `packages/shared-contracts` `GameSnapshot` shape (T3.1), built from the reconstructed state (for use by a future REST `GET /games/:id`, T3.7).

## Required tests — these need a REAL Postgres connection (the `xq_test` database T3.2 wired up)

Try running these in your own sandbox first — you may or may not have access to `localhost:5432` depending on your sandbox's network policy. If connection attempts fail, that's expected and fine: write the tests correctly per the spec below, note in KNOWN GAPS that you couldn't execute them yourself, and the orchestrator will run them against the real test DB afterward.

- **SYNC-01 (the main event)**: create a game, then fire 20 CONCURRENT `submitMove` calls (`Promise.all`) all claiming the SAME `expectedVersion` and the SAME legal move (or 20 different legal moves from the same position, your call — same expectedVersion is what matters) but DIFFERENT `moveId`s. Assert EXACTLY ONE resolves to `'accepted'` and the other 19 resolve to `'rejected'` with `reason: 'VERSION_CONFLICT'`. Then assert the DB has exactly ONE new `GameMove` row for that game.
- **SYNC-02**: submit a move, then submit the EXACT SAME `{moveId, expectedVersion, move, color}` again — second call returns `'duplicate'`; assert the DB still has exactly one `GameMove` row for that `moveId`/ply (no duplicate insert).
- **DATA-01**: after several moves (including at least one snapshot boundary if you make the snapshot interval small enough to test, or just directly assert a snapshot row's `fen` matches `toFen` of the position at that ply), construct a FRESH instance of the state-reconstruction logic (simulating "the process restarted") and confirm it reproduces the exact same `position`/`gameVersion`/`moves` as what's in memory.
- A full game reaching checkmate correctly updates the `Game` row's result columns and `status: 'FINISHED'`.

Use `apps/api/test/setup/test-db.ts` (T3.2) for the test database client, and make sure your test file's setup creates whatever `User`/`Game` fixture rows it needs via plain Prisma calls (no need for the full session/room machinery from later tasks — just insert minimal valid rows).
