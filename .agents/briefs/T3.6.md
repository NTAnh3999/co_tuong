# Brief: T3.6 — Rooms module: create, join, seat assignment

## Goal

The private-room flow: a host creates a room with a time control and color preference, gets a shareable code, a second guest joins by that code, and once both seats are filled the actual `Game` (via T3.5's `GamesService`) is created and activated. This is the last piece before M4's Socket.IO layer can make any of this live.

## Acceptance-criteria IDs

ROOM-01, ROOM-02

## Allowed paths

- `apps/api/src/modules/rooms/**` (new)

## Forbidden

- Do not build the Socket.IO gateway (T4.2) — rooms are REST-only in this task; realtime room-state push is M4.
- Do not modify `apps/api/src/modules/games/**` (T3.4/T3.5) or `apps/api/src/modules/sessions/**` (T3.3) — only call their already-exported services/guards.

## Design

### Room codes

8 characters, uppercase, drawn from a set that excludes visually-confusable characters (no `0`/`O`, no `1`/`I`/`L`) — e.g. `23456789ABCDEFGHJKMNPQRSTUVWXYZ`. Generate with `crypto.randomInt`/`crypto.randomBytes`, retry on a unique-constraint collision (the `Room.code` column is already `@unique` from T3.2) rather than pre-checking existence (simpler, race-free).

### `POST /rooms`

Body: `{ timeControl: TimeControl, hostColor: 'red' | 'black' | 'random' }` (schema already in `packages/shared-contracts`). Protected by `SessionGuard` (T3.3) — the caller becomes the host. Resolve `'random'` to an actual color HERE, at creation time (a coin flip, `crypto.randomInt(2)`), so the host's color is fixed and known from the moment the room exists — don't defer the random choice to join time. Create a `Room` row (`status: WAITING`, `initialMs`/`incrementMs` from `timeControl`) and a `RoomMember` row for the host (`isHost: true`, the resolved `color`). Return the `RoomSnapshot` shape (T3.1).

### `POST /rooms/:code/join`

Protected by `SessionGuard`. Body: `{ nickname?: string }` (if provided, update the CURRENT user's nickname — reuse `SessionsService` from T3.3 rather than writing a second nickname-update code path; if not already imported, add `SessionsService` as a constructor dependency). Look up the `Room` by `code`:
- Not found → 404 (`ROOM_NOT_FOUND` style error code through T3.8's envelope).
- `status !== 'WAITING'` or already has 2 members → 409-style `ROOM_FULL` (don't let a 3rd person "join" a full room, and don't let someone re-join a room that's already started — see idempotency note below).
- The joiner IS already the host (same `userId` already a member) → just return the current snapshot, don't create a duplicate `RoomMember` (idempotent re-fetch, e.g. the host reloading their own room page).
- Otherwise: create a `RoomMember` for the joiner with the color NOT taken by the host, `isHost: false`. Now both seats are filled — call `GamesService.createGame(standardStartingFen, timeControl, <redId>, <blackId>)` (figure out which member is red/black from their `color`), then `GamesService.activateGame(gameId)`, then update the `Room` row: `gameId`, `status: 'STARTED'`.
Return the updated `RoomSnapshot`.
**Rate-limit this endpoint** (per IP, via `@nestjs/throttler` — same pattern T3.3 used for guest creation) — room codes are short enough that unrestricted guessing is a real concern (ROOM-02).

### `GET /rooms/:code`

Protected by `SessionGuard`. 404 if not found. Returns `RoomSnapshot`. Any authenticated user can READ a room's snapshot by its code (needed for the room's own members to poll/refresh) — this is fine since the code itself is the secret; don't add extra membership-checking here (that's enforced on the actions that matter — joining and, later in M4, moving).

## Required tests

Use the real `xq_test` Postgres (same pattern as T3.3/T3.5's tests) — create guest sessions via `SessionsService` directly or through the actual HTTP flow (your call on what's cleaner) to get valid authenticated requests for the e2e-style tests.

- `POST /rooms` creates a room, returns a well-formed 8-char code, the host is seated with the resolved color (test `'red'`, `'black'`, and `'random'` — for `'random'`, just assert it resolved to ONE of the two colors, not which one).
- `POST /rooms/:code/join` by a second user fills the second seat, creates and activates a `Game`, room status becomes `STARTED`.
- Joining a non-existent code → 404 through the standard error envelope.
- Joining an already-full room (a third user) → the `ROOM_FULL`-style rejection, not accepted.
- The host re-calling join on their own room returns the existing snapshot without creating a second `RoomMember` row (assert the member count stays 1 until the real second player joins).
- `GET /rooms/:code` returns the current snapshot for an authenticated user who isn't necessarily a member.
- Rate limit: fire enough join attempts to trip the configured limit at some point, assert a 429 eventually appears (same light-touch approach T3.3 used, don't chase exact timing).
