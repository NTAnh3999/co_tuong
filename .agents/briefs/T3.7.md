# Brief: T3.7 — Games REST controller

## Goal

The read/action REST surface for an existing game: fetch its snapshot, paginated move history, resign, and draw-offer actions. This is a thin controller over T3.5's `GamesService` — almost no new logic, mostly authorization (only the two actual players may resign/offer-draw for a game) and wiring to the existing REST shapes from `packages/shared-contracts`.

## Endpoints (protected by `SessionGuard` from T3.3, using `@CurrentUser()`)

- `GET /games/:id` — returns `GameSnapshot` via `GamesService.getSnapshot`. 404 if the game doesn't exist. No membership check needed to READ (same reasoning as T3.6's room read).
- `GET /games/:id/moves` — query `{ cursor?: string, limit?: number }` per the `packages/shared-contracts` shape. For MVP, "cursor" can simply be a ply number as a string (paginate by ply, `limit` defaulting to something reasonable like 50, capped at e.g. 200) — fetch moves after that ply, ordered, return `{ moves: [...], nextCursor }`. Reuse `GamesService`'s DB access pattern (add a method there if one doesn't exist — see Forbidden above about keeping additions narrow) rather than querying Prisma directly from the controller.
- `POST /games/:id/resign` — the caller must be ONE OF the game's two players (`redId`/`blackId` on the `Game` row) — 403 if not. Add a `GamesService.resign(gameId, color)` method (if not present) that constructs the `{ type: 'RESIGNATION', loser: color }` terminal event path: it should follow the SAME transactional pattern as `submitMove` (row lock, reconstruct state, call `@xq/xiangqi-core`'s `evaluateGame` with that `terminalEvent` added to the reconstructed `GameRecord`, persist the result/status). Determine `color` from which of `redId`/`blackId` matches the caller — don't trust a client-supplied color field. Returns the updated `GameSnapshot`.
- `POST /games/:id/draw-offer` — body `{ action: 'offer' | 'accept' | 'decline' }`. Per ADR-022: `'offer'` records `drawOfferBy`/`drawOfferPly` on the `Game` row (only if the caller is a current player and no offer is already pending — reject a second simultaneous offer); `'accept'` (only by the OTHER player than `drawOfferBy`) finalizes the game via the same transactional pattern as resign, with `{ type: 'DRAW_AGREEMENT' }`; `'decline'` just clears `drawOfferBy`/`drawOfferPly`. Add whatever minimal `GamesService` methods this needs, following `submitMove`'s transactional pattern for the state-changing ones.
- `GET /me/games` — the current user's games (where they're `redId` or `blackId`), most recent first, a simple list of lightweight summaries (gameId, opponent info if easily available, status, result) — paginate simply if you like, exact shape is your call since it's not yet defined in `shared-contracts` (add a schema there IF you think it's warranted, but keep it minimal — a simple `{ games: [...] }` array is fine without over-engineering cursor pagination for this one).

## Required tests

Real `xq_test` Postgres, same pattern as T3.3/T3.5/T3.6.

- `GET /games/:id`: correct snapshot for an existing game, 404 for a missing one.
- `GET /games/:id/moves`: pagination actually works (create a game with several moves via `GamesService.submitMove` directly in the test setup, then fetch with a small `limit` and confirm `nextCursor` lets you page through all of them).
- `POST /games/:id/resign`: the non-player (a third user) gets 403; a real player resigning ends the game with the correct winner/reason, and the OTHER player submitting a move afterward is rejected (`GAME_NOT_ACTIVE`).
- `POST /games/:id/draw-offer`: offer → accept ends the game as a draw; offer → decline leaves it ongoing and clears the offer so a new one can be made; a second simultaneous offer (before the first is resolved) is rejected.
- `GET /me/games`: returns games the caller is actually part of, not someone else's.
