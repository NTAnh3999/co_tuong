# Brief: T3.8 — Error envelope, validation pipe, request logging, security headers

## Goal

Set the cross-cutting HTTP module pattern every later controller (T3.3, T3.6, T3.7) will rely on: a consistent JSON error shape for every failure, Zod-based request validation, structured request logging with correlation IDs, and basic security headers. This task establishes the pattern; it doesn't add any game/room/session business logic.

OPS-01 (partial — logging/health piece; the rest of OPS-01 lands in M7)

## What to build

### 1. Error envelope + global exception filter

Use the `ApiError`/error-envelope shape from `packages/shared-contracts` (T3.1 — check `src/errors.ts` for what's already defined there; reuse it rather than redefining). A global NestJS exception filter (`@Catch()`) that:
- Catches `HttpException` (and subclasses) and any unhandled error.
- Maps to `{ error: { code: string, message: string, details?: unknown } }` — for `HttpException`, derive `code` from the HTTP status (e.g. a short upper-snake name like `BAD_REQUEST`, `NOT_FOUND`, `UNAUTHORIZED`) and `message` from the exception; for an unhandled/unknown error, respond with a generic 500 `{ code: 'INTERNAL_ERROR', message: 'Internal server error' }` and log the real error server-side (never leak internals to the client).
- Every response should also get the request's correlation ID attached somewhere reasonable (e.g. a `x-request-id` response header) — see logging below for where that ID comes from.

### 2. Zod validation pipe

A global `ZodValidationPipe` (or scoped, applied per-route via a decorator — your call) that takes a Zod schema and validates `@Body()`/`@Query()`/`@Param()` against it, throwing a `BadRequestException` with the Zod error's issues as `details` on failure (caught by the filter above, which will format it through the standard envelope). Later controllers (T3.3+) will use this with the request schemas already defined in `packages/shared-contracts`.

### 3. Request ID + structured logging

Every request gets a correlation ID (reuse an inbound `x-request-id` header if the client sent one — useful for the web app forwarding its own trace — otherwise generate one, e.g. `crypto.randomUUID()`). Log at least: method, path, status code, duration, and the request ID, for every request. Pick ONE of: (a) `nestjs-pino` (idiomatic Nest integration, auto request logging), or (b) a small hand-rolled middleware using `pino` directly, or (c) Nest's built-in `Logger` if you want to avoid a new dependency entirely — your call based on what's simplest to wire correctly; note your choice and why in your final message. Whatever you choose, the request ID must also be usable later for tagging `gameId`/`moveId` in game-related logs (T4.x) — don't paint yourself into a corner where request-scoped context isn't accessible from deeper in the call stack (Nest's `AsyncLocalStorage`-based request context, or a request-scoped provider, are both reasonable approaches — a global mutable variable is NOT, since requests are concurrent).

### 4. `helmet` + CORS

Wire `helmet` as Express middleware in `main.ts`. Configure CORS to allow the web app's origin (read from an env var, e.g. `WEB_ORIGIN`, defaulting to `http://localhost:3000` for dev — add it to `apps/api/src/config/env.schema.ts` from T0.3 and to `.env.example`) with `credentials: true` (needed later for the guest-session cookie, T3.3).

### 5. `/health` DB ping

Extend the existing `HealthController` (don't remove its current `coreStartingFen` field) to also attempt a trivial DB query via the injected `PrismaService` (e.g. `SELECT 1` or `prisma.$queryRaw` equivalent) and include a `db: 'ok' | 'error'` field in the response — if the query throws, catch it, report `db: 'error'`, and still return 200 (a DB blip shouldn't make the whole health check unreachable for infra tooling that just wants to know the process is alive; a monitoring system can distinguish `db: 'error'` from a hard failure). Update the existing e2e test for this new field.

## Required tests

- Exception filter: a thrown `HttpException` produces the exact envelope shape; an unhandled generic `Error` produces the generic 500 envelope without leaking its message.
- Validation pipe: a request failing a Zod schema produces a 400 with `details` containing the Zod issues; a valid request passes through unchanged.
- `/health` e2e: still returns `coreStartingFen`, now also returns `db: 'ok'` against the real test DB (reuse the existing e2e test file/pattern, extend rather than replace).
