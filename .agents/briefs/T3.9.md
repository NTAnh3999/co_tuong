# Brief: T3.9 — `api-client`: typed fetch layer

## Goal

Build `packages/api-client`'s real content: one typed function per REST endpoint defined in `packages/shared-contracts` (T3.1), so `apps/web` never hand-writes a raw `fetch` call or duplicates a response shape. The Socket.IO client wrapper (`createGameSocket`) is a SEPARATE task (T4.1) — this one is REST only.

## Acceptance-criteria IDs

None directly (infra enabler).

## Allowed paths

- `packages/api-client/src/**` (replace the T0.2 placeholder)
- `packages/api-client/package.json` (add `@xq/shared-contracts` as a workspace dependency if not already present)

## Forbidden

- Do not build the Socket.IO client (T4.1).
- Do not call this from any `apps/web` page yet — that wiring happens in M4/M6 pages as they're built. This task only builds the client library itself, with its own tests.

## Design

A small `ApiClient` with one method per endpoint from `packages/shared-contracts/src/rest.ts` (the table T3.1 built): `createGuestSession`, `getMe`, `updateMe`, `createRoom`, `joinRoom`, `getRoom`, `getGame`, `getGameMoves`, `resignGame`, `offerDraw` (naming is your call, keep it consistent and obvious). Each function:

1. Takes a typed request payload (validated against the matching Zod request schema from `shared-contracts` BEFORE sending — fail fast on a malformed call site rather than sending bad data).
2. Calls `fetch(url, { method, credentials: 'include', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify(payload) })` — `credentials: 'include'` is required so the `xq_sid` guest-session cookie (T3.3) actually gets sent cross-origin in dev (web on :3000, api on :3001).
3. On a non-2xx response, parse the body as the `ApiError` envelope shape (T3.8/T3.1) and throw a typed `ApiClientError` (a small class wrapping `code`/`message`/`details`/the HTTP status) — never throw a raw, unparsed error.
4. On success, parse and validate the response body against the matching Zod RESPONSE schema from `shared-contracts` (defense in depth — if the server and client drift, fail loudly in dev rather than silently misrendering), then return the typed, parsed value.

Base URL: accept it as a constructor/factory parameter (e.g. `createApiClient({ baseUrl: string })`) rather than hardcoding — `apps/web` will pass `process.env.NEXT_PUBLIC_API_BASE_URL` (already in its `.env.example` from T0.6) when it eventually wires this up.

## Required tests

Mock `fetch` (e.g. via `vi.stubGlobal('fetch', ...)` or a small manual mock — `node-fetch`/`msw` are NOT already dependencies, don't add one unless you have a strong reason, a plain mock function is enough for this). For at least 3-4 representative endpoints (don't exhaustively test all ~10, pick a GET, a POST-with-body, and one that returns a list):
- A successful call returns the correctly parsed/typed response.
- A non-2xx response throws `ApiClientError` with the right `code`/`message` from the envelope.
- A response that doesn't match the expected Zod schema (simulate a malformed/drifted server response) throws clearly rather than returning silently-wrong data.
- `credentials: 'include'` is actually passed in the `fetch` call (assert on the mock's call arguments).
