# Brief: T4.2 — `GameGateway`: the realtime move lifecycle

## Goal

The Socket.IO gateway implementing the server-authoritative move lifecycle from `docs/spec/v1.0/03_Technical_Architecture.md` §6: authenticated handshake, room/game join, move submission with the SAME accept/reject logic T3.5's `GamesService` already enforces via HTTP, and presence-aware resign/draw/claim-win. **This task does not reimplement any legality/persistence logic** — it is a thin realtime transport over `GamesService`/`RoomsService`, which already do the actual work.

## Acceptance-criteria IDs

SYNC-01, SYNC-02, SYNC-03, ROOM-02

## Allowed paths

- `apps/api/src/modules/games/game.gateway.ts`, `apps/api/src/modules/games/game.gateway.test.ts` (new)
- `apps/api/src/modules/games/games.service.ts` (EXTEND only — add a method to emit a domain event after a state-changing operation succeeds; see "Domain events" below. Do not touch its existing transactional logic from T3.5/T3.7.)
- `apps/api/src/modules/rooms/rooms.service.ts` (EXTEND only, same kind of addition — emit a domain event when room membership changes or a game starts. Do not touch T3.6's existing logic.)
- `apps/api/src/modules/games/games.module.ts`, `apps/api/src/modules/rooms/rooms.module.ts` (register the gateway/event emitter wiring)
- `apps/api/package.json` (add `@nestjs/event-emitter`, `@nestjs/websockets`, `@nestjs/platform-socket.io`, `socket.io` if any are missing — check first)

## Forbidden

- Do not change move-legality, clock, or persistence logic — every actual state mutation goes through `GamesService`/`RoomsService`'s EXISTING methods (`submitMove`, `resign`, the draw-offer methods from T3.7, `RoomsService.join` etc.). This gateway calls them and broadcasts the result, nothing more.
- Do not implement the `ClockScheduler` (per-game timeout timers) — that's T4.3. You may assume `GamesService`'s existing clock-expiry check inside `submitMove` is the only clock enforcement for now.

## Read first

`docs/spec/v1.0/03_Technical_Architecture.md` §6 (the lifecycle description) and `packages/shared-contracts/src/sockets.ts` (T3.1 — the exact event names/payloads; don't invent different ones).

## Design

### Authenticated handshake

In the gateway's connection handler, read the raw `Cookie` header from `client.handshake.headers.cookie` and resolve it via T3.3's `resolveSessionFromCookieHeader` (already built, exported from the sessions module — reuse it, don't reimplement cookie/hash lookup). If it resolves to `null` (no/invalid/expired session), immediately `client.disconnect(true)` — every socket interaction requires an authenticated guest/user, per ADR-020. If valid, store the resolved user on the socket (`client.data.user = ...`) for every later handler to use — never trust a client-supplied user/color field for authorization, always use what the handshake resolved.

### Domain events (the REST/WS unification mechanism)

Add `@nestjs/event-emitter`'s `EventEmitterModule.forRoot()` to wherever makes sense (likely `AppModule`, but that's outside your allowed paths — note in QUESTIONS if you think `AppModule` genuinely needs a change beyond what's already there, otherwise register `EventEmitterModule` within `GamesModule`/`RoomsModule` if that's sufficient for the emitter to be shared — check how NestJS's event emitter scoping actually works via context7 MCP if unsure).

`GamesService`: after `submitMove` returns `'accepted'`, after `resign` succeeds, after a draw-offer action changes state — emit `this.eventEmitter.emit('game.updated', { gameId, kind: 'move' | 'resign' | 'draw' | ..., moveId?, move? })` (inject `EventEmitter2` via constructor). Keep the payload minimal — the gateway will re-fetch a fresh snapshot via `getSnapshot(gameId)` rather than trusting a potentially-stale event payload for anything beyond "something changed, go look."

`RoomsService`: similarly emit `'room.updated', { roomId, gameId? }` when membership changes or a game starts (from `join`).

`GameGateway` (and this file may ALSO need to listen for room events — your call whether that's one gateway class or two, but they likely share a lot of plumbing like the authenticated-socket map, so one combined gateway handling both `room:*` and `game:*` events is probably simpler): `@OnEvent('game.updated')`/`@OnEvent('room.updated')` handlers that fetch the fresh snapshot and broadcast it to the Socket.IO room named by `gameId`/`roomId` (`this.server.to(gameId).emit('game:state', snapshot)` / `.emit('room:state', ...)`). For a move specifically, ALSO emit `game:move:accepted` with the move/moveId/gameVersion/clocks (T4.4's optimistic-move reconciliation on the client needs this granular event, not just a full snapshot to diff against) — emit BOTH `game:move:accepted` and `game:state` for a move update (slightly redundant, but simple and correct; don't over-engineer which one 'wins').

**Why this matters**: a player resigning via the REST endpoint (T3.7, no socket involved in that HTTP request) must still cause the OTHER player's live socket connection to see `game:finished` — that only works if `GamesService.resign` emits the same domain event `submitMove` does, and the gateway's listener doesn't care whether the change originated from REST or a socket event.

### Socket event handlers (`@SubscribeMessage`)

- `room:join` (`{roomId}`): validate via T3.1's Zod schema, `client.join(roomId)` (Socket.IO room == the `roomId` string), then emit the current `RoomSnapshot` back to the joining socket via a `room:state` ack/emit.
- `game:join` (`{gameId}`): same pattern — `client.join(gameId)`, emit `game:state` with the current `GameSnapshot`.
- `game:move` (`{gameId, moveId, expectedVersion, move}`): validate via Zod. Look up the game's `redId`/`blackId` (via `GamesService`) to determine which color `client.data.user.id` actually is — reject (`game:move:rejected`, reason `NOT_A_PLAYER` per `RejectReason`) if the authenticated user isn't either player. Call `GamesService.submitMove(gameId, { color, moveId, expectedVersion, move })`. On `'accepted'`: do nothing extra here — the `game.updated` event (emitted by `GamesService` itself) handles broadcasting via the listener above, so you're not duplicating broadcast logic in two places. On `'rejected'`: emit `game:move:rejected` to the SENDER ONLY, with the reason and a freshly-fetched `authoritativeVersion` (from `getSnapshot`). On `'duplicate'`: emit a fresh `game:state` to the sender only (so a retried client reconciles against current truth rather than getting a bespoke "duplicate" response shape).
- `game:sync` (`{gameId}`): fetch a fresh snapshot, emit `game:state` to the sender only (this is the reconnect/resync primitive T4.4 will call).
- `game:resign` (`{gameId}`): resolve the caller's color the same way as `game:move`, call `GamesService.resign` (or whatever T3.7's method is named).
- `game:draw` (`{gameId, action}`): same pattern, call the appropriate T3.7 draw-offer method.
- `game:claim-win` (`{gameId}`): implement simple in-memory presence tracking for this task — a `Map<gameId, Map<color, { connected: boolean; disconnectedAt: number | null }>>` on the gateway instance (single-process MVP; no Redis, per the architecture doc's explicit MVP guidance). Update it on `game:join` (mark connected) and on the gateway's `handleDisconnect` (mark disconnected + timestamp, for every game room that socket had joined — track which games a socket joined via `client.data.joinedGames: Set<string>`). On `game:claim-win`, check whether the OTHER color's presence entry shows `disconnectedAt` at least 60 seconds ago (ADR-019's abandonment threshold); if so, call a resign-like `GamesService` method with reason `ABANDONMENT` (add this as a minimal extension if T3.7 doesn't already have an abandonment path — reuse as much of the resign code path as possible, it's structurally identical with a different `TerminalEvent.type`); if not, reject (emit back to sender why, e.g. via a lightweight ack/error, exact shape is your call since no `ClientToServerEvents`/`ServerToClientEvents` entry explicitly covers the rejection response for this one — keep it simple).

### Disconnect handling

`handleDisconnect(client)`: for every game the socket had joined (`client.data.joinedGames`), mark that color's presence as disconnected (for the claim-win check above). Don't end any game automatically on disconnect — only an explicit `game:claim-win` after the 60s threshold ends a game for abandonment; a disconnect alone is just a presence change (the player might reconnect, per ADR-019's intent — handled by T4.3/T4.4, not by auto-resigning here).

## Required tests

Use `@nestjs/testing`'s module-building plus a real Socket.IO server/client pair bound to an ephemeral port (the standard way to integration-test a NestJS WebSocket gateway — check context7 MCP for the current idiomatic pattern if unsure), against the real `xq_test` Postgres (same harness as T3.3/T3.5/T3.6/T3.7).

- An unauthenticated connection (no/garbage cookie) gets disconnected immediately.
- Two authenticated socket clients representing the two players of a real game: `game:join` both, one submits a legal move, BOTH sockets receive `game:move:accepted` and `game:state` (not just the sender).
- An illegal move / wrong-turn move gets `game:move:rejected` on the sender ONLY, with the right `reason`, and the other socket receives nothing for that rejected attempt.
- **SYNC-01 over the wire**: two sockets racing the same `expectedVersion` — exactly one gets accepted, confirm via the DB (same assertion style as T3.5's test) that there's exactly one `GameMove` row.
- **REST→socket propagation**: resign a game via `GamesService.resign` directly (simulating what the REST controller does) while a socket is joined to that game room — confirm the socket receives `game:finished` even though the resignation didn't originate from a socket event.
- `game:claim-win` before the 60s threshold is rejected; after simulating the threshold (you'll need to either wait — avoid real sleeping in a test if possible, consider whether the presence map can accept an injectable/fakeable clock, or just accept a short real wait like 60s+ IS too slow for a test — reconsider: make the 60-second threshold a constant you can import and the test can use a MUCH shorter configured threshold via dependency injection, OR structure the presence check to take `now` as a parameter so the test can fake time — pick whichever keeps the test fast and deterministic, don't make the test suite sleep 60 real seconds).
