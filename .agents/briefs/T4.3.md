# Brief: T4.3 — `ClockScheduler`: proactive timeout, first-move abort, boot recovery

## Goal

T3.4/T3.5's clock logic only catches a timeout WHEN a move is submitted (the synchronous check inside `submitMove`). This task makes timeouts happen even when the losing player just stops playing and never submits anything — a real server-side timer per active timed game, armed/rearmed on every move, that proactively finishes the game the moment time runs out. Also handles ADR-019's "first move within 60s or ABORTED" rule and recovers correctly if the server process restarts mid-game (in-memory timers don't survive a restart).

## Design

### Timer map

An in-memory `Map<gameId, NodeJS.Timeout>` on the scheduler instance (single-process MVP, no Redis/BullMQ — matches the architecture doc's explicit MVP guidance). `arm(gameId, fireAt: Date)`: clears any existing timer for that `gameId`, sets a new `setTimeout` for `fireAt - now` ms that calls `checkTimeout(gameId, Date.now())`. `clear(gameId)`: just clears the timer (e.g. when a game finishes for any other reason).

### `GamesService.checkTimeout(gameId, now)` — the exactly-once mechanism

Same transactional shape as `submitMove`: row-lock the `Game`, reconstruct state, then:
- If `status !== 'ACTIVE'`: no-op (already finished by something else — this is the race-safety net).
- If the game has had fewer than 2 moves total (i.e. still within the "first move" phase for one or both sides) and the relevant side's 60-second first-move window (per ADR-019 — the window starts when the game became `ACTIVE` for Red's first move, and when Red's first move was accepted for Black's first move) has elapsed without that move existing: set `status: 'ABORTED'`, persist, emit the domain event, return.
- Otherwise, use T3.4's `isClockExpired(clock, now)` — if it returns the active color, apply a `TIMEOUT` result via `@xq/xiangqi-core`'s `evaluateGame` with that terminal event (same pattern T3.7 used for resign/draw), persist `status: 'FINISHED'`/result columns, emit the domain event.
- If neither condition holds (the timer fired slightly early/late relative to an intervening accepted move that reset the clock — a normal race, not a bug): no-op. This is why `checkTimeout` re-derives everything from the current DB state rather than trusting whatever triggered the timer call.

### Arming/rearming timers

Whenever a game becomes `ACTIVE` (hook into wherever that happens — check `RoomsService`/`GamesService` for the actual transition point from T3.5/T3.6, and add a minimal call from there, or listen for the domain event if one already exists for this transition) — arm the first-move-abort timer for Red (now + 60s).

Whenever a move is accepted (via the `'game.updated'` domain event with `kind: 'move'`, OR by extending wherever `submitMove` concludes if the event isn't wired yet): fetch the fresh clock state and `arm(gameId, now + remainingMsForNewActiveColor)` — this both handles the ordinary ongoing-timeout case AND, for the first two moves specifically, effectively gets overridden by the first-move-abort logic inside `checkTimeout` itself (since `checkTimeout` checks the abort condition FIRST) — you don't need two different timer-arming code paths for "first move" vs "ongoing," just arm consistently and let `checkTimeout`'s own branching sort out which rule applies when the timer fires.

Whenever a game finishes (any reason): `clear(gameId)`.

### Boot recovery (`OnModuleInit`)

On startup: query all `Game` rows with `status: 'ACTIVE'`. For each: call `checkTimeout(gameId, Date.now())` immediately (catches anything that expired while the process was down — this will correctly no-op for games that are still fine) and, if still active afterward, `arm` its timer based on current remaining time. This single pass handles both "a game timed out while we were offline" and "re-establish timers for everything still running."

## Required tests

Use fake timers (`vi.useFakeTimers()`) so tests run instantly rather than waiting real seconds. Real `xq_test` Postgres for the persistence assertions (same harness as prior M3 tasks).

- A game nearing its active color's time limit: advance fake time past expiry, confirm `checkTimeout`'s timer fires and the game ends with `TIMEOUT` and the correct winner, persisted to the DB.
- A move accepted just before the old timer would have fired correctly REARMS to the new deadline — advancing time to the OLD deadline does nothing; advancing to the NEW (later) deadline does finish it.
- First-move abort: a game with zero moves, past 60s from activation → `ABORTED`. A game with exactly one move (Red moved, Black hasn't), past 60s from THAT move → also `ABORTED`.
- Exactly-once: call `checkTimeout` twice in a row after real expiry — second call is a no-op (game already `FINISHED`, status check short-circuits), no double-processing.
- Boot recovery: construct a DB state representing a game that "expired while the server was down" (an `ACTIVE` game with a `turnStartedAt`/clock that's already expired relative to the current fake time, with NO scheduler timer having ever been armed for it, simulating a fresh process), instantiate a new scheduler, call its `OnModuleInit` logic directly, confirm it gets finished immediately.
