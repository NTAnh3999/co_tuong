# Brief: T4.4 — `OnlineGameController`

## Goal

A second implementation of T2.1's `GameController` interface, for online play: wraps T4.1's `createGameSocket`, treats every `game:state` snapshot from the server as authoritative truth, optimistically renders the local player's own move while awaiting confirmation, and resyncs on connect/reconnect/tab-visibility.

## Acceptance-criteria IDs

SYNC-03

## Allowed paths

- `apps/web/src/features/game/controller/online-game-controller.ts`, `.test.ts` (new — alongside T2.1's existing `game-controller.ts`/`local-game-controller.ts`, do not modify those)
- `apps/web/package.json` (add `uuid` or use `crypto.randomUUID()` — prefer the latter, no new dependency needed, browsers and Node 22 both support it)

## Forbidden

- Do not modify `apps/web/src/features/game/controller/game-controller.ts`'s core `GameController` interface in a way that breaks `LocalGameController` — you may ADD optional fields to a wider state type specific to this controller (see below), but the base interface's required members stay as T2.1 defined them.
- Do not modify `packages/api-client/src/socket.ts` (T4.1).

## Design

### Extended state shape

```ts
export interface OnlineGameControllerState extends GameControllerState {
  readonly clocks: ClockState | null;       // from the latest GameSnapshot
  readonly gameVersion: number;
  readonly connectionStatus: 'connecting' | 'connected' | 'disconnected';
  readonly pendingMoveId: string | null;     // non-null while our own move awaits server confirmation
}

export function createOnlineGameController(
  gameId: string,
  apiBaseUrl: string,
): GameController & { getState(): OnlineGameControllerState };
```

### Core behavior

1. On creation: `createGameSocket(apiBaseUrl, { onConnect, onDisconnect, onGameState, onMoveAccepted, onMoveRejected, onGameFinished })` (T4.1). Set `connectionStatus: 'connecting'` initially.
2. `onConnect`: emit `joinGame(gameId)` via the socket wrapper's method, set `connectionStatus: 'connected'`.
3. `onGameState(snapshot)`: this is authoritative — replace `position` (derive from `snapshot.initialFen` + `snapshot.moves` via `@xq/xiangqi-core`'s `fromFen`/`applyMove`, or if that's expensive to redo every time, at minimum trust `snapshot`'s move list length/content as ground truth), `history`, `lastMove`, `clocks`, `gameVersion`, `result`. If `pendingMoveId` is set and the snapshot's move list now includes a move at the expected position matching what we optimistically applied, clear `pendingMoveId` (our move was confirmed). If the snapshot DISAGREES with our optimistic local state in a way that means our pending move was NOT applied (e.g. move count didn't grow the way we expected), roll back to the snapshot's truth and clear `pendingMoveId` (our optimistic guess was wrong — maybe we got disconnected mid-flight and the server never saw it; the user will need to retry the move manually, don't auto-resend blindly here since that's covered by the reconnect flow in point 6).
4. `submitMove(move)`: if `isLegalMove(currentPosition, move)` is false locally (quick optimistic check via `@xq/xiangqi-core`), return `false` immediately without any network call. Otherwise: generate `const moveId = crypto.randomUUID()`, optimistically compute the new local `position`/`history`/`lastMove` (same as `LocalGameController`'s apply step, but DON'T touch `result` optimistically — only the server's `game:state`/`game:finished` decides results online, per the architecture doc's "client chỉ hiển thị dự đoán" principle), set `pendingMoveId: moveId`, emit `socket.submitMove({ gameId, moveId, expectedVersion: state.gameVersion, move })`, return `true` (optimistically accepted locally — the UI shows the move immediately; a later rejection rolls it back).
5. `onMoveRejected({moveId, reason, authoritativeVersion})`: if `moveId !== state.pendingMoveId`, ignore (stale/irrelevant). Otherwise: roll back the optimistic move (you'll need to have kept the pre-move state around, or simply re-derive from the last known-authoritative `game:state` — either approach is fine, just don't leave the board showing a move the server didn't accept), clear `pendingMoveId`, update `gameVersion` to `authoritativeVersion`. Surface the rejection somehow for the UI to use later (e.g. a `lastRejection: { reason, at: number } | null` field on the state — your call on the exact shape, keep it simple).
6. `onMoveAccepted(payload)`: if it's OUR pending move (matching `moveId`), this mostly just confirms what `onGameState` will also tell us — you can treat this as a secondary confirmation signal or rely primarily on `onGameState`; don't build complex logic here, the state-reconciliation in point 3 is the source of truth.
7. `onDisconnect`: set `connectionStatus: 'disconnected'`. Do NOT clear `pendingMoveId` or roll back optimistic state yet — wait for reconnection to resolve it (point 8).
8. **Reconnect**: when the underlying socket reconnects (T4.1's `onConnect` fires again after a disconnect — Socket.IO's default reconnection will do this automatically; you don't need to hand-roll retry logic, just react to the connect event happening a 2nd+ time), re-emit `joinGame(gameId)` (which per T4.2's gateway handler responds with a fresh `game:state`) — this naturally resolves any pending move via the SAME reconciliation logic in point 3, no special "resend" code path needed. (This satisfies "idempotent moveId resend on reject" from the plan via the simpler route of always re-syncing truth on reconnect rather than guessing whether to resend — document this reasoning in a code comment since it deliberately differs from a literal reading of that phrase.)
9. **Tab visibility**: add a `document.visibilitychange` listener (guard for SSR/non-browser environments — this controller is only ever instantiated client-side in practice, but don't crash if `document` is somehow unavailable) that calls the same "re-join and resync" logic as reconnect, when the tab becomes visible again (`document.visibilityState === 'visible'`) — catches drift from being backgrounded, independent of the socket's own connection state.
10. `flip()`, `resign(color)`, `offerDraw()`: these call the socket wrapper's `resign(gameId)`/`draw(gameId, 'offer')` methods (server-authoritative — don't apply any optimistic local result for these, wait for the server's broadcast). `undo` is NOT implemented for online play (leave it `undefined` on the returned object — per the base docs, online games don't support undo).
11. Clean up: expose a `dispose()`-equivalent somehow (the base `GameController` interface doesn't have one — check whether to add it as another optional member, since the socket connection needs explicit teardown when a page unmounts; if the interface doesn't support this cleanly, note it in QUESTIONS rather than silently leaking the connection).

## Required tests

Mock `createGameSocket` (from `@xq/api-client`) the same way T4.1's own tests mocked `socket.io-client` — don't depend on a real server for this unit-level test.
- `submitMove` with a locally-illegal move returns `false`, no socket call.
- `submitMove` with a legal move optimistically updates `position`/`history` immediately (before any mocked server response) and sets `pendingMoveId`.
- A simulated `onGameState` call confirming the move clears `pendingMoveId` and keeps the optimistic position (now backed by authoritative data).
- A simulated `onMoveRejected` for the pending move rolls back the optimistic position and clears `pendingMoveId`.
- A simulated disconnect→reconnect sequence re-emits `joinGame`.
- `resign`/`offerDraw` call the socket wrapper's corresponding methods, without locally mutating `result`.
