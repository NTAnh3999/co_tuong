# Brief: T4.5 — `/play/online` + `/room/[code]`: create/join a private room

## Goal

The first web pages that exercise the REST rooms API (T3.6) and the realtime room lifecycle (T4.2). A player picks a time control and color preference and creates a room, or enters a code to join one; both players land on the SAME room page, see each other appear live via Socket.IO, and get redirected to `/game/[gameId]` once the room's second seat fills and the game starts.

This task ALSO has to close a real gap nothing before it has touched: **nothing in `apps/web` has ever called `POST /sessions/guest`**. Every socket connection requires an authenticated session cookie (T4.2's handshake disconnects unauthenticated sockets), and the rooms REST endpoints require `SessionGuard`. You are building the first "ensure I have a session" bootstrap for the whole web app.

## A gotcha you must get right: the socket URL is NOT the REST base URL

`NEXT_PUBLIC_API_BASE_URL` is `http://localhost:3001/api/v1` — that `/api/v1` path is a NestJS **global HTTP prefix** (`app.setGlobalPrefix('api/v1')` in `apps/api/src/main.ts`) and does **not** apply to the Socket.IO gateway, which listens at the bare origin with the default `/socket.io` engine path and the default `/` namespace. If you pass the REST base URL (including `/api/v1`) straight into `createGameSocket`, `socket.io-client` will interpret `/api/v1` as a **namespace**, and the connection will silently never fire `connect` (the server has no such namespace registered) — it'll just hang/time out, which is an easy thing to ship undetected since there's no socket integration test for the web side yet.

Derive the socket origin by stripping the path: `new URL(apiBaseUrl).origin`. Put this derivation in `use-session.ts` (or a tiny exported helper next to it) so T4.6 can reuse it for `createOnlineGameController`'s `apiBaseUrl` parameter too — note T4.4's `OnlineGameController` names that parameter `apiBaseUrl` but it's actually passed straight into `createGameSocket(apiBaseUrl, ...)`, so despite the name it needs to be the ORIGIN, not the REST base URL. Document this clearly with a one-line comment at the call site since the naming is misleading.

## Design

### `apps/web/src/lib/api-client.ts`

```ts
import { createApiClient } from '@xq/api-client'

export const apiClient = createApiClient({
  baseUrl: process.env.NEXT_PUBLIC_API_BASE_URL ?? 'http://localhost:3001/api/v1',
})

export function socketOrigin(): string {
  return new URL(process.env.NEXT_PUBLIC_API_BASE_URL ?? 'http://localhost:3001/api/v1').origin
}
```

(Exact shape is your call — the two exports above are the minimum every later page needs: a shared REST client instance, and the derived socket origin.)

### `apps/web/src/features/session/use-session.ts`

A React hook `useSession(): { user: UserSummary | null; status: 'loading' | 'ready' | 'error' }` that, on mount (client-side only — this hook is for Client Components):

1. Calls `apiClient.getMe()`.
2. If it resolves, that's the user — `status: 'ready'`.
3. If it rejects with `ApiClientError` and `status === 401` (no/invalid/expired session cookie), call `apiClient.createGuestSession({ nickname: <generated> })` — generate something like `` `Khách${Math.floor(1000 + Math.random() * 9000)}` `` (a default guest nickname; there's no nickname-entry UI in this task's scope, keep it simple) — its response IS already a `UserSummary` (the schema is literally `userSummarySchema`), use it directly as the user, `status: 'ready'`.
4. Any other error (network, 500, etc.) → `status: 'error'`.
5. Guard against double-invocation in React's dev-mode strict effects (e.g. a ref flag) so you don't accidentally create two guest sessions for one page load.

This hook is the first piece of session-bootstrap infrastructure in the whole web app — T4.6 and T4.7 will both need it too (to know "which color am I" and to have an authenticated cookie before opening a socket), so keep its exported shape simple and obviously reusable; mention in your final message if you think it should move to a more shared location, but building it here is fine for this task.

### `apps/web/app/play/online/page.tsx`

A client component:

- Time control picker: 3 presets per ADR-019 — "Nhanh" (5 phút + 3 giây), "Tiêu chuẩn" (10 phút + 5 giây, default-selected), "Chậm" (15 phút + 10 giây). Map to `{initialMs, incrementMs}` in milliseconds.
- Host color picker: Đỏ (red) / Đen (black) / Ngẫu nhiên (random) — matches `createRoomRequestSchema`'s `hostColor` enum.
- "Tạo phòng" button: uses `useSession()` to ensure a user exists first (show a loading state while `status === 'loading'`), then `apiClient.createRoom({ timeControl, hostColor })`, then `router.push(`/room/${room.code}`)` (use the returned `code`, not `roomId`, since that's what the URL param is).
- A separate "Nhập mã phòng" input + "Tham gia" button: takes a user-typed code, `router.push(`/room/${code.trim().toUpperCase()}`)` directly — don't call `joinRoom` here, let the room page's own join-if-not-a-member logic (below) handle it, so there's exactly one join code path instead of two.
- Surface `ApiClientError` messages (e.g. room full, not found) inline, in Vietnamese, reusing this project's existing error-display conventions if any exist (check `apps/web/src/components/states/` from T2.6), otherwise keep it simple.

### `apps/web/app/room/[code]/page.tsx`

A client component, `params: { code: string }` (Next.js 15 App Router — confirm whether your Next version wants `params` as a Promise you `await`/`use()` in a Client Component; check an existing dynamic-route example in this codebase or Next 15's docs if none exists yet — this codebase has no `[param]` route yet, so you're the first; get this right, it's a common Next 15 App Router gotcha).

1. `useSession()` first — need an authenticated user before anything else.
2. `apiClient.getRoom(code)` to fetch the current snapshot. If the response's `members` doesn't include the current user's `userId` AND `members.length < 2` AND `status === 'WAITING'`, call `apiClient.joinRoom(code)` to join (this is the ONE join code path mentioned above). If the room is full/not-found/already-started-without-you, show an appropriate Vietnamese error state instead of trying to join.
3. Open a socket via `createGameSocket(socketOrigin(), { onConnect: () => socket.joinRoom(roomId), onRoomState: (snapshot) => setRoom(snapshot), ... })` (import from `@xq/api-client`) once the initial REST fetch/join settles and you have the room's `roomId` (note: the socket's `room:join` event takes `roomId`, not the human-typed `code` — don't confuse the two, `RoomSnapshot.roomId` is what T4.2's gateway expects).
4. Render: room code (large, with a "copy" affordance — a plain `navigator.clipboard.writeText` button is fine, no need for a toast library), time control, each member's nickname + assigned color + host badge, a "waiting for opponent" state when `members.length < 2`.
5. When `room.status === 'STARTED'` and `room.gameId !== null` (from either the initial fetch or a live `room:state` push), `router.push(`/game/${room.gameId}`)`.
6. Dispose the socket connection on unmount (`socket.disconnect()` in a cleanup effect) — same pattern T4.4's `OnlineGameController.dispose()` establishes, just inline here since this page doesn't need a full `GameController`.
