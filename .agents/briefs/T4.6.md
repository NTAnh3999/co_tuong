## Closing the draw-offer visibility gap (small, necessary shared-contracts extension)

`GameSnapshot` (in `packages/shared-contracts/src/domain.ts`) currently has no field exposing a pending draw offer, even though the DB (`Game.drawOfferBy`/`drawOfferPly`, from T3.7) already tracks one. Without this, there is no way for the UI to show "your opponent offered a draw, accept/decline?" — the feature would be unusable. Add one field:

```ts
export const gameSnapshotSchema = z.object({
  // ...existing fields...
  drawOfferBy: colorSchema.nullable(),
});
```

Then in `apps/api/src/modules/games/games.service.ts`, populate it in `getSnapshot` (likely needs a small addition to what `reconstruct` returns, or a second small query — your call on the cleanest way to thread it through without touching `submitMove`/`resign`/`drawOffer`'s own transactional logic). This is purely additive (a new nullable field nothing currently reads), so it cannot break any existing test; run the full `@xq/api` gate after the change to confirm.

## Design

### `ClockDisplay` component (new)

```ts
export interface ClockDisplayProps {
  readonly clocks: ClockState | null; // from @xq/shared-contracts
  readonly orientation: Color; // which side renders on top vs bottom, matching Board2D's orientation convention
}
```

Ticks locally once per second (a `setInterval`/`useEffect`, cleaned up on unmount) to recompute each side's remaining time as `remaining - max(0, now - turnStartedAt)` for whichever color is `activeColor` (the OTHER color's remaining is static until it becomes their turn) — this is purely a presentational countdown; it must NEVER decide a timeout itself (that's server-authoritative, via `ClockScheduler`/`game:finished`). Format as `mm:ss`. Render both players' time, visually marking whichever is `activeColor`. Render nothing (or a placeholder dash) when `clocks` is `null` (untimed game — not currently reachable from `/play/online`'s presets, but don't crash if it happens).

### `apps/web/app/game/[id]/page.tsx`

A client component, `params: { id: string }` (same Next 15 App Router params convention T4.5 had to resolve for `/room/[code]` — check what T4.5 landed on and follow the same pattern for consistency).

1. `useSession()` for the current user.
2. Once the user is ready, construct `createOnlineGameController(gameId, socketOrigin())` (from T4.4 + T4.5's helper) — exactly ONE instance per page mount, via `useState(() => ...)` (same lazy-init pattern `/play/local/page.tsx` uses for `LocalGameController`), and call `.dispose()` in a cleanup effect on unmount.
3. Subscribe via `useSyncExternalStore` (same helper pattern as `/play/local/page.tsx`'s `useGameControllerState`).
4. Determine the current player's color: compare `useSession()`'s user id against the snapshot's `redPlayerId`/`blackPlayerId` (you'll need these — `OnlineGameControllerState` doesn't currently expose them directly; either read them from the controller's internal snapshot some other way, or note this as a gap and fall back to treating the player as a spectator if you can't determine it cleanly. Check `online-game-controller.ts` again — if `redPlayerId`/`blackPlayerId` genuinely aren't threaded through to the state, that's a real gap worth flagging in QUESTIONS, but try first: `OnlineGameController`'s state is built from `GameSnapshot` which DOES have both IDs, so the simplest fix might be adding them to `OnlineGameControllerState` — but that file is FORBIDDEN for you to touch. If you hit this, report it precisely in QUESTIONS and ship the page treating color as unknown/spectator-safe in the meantime, rather than guessing or silently editing a forbidden file).
5. Layout (match `/play/local/page.tsx`'s general structure): `Board2D` (interactive only if the determined color matches `state.position.turn` AND it's actually this player's own color — not a spectator), `ClockDisplay`, `MoveList`, `CapturedPieces` ×2 (computed via replay, same as T2.4's pattern), `GameStatusBanner`.
6. Connection banner: when `state.connectionStatus === 'disconnected'`, show an inline Vietnamese banner ("Mất kết nối, đang thử kết nối lại...") — this is a NEW small inline element here, not `OfflineBanner` from T2.6 (that one tracks `navigator.onLine`, a different signal than the socket's own connection state).
7. Rejection feedback: when `state.lastRejection` is set, show it briefly (e.g. a line of text near the board with the Vietnamese reason) — keep this simple, no toast library needed.
8. Action buttons (hidden entirely for a spectator): "Đầu hàng" (resign — confirm-before-send is nice-to-have, not required) calling `controller.resign?.(myColor)`; "Cầu hòa" calling `controller.offerDraw?.()`. If the new `drawOfferBy` snapshot field (see above) shows the OPPONENT offered and it's not already responded to, show "Đối thủ đề nghị hòa" with Chấp nhận/Từ chối buttons that call `controller.offerDraw?.()` too (per T4.4's design, `offerDraw` just emits `game:draw` with `action:'offer'` — check whether you need `OnlineGameController` to support `accept`/`decline` actions distinctly; if its current `offerDraw()` signature only supports the `'offer'` action and not `'accept'`/`'decline'`, that's a real gap — `online-game-controller.ts` is forbidden for you to edit, so report this precisely in QUESTIONS rather than reinventing a workaround, and ship the page with just the "offer" half of the flow functional in the meantime).
9. `ResultDialog` wired to `state.result`, no `onRematch` (per Forbidden).
