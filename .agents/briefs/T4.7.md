# Brief: T4.7 — Rematch flow (ADR-022)

## Goal

Per ADR-022: after a game finishes, either player can request a rematch — a new game in the SAME room, colors swapped, and it only starts once BOTH players have asked for one. This is a full-stack task: nothing in the backend currently tracks a rematch vote at all, and the web game page needs a way to trigger it and learn when the opponent has also agreed.

- `apps/web/app/game/[id]/page.tsx` (EXTEND only — wire up `ResultDialog`'s `onRematch`, read the room code, show rematch status, navigate on success)

## Forbidden

- Do not modify `apps/web/src/features/game/controller/online-game-controller.ts` (T4.4) — rematch is driven by REST (`apiClient`) + polling, not through the `GameController`/socket layer, so this file shouldn't need touching at all; if you think it does, stop and ask in QUESTIONS.
- Do not modify `GameGateway` (T4.2), `ClockScheduler` (T4.3), or any `games.*` file — rematch only touches rooms.
- Do not add a database migration. Track rematch votes in-memory on `RoomsService` (a `Map<roomId, Set<userId>>`), the SAME MVP pattern already used for `GameGateway`'s presence map (T4.2) and `ClockScheduler`'s timer map (T4.3) — single-process, no Redis, documented precedent in this codebase.

## Carrying the room code to the game page

`GameSnapshot` has no `roomId`/room-code field (the `Room`→`Game` link is one-directional; a game doesn't know its room). The game page needs the room code to let a player request a rematch in that room. Simplest fix, no schema change needed: when `/room/[code]/page.tsx` (T4.5) redirects to the game page on `room.status === 'STARTED'`, change it to navigate to `` `/game/${room.gameId}?room=${code}` `` (append the query param) instead of the bare path. Read it back in `/game/[id]/page.tsx` via `useSearchParams()`. If there's no `?room=` param (e.g. someone navigates to `/game/[id]` directly without going through a room — not currently possible via any built UI, but don't crash), simply hide the rematch button entirely.

## Design

### Backend: tracking and resolving a rematch vote

`packages/shared-contracts/src/domain.ts` — extend `roomSnapshotSchema` with one field:

```ts
rematchVotes: z.array(z.string()), // userIds who have asked for a rematch in the CURRENT room.gameId
```

`packages/shared-contracts/src/rest.ts` — new schemas:

```ts
export const requestRematchResponseSchema = roomSnapshotSchema;
export type RequestRematchResponse = z.infer<typeof requestRematchResponseSchema>;
```

(No request body needed — it's just "I, the authenticated caller, want a rematch.")

`apps/api/src/modules/rooms/rooms.service.ts` — add:

```ts
private readonly rematchVotes = new Map<string, Set<string>>(); // roomId -> userIds

async requestRematch(code: string, user: UserSummary): Promise<RoomSnapshot> {
  // 1. Look up the room by code (reuse the existing FOR UPDATE row-lock pattern from joinRoom).
  // 2. Reject (NotFoundException/ConflictException — your call on exact codes) if:
  //    - the room doesn't exist,
  //    - the caller isn't one of its two members,
  //    - room.gameId is null, or the CURRENT game (via `this.games.getSnapshot(room.gameId)`) is
  //      still ACTIVE (no result yet) — a rematch can only be requested once the current game
  //      has actually finished/aborted.
  // 3. Add `user.id` to this room's vote set (idempotent — calling it twice does nothing extra).
  // 4. If BOTH members' ids are now in the vote set:
  //    - create a new game via `this.games.createGame(STARTING_FEN, room's timeControl, <swapped ids>, ...)`
  //      — swap which member is red/black vs the CURRENT room membership's colors (read the
  //      existing RoomMember rows' `color` to know current assignment, then invert it — don't
  //      just invert `hostColor`, since the host's color was fixed at room creation and may not
  //      match who's currently red/black after a previous rematch already swapped it once).
  //    - `activateGame` it, update `room.gameId` to the new game and the two `RoomMember.color`
  //      values to their new (swapped) colors, clear this room's vote set.
  //    - emit `room.updated` (same event T4.2's gateway already listens for — a live socket in
  //      the room, if any, will get the fresh snapshot with the new `gameId` for free; the GAME
  //      page itself does NOT hold a room socket connection, see "resolving on the client" below,
  //      so don't rely on this push reaching the game page — it's a nice-to-have for anyone still
  //      on the room page, not the mechanism the game page uses).
  // 5. Return the current room snapshot (with the vote set echoed in `rematchVotes`) either way.
}
```

`apps/api/src/modules/rooms/rooms.controller.ts` — add:

```ts
@Post(':code/rematch')
requestRematch(@Param('code') code: string, @CurrentUser() user: UserSummary): Promise<RoomSnapshot> {
  return this.rooms.requestRematch(code, user);
}
```

(Behind the existing `@UseGuards(SessionGuard)` on the controller class — no new guard needed.)

`toSnapshot`'s signature will need the votes threaded in from each call site (`createRoom`'s fresh room has none yet; `joinRoom`/`getRoom`/`getRoomById`/`requestRematch` all need to look up `this.rematchVotes.get(room.id) ?? new Set()` and pass the array in).

`packages/api-client/src/index.ts` is explicitly OUT of your allowed paths — if the web side needs a typed client method for this new endpoint and one doesn't exist, call `apiClient`'s underlying `fetch`/`request` some other way inside the page itself, OR note in QUESTIONS that `packages/api-client` needs a `requestRematch(code)` method added (a one-line, low-risk addition) rather than editing that package yourself.

### Web: requesting and resolving a rematch

In `apps/web/app/game/[id]/page.tsx`:

1. Read `?room=` via `useSearchParams()`. If present, pass an `onRematch` callback to `ResultDialog` (per its existing optional prop — see T4.6's work); if absent, pass nothing (dialog hides the button automatically, per its existing implementation).
2. `onRematch`: call the rematch REST endpoint (via `apiClient`, or the fallback approach above if `api-client` wasn't extended), then show a waiting state ("Đang chờ đối thủ đồng ý chơi lại...") if the room's `gameId` hasn't changed yet (i.e. the response's `rematchVotes` has 1 entry, not 2, OR the response's `gameId` still equals the CURRENT `id` route param).
3. While waiting, poll `GET /rooms/:code` (via `apiClient.getRoom(code)`, already exists) every ~2 seconds. The moment the returned `gameId` differs from the current page's `id`, navigate to `` `/game/${newGameId}?room=${code}` ``. Stop polling on unmount.
4. If the OTHER player requests it first (you never find out proactively since this page has no room socket — that's fine, this is a deliberate MVP simplification per the design above), nothing happens on your screen until YOU also click "Chơi lại" (which immediately resolves the vote on the server and gets the new `gameId` back in that same request's response) — document this one-directional-until-both-click behavior plainly in KNOWN GAPS; it's an acceptable MVP limitation, not a bug, but should be visible to the orchestrator.

## Required tests

- `rooms.service` (extend `rooms.integration.test.ts` if it exists, or add to it — check first): one member requesting a rematch alone does not create a new game; both requesting it does, with colors swapped from the original room membership; requesting before the current game has finished is rejected; requesting by a non-member is rejected.
- `game/[id]/page.test.tsx`: clicking "Chơi lại" calls the rematch endpoint; a subsequent `getRoom` poll returning a new `gameId` navigates to the new game's URL with the room code preserved.
