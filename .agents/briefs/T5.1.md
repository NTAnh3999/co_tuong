# Brief: T5.1 — Pikafish worker HTTP service (engine pool + ADR-024 difficulty)

## Goal

Turn `services/pikafish-worker` from a pure UCI-client library (built in T0.8: `EngineProcess`, `initEngine`/`setPosition`/`perft`/`getFen`/`bestMove`) into an actual standalone HTTP service: a small pool of real Pikafish subprocesses, a bounded request queue, hard-timeout kill/respawn, and one internal endpoint that returns a move picked according to ADR-024's three difficulty profiles. This is the ONLY task that talks to the raw UCI protocol for move selection; `apps/api`'s future `AiModule` (T5.3) will call this service over plain HTTP and never spawns an engine itself.

This task also extends the existing UCI command layer with MultiPV support, which doesn't exist yet — `bestMove()` in `commands.ts` only reads the single `bestmove` line today.

## Acceptance-criteria IDs

AI-01, AI-02

## Read first — do this before writing any parsing code

- `docs/adr/ADR-024-ai-difficulty.md` — the EXACT algorithm: three profiles (Dễ/Vừa/Khó), each with a `movetime`, a `MultiPV` count, and a specific selection rule (uniform-random-in-threshold / weighted-random-in-threshold / always-best). Implement exactly what it specifies — the numbers (50ms/200ms/1000ms, MultiPV 5/3/1, ±300cp/±80cp thresholds, 50/35/15 weights) are not suggestions.
- `services/pikafish-worker/src/uci/{engine-process,commands}.ts` — the existing UCI client. `EngineProcess.send`/`waitFor` is the primitive; `commands.ts` has the existing thin wrappers. Extend this layer, don't replace it.
- **Before writing the MultiPV parser, actually run the real engine by hand** (`tools/pikafish/Pikafish-Windows-x86-64-universal.exe` — gitignored but present on disk per T0.0's setup, confirmed working: `go perft 4` returns `3290240`) and inspect its real `info ... multipv N ...` output for a `go movetime 200` search with `setoption name MultiPV value 3` set first. Don't guess the line format from UCI spec memory alone — Pikafish's actual output format (score cp vs score mate, pv formatting, whether it reprints lower-index multipv lines on every depth iteration) is what the parser must match.

## Design

### Package shape

Add a real HTTP entrypoint. Use whatever minimal server you're comfortable with (Node's built-in `http` module, or a tiny dependency like `express` if that's clearly less code — this package currently has zero runtime dependencies, so weigh that before adding one). Add `"start": "node dist/index.js"` to `package.json` (matching `apps/api`'s convention) and a `"dev"` script if a watch-mode tool is trivial to wire up, but `start` over the built output is the one that actually matters (T5.6's Dockerfile will run it).

Env vars (all with sane defaults except `PIKAFISH_PATH`, which must be required — fail fast at startup with a clear error if unset):
- `PIKAFISH_PATH` (required, no fallback — same convention `EngineProcess` already documents)
- `PORT` (default `4000`)
- `POOL_SIZE` (default `2`, per ADR-024)
- `QUEUE_CAP` (default `20`, per ADR-024)

### MultiPV UCI extension (`commands.ts`)

Add something like:

```ts
export interface MultiPvLine {
  readonly multipv: number;  // 1-based, 1 = best
  readonly move: string;      // UCI move, e.g. "h2e2"
  readonly scoreCp: number;   // centipawns from the side-to-move's perspective; map a "mate N" score to a large-magnitude cp value with the correct sign (your call on the exact mapping — document it with a one-line comment) so downstream threshold math still makes sense
}

export async function searchMultiPv(
  engine: EngineProcess,
  movetimeMs: number,
  multiPv: number,
): Promise<MultiPvLine[]>
```

Send `setoption name MultiPV value <multiPv>` once before `go movetime <movetimeMs>`. Collect every `info ... multipv <N> ...` line up to and including `bestmove`; for each multipv index, keep only the LAST line seen (engines re-emit updates per iterative-deepening pass) before parsing out `score cp`/`score mate` and the first move token after `pv`. Return the lines sorted by `multipv` ascending. If the engine returns fewer lines than requested (e.g. fewer than `multiPv` legal moves exist, common near mate), return however many it actually gave — don't pad or error.

### ADR-024 selection (new module, e.g. `difficulty.ts`)

```ts
export type Difficulty = 'easy' | 'medium' | 'hard';

export interface DifficultyProfile {
  readonly movetimeMs: number;
  readonly multiPv: number;
  readonly thresholdCp: number;
}

export const DIFFICULTY_PROFILES: Record<Difficulty, DifficultyProfile>; // the exact ADR-024 numbers

export function selectMove(lines: MultiPvLine[], difficulty: Difficulty, random: () => number = Math.random): MultiPvLine;
```

`selectMove` filters `lines` to those within `thresholdCp` of the best (index-1) line's score, then applies the ADR-024 selection rule for that difficulty (uniform random / weighted 50-35-15 / always best). Take `random` as an injectable parameter (not a hardcoded `Math.random()` call inside the branching logic) specifically so unit tests can assert the distribution deterministically without flaky real-randomness — this mirrors how `games.service.ts` injects `now` everywhere instead of calling `Date.now()` inline.

### Engine pool + queue (new module, e.g. `pool.ts`)

- `POOL_SIZE` persistent `EngineProcess` instances, each initialized via the existing `initEngine()` at service startup (fail startup loudly if any fails to initialize — this is a required dependency, not optional).
- An in-memory FIFO queue of pending requests when every engine is busy. `QUEUE_CAP` is the max queue LENGTH (not counting the ones currently running on an engine) — reject immediately (don't queue at all) once the queue is at capacity.
- Per-request hard timeout: `movetimeMs + 1500`. If exceeded: treat that specific `EngineProcess` as dead — `dispose()` it (don't wait long for graceful quit) and spawn+`initEngine()` a fresh replacement for that pool slot, then reject the timed-out request's promise. A slow/wedged engine must not take down the whole pool slot permanently.
- Track simple counters for `/metrics` (see below) as requests complete, time out, or error.

### HTTP endpoints

- `GET /health` → `200 { status: 'ok', poolSize, idleEngines, queueLength }` always 200 if the process is alive; this is a liveness check, not a "is everything healthy" check (that's `/metrics` for a human/dashboard to judge).
- `GET /metrics` → `200` JSON (plain JSON is fine — no Prometheus text format needed, keep this simple): `{ totalRequests, totalTimeouts, totalErrors, totalRespawns, poolSize, queueLength }`. No need for latency histograms etc. — counters are enough for MVP.
- `POST /bestmove` body `{ fen?: string, moves?: string[], difficulty: 'easy' | 'medium' | 'hard' }` (same `{fen, moves}` shape `setPosition` already takes — reuse it, don't invent a different position encoding) →
  - `200 { move: string, scoreCp: number }` on success.
  - `503 { error: { code: 'QUEUE_FULL', message: '...' } }` if the queue is already at `QUEUE_CAP`.
  - `504 { error: { code: 'ENGINE_TIMEOUT', message: '...' } }` if the hard timeout fires.
  - `400 { error: { code: 'INVALID_REQUEST', message: '...' } }` for a malformed body (missing/invalid `difficulty`, etc.) — use Zod for this validation (the project's one runtime validation library, per `AGENTS.md`) even though this package has never used it before; add it as a new dependency.
  - `500 { error: { code: 'ENGINE_ERROR', message: '...' } }` for any other engine-side failure.

## Required tests

Unit tests (no real engine needed) for `difficulty.ts`'s `selectMove`: given a fixed `random` sequence, assert the exact move chosen for each difficulty, including the threshold-filtering boundary (a candidate exactly at the threshold edge, one just outside it) and the medium-difficulty weight boundaries (force `random()` to return values that land in each of the 50/35/15 bands and assert the corresponding pick).

Unit tests for the pool/queue (mock `EngineProcess`, don't spawn a real binary) covering: a request queues when all engines are busy and is served once one frees up; the queue rejects once at `QUEUE_CAP`; a request that exceeds its timeout causes that engine to be disposed and replaced, and the NEXT request to that pool slot succeeds against the fresh instance.

Live test (guarded by `describe.skipIf(!process.env.PIKAFISH_PATH)`, same pattern as the existing `live.smoke.test.ts`): `searchMultiPv` against the real binary at `movetime: 200, multiPv: 3` from the start position returns 3 distinct legal moves with sensibly-ordered scores (line 1's score ≥ line 2's ≥ line 3's, from the side-to-move's perspective).

HTTP-level test for `/bestmove`/`/health`/`/metrics` using mocked `EngineProcess`es (no real binary needed) — spin the actual HTTP server on an ephemeral port and hit it with a real HTTP client (same pattern `game.gateway.test.ts` used for a real Socket.IO server/client pair), confirming the request/response shapes above.
