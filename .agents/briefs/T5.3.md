# Brief: T5.3 — API `AiModule`: untimed AI games

## Goal

Lets a human play an untimed game against the Pikafish worker (T5.1). A new module creates AI games, listens for the existing `'game.updated'` domain event (already emitted by `GamesService.submitMove`/`resign`/`drawOffer` since T4.2) to notice when it's the engine's turn, calls T5.1's worker over plain HTTP, and resubmits the engine's move through `GamesService.submitMove`'s EXISTING validated pipeline — the engine is never trusted directly, exactly like every other move source in this codebase. Falls back to a capture-preferring random legal move if the worker errors, times out, or (defensively) returns something `submitMove` itself rejects.

## Design

### Schema addition

```prisma
enum AiDifficulty {
  EASY
  MEDIUM
  HARD
}
```

Add one nullable field to the EXISTING `Game` model: `aiDifficulty AiDifficulty?`. `null` for every non-AI game; set once at creation for an AI game, never changes.

### `AiService.createAiGame(humanId: string, humanColor: 'red' | 'black', difficulty: 'easy' | 'medium' | 'hard'): Promise<{ gameId: string }>`

- Resolve which of `redId`/`blackId` is the human (per `humanColor`) and which is `null` (the engine's seat) — exactly the same shape `GamesService.createGame` already accepts (it already supports a `null` player id, used today for... actually check: if neither `RoomsService` nor any existing caller has ever passed `null` for a REAL game before, this may be new territory — read `createGame`'s current implementation carefully to confirm it doesn't assume both ids are non-null anywhere before you rely on this).
- `createGame(STARTING_FEN, null, redId, blackId)` — `null` time control (untimed). Store the Prisma column's `aiDifficulty` on this same row (you may need to extend the create call's `data` directly via a follow-up `prisma.game.update`, OR check whether `GamesService.createGame` would need a new optional parameter to set it atomically at creation — your call, but keep `GamesService` itself untouched per Forbidden above, so lean towards a follow-up update from THIS module rather than threading a new parameter through the shared service).
- `activateGame(gameId)`.
- If the human is BLACK, the engine (RED) must move first — trigger the SAME engine-move logic described below immediately after activation, don't wait for a `'game.updated'` event that will never fire until a move happens.

### `@OnEvent('game.updated')` handler

On every event: fetch `getSnapshot(gameId)`. If `game.aiDifficulty` is null (not an AI game — you'll need a way to check this; `getSnapshot`'s current return shape doesn't include it, so either extend what you fetch here with a direct `prisma.game.findUnique` for just this field, or note in QUESTIONS if you think `GameSnapshot` itself should gain this field — your call, but prefer the narrower direct-query approach since this is AI-module-internal bookkeeping, not something the client needs to see), do nothing. If `snapshot.status !== 'ACTIVE'`, do nothing (game over). Otherwise, determine whose turn it is from `snapshot.moves.length` parity and the stored `redId`/`blackId` (whichever is `null` is the engine's seat) — if the seat to move isn't the engine's, do nothing (it's the human's turn, wait for their move to trigger the next event).

If it IS the engine's turn: call the worker (see below), get a move, resubmit via `submitMove(gameId, { color: engineColor, moveId: crypto.randomUUID(), expectedVersion: snapshot.gameVersion, move: decodeMove(theMove) })`. If that resubmission itself gets rejected (version conflict from a race, or the fallback path below also somehow fails) — log it and return; don't retry in an infinite loop. A human move landing moments later will fire another `'game.updated'` event and this handler runs again from fresh state anyway.

### Worker call + fallback

```ts
async function requestEngineMove(fen: string, moves: string[], difficulty: Difficulty): Promise<string> {
  // POST to process.env.PIKAFISH_WORKER_URL + '/bestmove', { fen, moves, difficulty }
  // on any failure (non-2xx, network error, malformed response), fall through to the fallback below
}
```

Fallback — a capture-preferring random legal move, computed locally with `@xq/xiangqi-core` (no engine involved at all):

```ts
function fallbackMove(position: Position): Move {
  const legal = getAllLegalMoves(position, position.turn);
  const captures = legal.filter((move) => position.board[squareToIndex(move.to)] !== null);
  const pool = captures.length > 0 ? captures : legal;
  return pool[Math.floor(Math.random() * pool.length)]!;
}
```

(Exact signature/helper names your call — the behavior is what matters: prefer any move that captures a piece, picked uniformly at random among captures if any exist, else uniformly at random among all legal moves. A position with ZERO legal moves shouldn't reach this function at all — the game would already be over per ADR-017 and the `'game.updated'` handler's own `status !== 'ACTIVE'` check above would have already returned early.)

Call the worker FIRST; only use the fallback if that call fails for any reason (network error, non-2xx status, or — defensively — if `submitMove` itself rejects the engine's returned move as illegal, which should never happen if T5.1's worker is working correctly, but don't trust it blindly: if the resubmission comes back `rejected` with reason `ILLEGAL_MOVE`, retry ONCE with the fallback move before giving up for this turn).

## Required tests

- The `'game.updated'` listener: does nothing for a non-AI game; does nothing when it's the human's turn; calls the worker and resubmits its move when it's the engine's turn (assert the resubmitted move via a real `GamesService.submitMove` call against the test DB, same integration-test pattern `games.service.integration.test.ts`/`clock-scheduler.service.test.ts` already use).
