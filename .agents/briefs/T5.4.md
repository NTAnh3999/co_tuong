# Brief: T5.4 — `/play/ai` page

## Goal

A page where a human picks a color and difficulty, creates an AI game via T5.3's `POST /games/ai`, and plays it. The actual gameplay UI is NOT new — `/game/[id]` (built in T4.6/T4.7) already renders any game by id using `OnlineGameController`, and an AI game's engine move arrives through the exact same socket/REST path a human opponent's move would (T5.3's `AiService` calls the same `GamesService.submitMove` every other move source uses). So this task is a small picker page that creates the game and redirects — it does NOT touch `/game/[id]` or its controller at all.

- `apps/web/app/game/[id]/page.tsx` — read it to CONFIRM (don't just assume) that it needs zero changes for an AI game: specifically, `myColor` is derived from `snapshot.redPlayerId === userId || snapshot.blackPlayerId === userId`, both nullable in `GameSnapshot` — an AI game's engine seat is `null` in the DB, so this comparison naturally resolves to the human's actual color with no special-casing needed. - `apps/web/src/features/session/use-session.ts` — the existing session hook (`useSession()`) every other page uses to get the current user before calling an authenticated endpoint.

## Design

A simple picker form, modeled on `/play/online/page.tsx`'s shape:

```tsx
'use client'
// pick color: red | black (radio buttons or two tappable cards)
// pick difficulty: easy | medium | hard (radio buttons or three tappable cards), default 'medium'
// on submit: const { gameId } = await apiClient.createAiGame({ color, difficulty })
//            router.push(`/game/${gameId}`)   // NOTE: no ?room= query param — this isn't a room game
```

- Use `useSession()` the same way `/play/online` does: show a loading state while the session resolves, an error state if it fails, and only render the form once a real user is available.
- Vietnamese labels for the color/difficulty choices (e.g. "Đỏ" / "Đen" for color; "Dễ" / "Vừa" / "Khó" for difficulty — match whatever terms `/play/online` or other pages already use for similar choices, for consistency, rather than inventing new wording).
- On a failed `createAiGame` call (network error, validation error), show an inline error message and let the user retry — don't crash the page.
- Reuse `Button`/`LoadingState`/`ErrorState` from `@/components/ui/button` and `@/src/components/states/*` the same way other pages do, rather than writing new primitives.

## Required tests

`apps/web/app/play/ai/page.test.tsx`, same testing approach `/play/online/page.test.tsx` already uses (mock `apiClient`, mock `useSession`/`next/navigation`'s router):
- Renders the color/difficulty pickers once the session resolves.
- Submitting calls `apiClient.createAiGame` with the selected `{ color, difficulty }` and navigates to `/game/<returned gameId>` (assert the exact pushed path, including that it has NO `?room=` query string).
- A failed `createAiGame` call shows an error message and does not navigate.
