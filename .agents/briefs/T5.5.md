# Brief: T5.5 — Live adapter test vs. the real Pikafish binary

## Goal

Every test so far for `services/pikafish-worker` (`uci/commands.test.ts`, `pool.test.ts`, `server.test.ts`, `difficulty.test.ts`) runs against either a scripted fake UCI process or pure in-memory logic — none of them actually launch the real Pikafish engine and parse its real output. This task adds ONE test file that does, so the MultiPV-parsing code (`searchMultiPv` in `src/uci/commands.ts`, added in T5.1) is verified against the real engine's actual UCI protocol output, not just a script written to match our own assumptions about that format.

## Acceptance-criteria IDs

CORE-06, AI-01

## Read first

- `services/pikafish-worker/src/uci/commands.test.ts` — the EXISTING pattern for spawning a UCI engine process and talking to it (currently only against scripted fake processes). Your new test reuses the real `EngineProcess`/`initEngine`/`searchMultiPv` functions, just points them at a real binary instead of a fake script.
- `services/pikafish-worker/src/pool.ts` and `src/server.ts` — the full worker stack (`EnginePool`, HTTP server) your test will exercise end-to-end over real HTTP, not just the low-level UCI client.
- `services/pikafish-worker/src/difficulty.ts` — `DIFFICULTY_PROFILES`'s exact movetimes (easy 50ms, medium 200ms, hard 1000ms) — your test's timeouts need headroom above these, not below.

## Design

The test file must be a complete no-op in any environment without the real engine available — this is what makes it safe to run in CI/Codex's sandbox (which has neither) while still being real and meaningful on the orchestrator's machine (which has both).

```ts
import { describe, it, expect } from 'vitest';
import { EnginePool } from './pool.js';
import { createServer } from './server.js';
// (adjust import names/paths to match T5.1's actual exports — read pool.ts/server.ts
// first rather than guessing signatures)

const PIKAFISH_PATH = process.env.PIKAFISH_PATH;

describe.skipIf(!PIKAFISH_PATH)('live Pikafish adapter (CORE-06, AI-01)', () => {
  // Use PIKAFISH_PATH! (non-null, guarded by skipIf above) as the real engine binary.
  // ...
});
```

Required cases inside that `describe` block (all against the REAL binary, no mocks):

1. **Raw UCI round-trip**: spawn a real `EngineProcess` at `PIKAFISH_PATH!`, run `initEngine`, then `searchMultiPv` with a small `movetimeMs` (e.g. 100ms) and `multiPv: 3` from the standard starting position. Assert you get back exactly 3 lines (or fewer if the position has fewer legal moves — it won't, from the start position, so assert exactly 3), each with a valid-looking UCI move (regex `^[a-i][0-9][a-i][0-9]$`) and a numeric `scoreCp`, sorted ascending by `multipv` index as `searchMultiPv`'s contract promises.
2. **Full pool → difficulty round-trip**: start a real `EnginePool` (pool size 1 is enough) pointed at `PIKAFISH_PATH!`, submit one job per difficulty (`easy`/`medium`/`hard`) from the starting position, and for each assert the returned move is syntactically valid UCI and the move is actually in `getAllLegalMoves(startPosition, 'red')` from `@xq/xiangqi-core` (import the real rules engine and cross-check — don't just assert "a string came back", prove the real engine's move is actually legal per our own rules implementation, since that's the property T5.3's `AiModule` depends on completely). Close the pool when done (`await pool.close()` or whatever T5.1's actual shutdown method is named — check it).
3. **Full HTTP round-trip**: start the real `server.ts` HTTP server (on an ephemeral port, same pattern `server.test.ts` already uses for its port allocation) backed by a real pool pointed at `PIKAFISH_PATH!`, `POST /bestmove` with `{ fen: <starting position FEN>, difficulty: 'easy' }`, assert `200` and a legal move in the JSON body (cross-check legality the same way as case 2). Shut the server and pool down afterward.

Use a generous `it(..., { timeout: ... })` per case (several seconds) since spawning a real engine process and letting it think is slower than the mocked tests — don't let a tight default timeout make this flaky on a slower machine.

## Required tests

This task's entire deliverable IS the test file described above — there's no separate "write code, then test it" split. The three cases above are the three `it(...)` blocks required.
