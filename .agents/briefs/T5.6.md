## Design

### Dockerfile (multi-stage)

1. **Builder stage**: a Node 22 image (match the engines constraint already declared in this monorepo's package.json files — check one, e.g. `apps/api/package.json`'s `"engines"` field, for the exact major version expected). Copy the whole monorepo (or just what `services/pikafish-worker` needs via pnpm's workspace — your call on the most efficient COPY set, but correctness over cleverness: if in doubt, copy more rather than risk a missing file breaking the build), run `corepack enable` + `pnpm install --frozen-lockfile` + `pnpm --filter @xq/pikafish-worker build` (matching this repo's actual package manager/version — check the root `package.json`'s `packageManager` field for the exact pnpm version to pin via corepack).
2. **Download+verify stage** (can be the same stage as the builder, or separate — your call): download the 7z archive from the pinned URL (use `curl` or `wget`, whichever the base image has or you install), verify its SHA-256 against the pinned value above (`sha256sum` + a shell comparison, or `echo "<hash>  <file>" | sha256sum -c -`), FAIL THE BUILD LOUDLY if the checksum doesn't match (don't silently continue with an unverified binary). Extract it (you'll need a `7z`/`p7zip` tool available in this stage — install via the base image's package manager) and locate the Linux x86-64 binary and the `.nnue` weights file inside the extracted tree (the archive's internal layout should mirror what's in the orchestrator's local `tools/pikafish/` copy — multiple platform binaries plus one shared `pikafish.nnue` — but confirm the ACTUAL internal paths once you've extracted it in your own build, rather than assuming they match exactly).
3. **Runtime stage**: a slim Node 22 base image. Copy the built `dist/` output (and `node_modules` — production deps only, via `pnpm deploy` or an equivalent prune step, your call on the exact mechanism as long as the final image doesn't carry the whole monorepo's `node_modules`) from the builder stage. Copy the verified Pikafish binary + NNUE file + the three license files (`Copying.txt`, `NNUE-License.md`, `AUTHORS`, extracted from the SAME downloaded archive — the archive bundles these per the orchestrator's local copy; if your extraction doesn't find them bundled, download them as separate assets from the SAME pinned release/tag instead, don't substitute a different source) from the download+verify stage. Create a non-root user and run the service as that user (`chmod +x` the binary, ensure the user can read the `.nnue` file). Set `PIKAFISH_PATH` to the binary's final in-image path as an `ENV`. `EXPOSE` the port (default 4000). `CMD ["node", "dist/index.js"]` (or whatever the package's actual `start` script resolves to — check it rather than hardcoding a guess).

### `.dockerignore`

Standard exclusions (`node_modules`, `dist`, `.git`, etc.) — keep the build context small.

### `docker-compose.dev.yml` addition

```yaml
  pikafish-worker:
    build:
      context: ../..
      dockerfile: services/pikafish-worker/Dockerfile
    container_name: xq_pikafish_worker_dev
    environment:
      PORT: 4000
      POOL_SIZE: 2
      QUEUE_CAP: 20
    ports:
      - '4000:4000'
    deploy:
      resources:
        limits:
          cpus: '2'
          memory: 1g
    healthcheck:
      test: ['CMD', 'node', '-e', "require('http').get('http://localhost:4000/health', (r) => process.exit(r.statusCode === 200 ? 0 : 1)).on('error', () => process.exit(1))"]
      interval: 10s
      timeout: 5s
      retries: 5
```

(`deploy.resources.limits` only actually enforces under Swarm mode in plain `docker compose` — if you know a `docker compose`-native equivalent for the Compose Specification version this file targets that DOES enforce limits outside Swarm, e.g. `cpus`/`mem_limit` as top-level service keys, use that instead; check what Compose Specification version this file is implicitly targeting and use whichever form actually works for plain `docker compose up`, not just the Swarm-only form shown above as a starting point.)
