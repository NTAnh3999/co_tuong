# Brief: T6.1 — `packages/content`: schemas, loader, validator, seed, Prisma tables

## Goal

The foundation every other M6 task builds on: typed content authoring for lessons and puzzles, a validator that actually replays every authored line through the real rules engine (not just schema-shape checking), and the Prisma tables + seed script that get authored content into the database for the REST layer (T6.7) to serve.

## Design

### Content file format

One JSON file per lesson/puzzle under `packages/content/data/lessons/*.json` and `packages/content/data/puzzles/*.json` (plain JSON, not Markdown+frontmatter — keeps the Zod-validation story simple with no new parsing dependency; prose fields inside the JSON can contain Markdown strings where the UI wants rich text, e.g. `objective`, hint text, lesson step captions).

### Zod schemas (`src/schema.ts` or similar)

```ts
export const puzzleSchema = z.object({
  id: z.string(),              // stable slug, also the Prisma id
  title: z.string(),
  objective: z.string(),        // markdown
  difficulty: z.number().int().min(1).max(5),
  initialFen: z.string(),
  sideToMove: z.enum(['red', 'black']),
  solutionLines: z.array(z.array(z.string())).min(1),       // each inner array: a full alternating UCI move sequence starting with the attacker's key move
  allowedAlternatives: z.array(z.array(z.string())).default([]),
  hints: z.array(z.string()).max(3),
  source: z.string(),
  contentVersion: z.number().int().default(1),
});

export const lessonSchema = z.object({
  slug: z.string(),
  title: z.string(),
  level: z.enum(['beginner', 'intermediate', 'advanced']),
  contentVersion: z.number().int().default(1),
  steps: z.array(z.object({
    fen: z.string(),
    caption: z.string(),        // markdown explanation shown with this step's board position
    highlightSquares: z.array(z.string()).default([]), // ADR-018 squares to visually emphasize, optional
  })).min(1),
});
```

(Exact shape is your call within these constraints — the fields above are the minimum every later M6 task needs; don't drop any of them, adding more is fine if well-justified.)

Moves are plain 4-character UCI strings (`"h2e2"`), not `{from,to}` objects — matches ADR-018 and every other place this codebase encodes a move as a string (`GameMove.uci`, socket payloads). Decode with `@xq/xiangqi-core`'s `decodeMove` wherever you need the structured form (e.g. to call `applyMove`).

### Loader (`src/loader.ts` or similar)

`loadLessons(): Lesson[]` / `loadPuzzles(): Puzzle[]` — read every `*.json` file in the respective `data/` directory, parse with the Zod schema (throw with the filename included in the error if one fails), return the validated array. Keep this synchronous and side-effect-free (no DB access here — this is pure file-system content loading, reused by both the validator and the seed script below).

### Validator (`content:validate` script + `package.json` script)

For every loaded puzzle: `fromFen(initialFen)`, then for EACH line in `solutionLines` AND `allowedAlternatives`: replay it move-by-move via `decodeMove`/`isLegalMove`/`applyMove`, asserting every move is legal in its turn and that `position.turn` alternates correctly starting from `sideToMove`. Fail loudly (exit non-zero, print which puzzle/line/ply failed) on any illegal move — this is the whole point of this task: a schema-valid-but-chess-illegal puzzle must be caught before it ever reaches a human player.

For every loaded lesson: `fromFen(step.fen)` for every step, just confirming each FEN parses (a lesson's steps aren't necessarily a legal game continuation of each other — each step can be an independently-set-up illustrative position — so there's no move-replay to validate here, just FEN validity).

Wire this as `"content:validate": "tsx src/validate.ts"` (or whatever the actual script path is) in `package.json`, and also run it as part of this task's own test suite (a vitest test that imports and calls the same validation function against the fixture content you added) so the gate command below actually exercises it.

### Prisma additions

```prisma
enum LessonLevel {
  BEGINNER
  INTERMEDIATE
  ADVANCED
}

enum LearningContentType {
  LESSON
  PUZZLE
}

enum LearningProgressStatus {
  IN_PROGRESS
  COMPLETED
}

model Lesson {
  id             String      @id @default(cuid())
  slug           String      @unique
  title          String
  level          LessonLevel
  contentVersion Int         @default(1)
  bodyJson       Json        // the validated Lesson's `steps` array
  createdAt      DateTime    @default(now())
}

model Puzzle {
  id                  String   @id @default(cuid())
  title               String
  objective           String
  difficulty          Int
  initialFen          String
  sideToMove          Color    // reuse the EXISTING Color enum, don't add a new one
  solutionJson        Json     // the validated Puzzle's `solutionLines`
  allowedAlternatives Json     // the validated Puzzle's `allowedAlternatives`
  hints               Json     // string[]
  source              String
  contentVersion      Int      @default(1)
  createdAt           DateTime @default(now())
}

model LearningProgress {
  id          String                  @id @default(cuid())
  userId      String
  user        User                    @relation(fields: [userId], references: [id])
  contentType LearningContentType
  contentId   String                  // the Lesson.id or Puzzle.id, deliberately not a real FK since it can point to either table
  status      LearningProgressStatus
  attempts    Int                     @default(0)
  completedAt DateTime?
  updatedAt   DateTime                @updatedAt

  @@unique([userId, contentType, contentId])
}
```

(You'll need to add `gameMoves... learningProgress LearningProgress[]` or similar back-relation on `User` — follow the existing pattern for how `User` relates to its other owned rows.)

Generate the migration against the real dev Postgres the same way T3.2 did (the orchestrator has Docker Compose's `xq_dev`/`xq_test` databases available; if your sandbox can't reach Postgres, write the migration SQL by hand following Prisma's own generated style as closely as possible and say so plainly in KNOWN GAPS — the orchestrator will regenerate it properly against a real database if your hand-written version doesn't match what `prisma migrate dev` would produce).

### Seed script

`"content:seed": "tsx src/seed.ts"` — loads validated lessons/puzzles via the loader (re-validating first; refuse to seed anything that fails `content:validate`'s checks) and upserts each into the `Lesson`/`Puzzle` tables by their stable `slug`/`id`. Idempotent — running it twice with the same content produces the same rows, not duplicates.

## Required tests

- Loader: loads the fixture lesson(s)/puzzle(s) you add, matching the Zod schema.
- Validator: a fixture puzzle with a deliberately illegal move in `solutionLines` is rejected with a clear error identifying which file/line/ply; a fixture puzzle with a fully legal line passes; same pair of cases for a lesson's FEN validity.
- Zod schema: rejects a puzzle with more than 3 hints, a difficulty outside 1–5, etc. (a few representative boundary cases, not exhaustive).
