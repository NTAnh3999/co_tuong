# Brief: T6.2 — Mate-in-N solver for puzzle authoring

## Goal

A content-authoring-time tool (not a runtime game feature) that, given a position and a claimed "mate in N" (N≤3 full moves), verifies: (a) the attacker (side to move) can force checkmate within exactly N of their own moves against EVERY possible defense, and (b) the FIRST move of that forced line — the "key move" — is unique (no other first move also forces mate within N). This is what makes T6.4's authored puzzles trustworthy without a human having to hand-verify every line against every possible defense.

Lives in `packages/content` (a puzzle-authoring concern, not a rule the live game engine needs — `packages/xiangqi-core` stays free of this).

## Read first

Confirm `getAllLegalMoves`'s actual exported name and signature by reading the file — don't guess.
- ADR-017 (`docs/adr/ADR-017-ruleset-casual-v1.md`) — under this ruleset, a side with ZERO legal moves on their turn has LOST, full stop (no stalemate-as-draw). This means "checkmate" and "no legal moves" are the same detection: `getAllLegalMoves(position).length === 0` when it's that side's turn. You do not need to separately check "is the king actually in check" — the ruleset doesn't distinguish checkmate from a hypothetical stalemate, they're both just a loss.
- T6.1's brief (`.agents/briefs/T6.1.md`) for the exact shape `solutionLines`/`allowedAlternatives` use (`string[][]`, UCI 4-char moves, each inner array a full alternating sequence starting with the attacker's move) — this task's solver's input/output should speak the same representation so T6.4's content-authoring loop (run the solver, paste its output into a puzzle's `solutionLines`) is friction-free. If T6.1 hasn't landed yet when you start, this shape is already fully specified in its brief regardless — build to it.

## The exact recursive definition (implement this, don't invent a variant)

"The side to move can force mate in exactly `n` of their own moves from position `p`" — call this `canForceMateIn(p, n)`:

- If `n < 1`: false.
- For each legal move `m` available to the side to move in `p`:
  - Let `p1 = applyMove(p, m)`.
  - If `n === 1`: `m` succeeds iff the OTHER side now has zero legal moves in `p1` (immediate loss per ADR-017, see above).
  - If `n > 1`: `m` succeeds iff, for EVERY legal reply `d` available to the other side in `p1` (if there are zero replies, the mate already happened early — that does NOT count as succeeding at "exactly n", see the "exactly N, not sooner" note below), `canForceMateIn(applyMove(p1, d), n - 1)` is true.
- `canForceMateIn(p, n)` is true iff at least one move `m` succeeds.

### "Exactly N, not sooner"

A well-formed "mate in N" puzzle should not ALSO be mate-in-(N-1) or faster (otherwise calling it "mate in N" is misleading, and more importantly a human solver playing the "correct" N-move line might get told their move was wrong if a faster mate was also available and the puzzle's own `solutionLines` don't account for it). Implement `isExactMateInN(p, n): boolean` = `canForceMateIn(p, n) && !canForceMateIn(p, n - 1)` for `n ≥ 2` (for `n === 1`, there's no faster case to exclude — it just is or isn't immediate mate).

### Unique key move — ROOT ONLY

"The key move is unique" means: among all of the side-to-move's legal moves in the STARTING position `p`, EXACTLY ONE of them succeeds per the recursive definition above for the claimed `n`. This uniqueness requirement applies ONLY to the first move. From ply 2 onward (the attacker's 2nd, 3rd, ... move within the forced line), there can legitimately be multiple moves that all still force the mate — that's exactly what a puzzle's `allowedAlternatives` field (see T6.1) is for. Do not require uniqueness at every ply, only at the root.

## Design

```ts
export interface SolveMateResult {
  readonly solved: boolean;
  readonly keyMoves: string[];     // UCI moves at the root that succeed for this n (length 0, 1, or >1)
  readonly isUnique: boolean;      // keyMoves.length === 1
  readonly lines: string[][];      // for each key move, ONE full forced line as a worked example (your call on which defense to pick when the defender has multiple losing replies — picking the first one `getAllLegalMoves` returns is fine, it's illustrative, not exhaustive)
}

export function solveMateInN(fen: string, n: number): SolveMateResult;
```

`solveMateInN` ties together `isExactMateInN` per the root's legal moves: for each root move `m`, check whether `m` itself succeeds under the n-ply recursive definition (not `isExactMateInN` on the position AFTER `m` — you're checking "does THIS move force mate in the remaining n-1 against every reply", which is the inner loop of `canForceMateIn`, so you'll likely want to factor out a `moveForcesMateIn(positionAfterMove, remaining): boolean` helper that both `canForceMateIn` and the key-move enumeration call). `solved` is true iff `canForceMateIn(fromFen(fen), n)` is true for the ORIGINAL starting position with the ORIGINAL `n` (i.e., at least one key move exists — don't apply the "exactly N, not sooner" check to `solved` itself, apply it when deciding whether a given `n` claim is well-formed, which is a judgment call for whoever authors the puzzle, not baked into this function's `solved` field — keep `solveMateInN` purely descriptive: what moves force mate in n, are they unique, here's a sample line each).

Reasonable performance ceiling: `n ≤ 3` against curated puzzle positions (few remaining pieces, as mate puzzles typically are) should run in well under a second. If you find a pathological case that's slow, a simple memoization keyed by FEN+remaining-n is a reasonable addition — don't over-engineer a full transposition table, this isn't a general-purpose chess engine.

## Required tests

- A textbook mate-in-1 position (construct one by hand, or derive one — verify it by hand-tracing, don't just trust your own solver's output as ground truth for the FIRST test case) → `solved: true`, exactly one key move, `isUnique: true`.
- A position with TWO different moves that both deliver immediate mate-in-1 → `isUnique: false`, `keyMoves.length === 2`.
- A constructed mate-in-2 or mate-in-3 position where the defender has a choice of replies at some point, and the solver confirms the key move holds against ALL of them, not just the first reply tried.
- A position that is NOT mate-in-n for the claimed n (either no forcing line exists, or the real mate is faster than claimed) → `solved: false` for the wrong `n`, and `isExactMateInN` correctly flags the "too slow a claim" case using a position that actually mates faster than claimed.
- A plain non-mating position (e.g. the start position, `n: 1`) → `solved: false`.
