# Brief: T6.5 — Web `PuzzleController` + `/puzzles`, `/puzzles/[id]`

## Goal

A puzzle-solving page per `docs/ux/lowfi.md` §3's wireframe: load a puzzle, let the player click-to-move exactly like the live game board, check each move against the puzzle's solution (position-based, allowing transpositions — not literal move-string matching), track hints/retries, and record progress server-side once solved.

## Design

### `PuzzleController`

```ts
export interface PuzzleControllerState {
  readonly position: Position;
  readonly selectedSquare: Square | null;
  readonly legalTargets: readonly Square[];   // from REAL getLegalMoves, same as LocalGameController — the player
                                               // can attempt ANY legal move, not just ones in the solution
  readonly history: readonly Move[];          // moves accepted so far in this attempt
  readonly status: 'in_progress' | 'solved';
  readonly lastMoveWasWrong: boolean;         // transient flag for showing "Sai nước. Thử lại." — clears on the next action
  readonly hintsRevealed: number;              // 0..hints.length
}

export interface PuzzleController {
  getState(): PuzzleControllerState;
  subscribe(listener: () => void): () => void;
  selectSquare(square: Square | null): void;
  requestHint(): void;
  retry(): void;
}

export function createPuzzleController(puzzle: PuzzleDetail): PuzzleController { ... }
```

- Board interaction mirrors `createLocalGameController` exactly: clicking your own piece selects it and shows `getLegalMoves` targets; clicking a legal target submits that move.
- **Solution matching is position-based** (per the lowfi doc's explicit note: "Position-based, not move-by-move string matching (allow transpositions if position equivalent)"). Precompute, for every line in `solutionLines` and `allowedAlternatives`, the full sequence of positions reached by applying that line's moves from `initialFen` (decode each UCI move, apply it in order — same technique `replay()` uses internally, though you don't need to import `replay()` itself since these lines aren't `Move[]` from a `GameRecord`, they're raw UCI strings you decode yourself). When the player submits a real legal move at ply depth `d` (i.e. `history.length` was `d` before this move), compute the resulting position and check: does it exactly equal (same FEN, ignoring the move-count suffix) the position at depth `d+1` of ANY solution/alternative line? If yes: accept the move (push to `history`, clear `lastMoveWasWrong`), and if `d+1` equals that matching line's full length, set `status: 'solved'`. If no match: this is a legal chess move but the WRONG one for the puzzle — **do not apply it to `position`/`history`** (reject it, same as how `LocalGameController.submitMove` returns `false` and the UI stays put for an actually-illegal move), just set `lastMoveWasWrong: true` and clear the selection, so the player tries again from the same position. (This is a reasonable, documented interpretation of the lowfi doc's "don't reset board, let them continue" — it means "don't force a full retry-to-initialFen reset," not "let a wrong move stand on the board." If you disagree after reading the doc yourself and have a clear reason, you may implement it differently — just say so plainly in KNOWN GAPS, don't silently diverge.)
- `requestHint()`: increments `hintsRevealed` by 1, capped at `hints.length`. The actual hint TEXT to display (`puzzle.hints[hintsRevealed - 1]`) is read by the page component from the puzzle data using the controller's `hintsRevealed` count — the controller itself doesn't need to store the hint text.
- `retry()`: resets `position` to `fromFen(initialFen)`, clears `history`, clears `lastMoveWasWrong`, resets `status` to `'in_progress'`. Your call whether `hintsRevealed` also resets on retry (the lowfi doc's wording is ambiguous — simplest and recommended: reset it too, so a retry is a genuinely clean restart; note whichever you pick).

### `/puzzles` page

- `apiClient.getPuzzles()` once on mount (no `useSession()` gating needed beyond what the other pages already do for an authenticated call — follow `/history`'s pattern). Render each as a row (title + difficulty badge, e.g. a simple "⭐" × difficulty or a plain number) linking to `/puzzles/<id>`.
- Loading/error/empty states via the existing shared components.

### `/puzzles/[id]` page

- `params: Promise<{ id: string }>` (Next 15 convention).
- `apiClient.getPuzzle(id)` once on mount → `createPuzzleController(puzzle)`, subscribed via `useSyncExternalStore`.
- Also fetch `apiClient.getPuzzles()` (the full list) once, to determine which puzzle comes "next" after this one (by array order) for the "Puzzle tiếp theo →" button — disabled until `status === 'solved'`, and simply absent/disabled if this is the last puzzle in the list.
- Render per the wireframe: title, difficulty badge, objective box, `Board2D` (interactive — reuse it with `onSquareClick`/`onMove` wired to the controller's `selectSquare`, same as `/play/local` already does), hint button ("Gợi ý (còn N lượt)" — show the remaining count `hints.length - hintsRevealed`, disabled once exhausted), retry button, a status line (wrong-move message when `lastMoveWasWrong`, or a solved confirmation), and a source/author footer line from `puzzle.source`.
- **On first reaching `status === 'solved'`** (not on every render after — call this exactly once per solve, e.g. via a `useEffect` keyed on the transition), call `apiClient.recordPuzzleAttempt(id, { completed: true, hintsUsed: <hintsRevealed at solve time> })`. A failed call here shouldn't block the player from seeing "solved" — log/swallow it or show a small non-blocking note, your call, but don't let a network hiccup hide the fact that they solved it.
