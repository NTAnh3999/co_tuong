# Brief: T6.8 — Web `ReplayController` + `/history`, `/history/[id]`

## Goal

Two pages: `/history` lists the current user's past games (via T6.7's newly-exposed `GET /me/games`), and `/history/[id]` replays one game ply-by-ply, proving that jumping to any ply reconstructs the exact position the server actually played (REPLAY-01) — not just "the UI looks plausible."

## Acceptance-criteria IDs

REPLAY-01, DATA-01

## Read first

- `apps/web/src/features/game/controller/game-controller.ts` — the existing `GameController` interface (`getState()`/`subscribe()` pattern every controller in this codebase follows, driven into React via `useSyncExternalStore`). Your new `ReplayController` is NOT this interface (replay has no move submission, selection, or legality — it's pure ply navigation), but follows the SAME subscribe/getState shape for consistency with how every other page wires a controller into React.
- `apps/web/src/features/game/controller/local-game-controller.ts` — a concrete, in-memory, no-server-calls controller implementation (closest existing analog to what you're building — a replay controller is also purely local state once it has the game's moves).
- `@xq/xiangqi-core`'s `replay()` function (already used by `apps/web/app/game/[id]/page.tsx`'s `useCapturedPieces` — read that usage) — given `{ initialFen, moves, ruleSetVersion }`, returns one step per ply with the resulting position. This is EXACTLY what reconstructs "the state after ply N," and it's the same function the live game page already trusts, so there's no new replay logic to invent.
- `packages/api-client/src/index.ts`'s `getMyGames()` and `getGame(id)` methods (both already exist — `getMyGames` from T6.7, `getGame` from T3.7/T3.9). `getGame(id)` returns the FULL `GameSnapshot` including `initialFen` and the complete `moves: string[]` array — that's everything needed to replay a finished game in one call; you do not need `getGameMoves`'s paginated endpoint for this task.
- `apps/web/src/features/game/board/Board2D.tsx`'s props — it already supports a fully read-only/non-interactive mode (`interactive: false` with no-op click/move handlers), which is exactly what a replay view needs. Reuse it directly rather than building a second board renderer.
- `apps/web/app/play/online/page.tsx` or `apps/web/app/game/[id]/page.tsx` — for the `useSession()` + loading/error-state conventions every authenticated page already follows.

## Design

### `ReplayController`

```ts
export interface ReplayStep {
  readonly position: Position;        // from @xq/xiangqi-core
  readonly lastMove: Move | null;      // null for ply 0 (the initial position)
}

export interface ReplayControllerState {
  readonly steps: readonly ReplayStep[];   // steps[0] is the initial position, steps[i] is after ply i
  readonly currentPly: number;             // 0..steps.length-1
  readonly result: GameResult | null;
}

export interface ReplayController {
  getState(): ReplayControllerState;
  subscribe(listener: () => void): () => void;
  goToPly(ply: number): void;   // clamp to [0, steps.length-1]
  next(): void;
  previous(): void;
}

export function createReplayController(game: GameSnapshot): ReplayController { ... }
```

Precompute every step up-front from `game.initialFen`/`game.moves` via `replay()` (same call shape `useCapturedPieces` already uses) — a finished game's move count is small (well under a thousand plies), so there's no reason to compute lazily. `goToPly`/`next`/`previous` just move `currentPly` and notify subscribers; they never touch the network or mutate `steps`.

### `/history` page

- `useSession()` for the current user; `apiClient.getMyGames()` once on mount.
- Render a list: for each game, the opponent's nickname (or "Máy" / an AI-appropriate label if `opponent` is `null` — this is also how an AI game will show up, since the engine's seat has no human opponent), status, and result if finished. Each row links to `/history/<gameId>`.
- Loading/error/empty states via the existing `LoadingState`/`ErrorState` components (empty: no games yet — a plain message, not an error).

### `/history/[id]` page

- `params: Promise<{ id: string }>` (Next 15 convention — same as `/game/[id]`).
- `apiClient.getGame(id)` once on mount → `createReplayController(snapshot)`.
- `useSyncExternalStore` to subscribe, same pattern every other controller-driven page uses.
- Render `Board2D` with `interactive={false}`, `position={state.steps[state.currentPly].position}`, `lastMove={state.steps[state.currentPly].lastMove}`, a fixed orientation (`'red'` is fine — there's no "my color" in a replay of someone else's finished game unless the viewer played in it; using the viewer's actual color if they were a participant is a nice touch but not required).
- A ply stepper: previous/next buttons plus either a slider or a numbered list of plies to jump directly to any ply (satisfies "jump to any ply," not just "step one at a time").
- Show the final result (if any) alongside the board.

## Required tests

- `replay-controller.test.ts`: given a small fixture `GameSnapshot` (initial FEN + a short real legal move list — verify it's legal yourself, don't hand-wave it), `goToPly`/`next`/`previous` move through the correct positions; out-of-range `goToPly` calls clamp instead of throwing; `steps[0].position` equals the initial FEN's position with `lastMove: null`.
- `history/page.test.tsx`: renders a list from a mocked `getMyGames()`, each row links to the right `/history/<id>`, and an empty list shows a friendly empty state (not an error).
- `history/[id]/page.test.tsx`: given a mocked `getGame()` response, stepping through plies with the stepper UI updates the rendered board to the position `replay()` independently computes for that ply (don't just assert "something rendered" — assert the actual FEN/position at a specific ply matches what the real `replay()` function returns for the same inputs, proving REPLAY-01's "reconstructs the correct state" property, not merely that clicking did something).
