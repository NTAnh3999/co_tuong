# Brief: T7.1 — Authorization matrix (endpoint/event × role)

## Goal

Produce a single, accurate reference document enumerating every REST endpoint and every Socket.IO event in `apps/api`, crossed against every actor type that can reach it, stating exactly what is allowed/denied and which guard or in-code check enforces that — derived by READING the actual guard/service/controller code, not by guessing or restating assumptions. This document is read-only output; it does not change any application code. (A separate step, run by the orchestrator afterward, uses this matrix as input to a security review — you are not expected to run that step yourself.)

## Read first

- `apps/api/src/modules/sessions/session.guard.ts` + `session-identity.ts` + `sessions.service.ts` — the only guard in the codebase. There are no role decorators (`@Roles()` etc.) — "role" in this matrix means actor categories you'll derive from how each handler actually checks identity: anonymous (no session), guest session, registered session, seat owner (red/black) of a specific game, room creator, spectator. Read each controller/gateway handler's body to see which of these it actually checks, not what you'd assume from the route name.
- Every controller: `apps/api/src/health/health.controller.ts`, `apps/api/src/modules/{ai,content,games,rooms,sessions}/*.controller.ts`.
- `apps/api/src/modules/games/game.gateway.ts` — every `@SubscribeMessage` handler and every server-emitted event; note which handlers check seat ownership (`userId` bound to a seat, not `socket.id`) per ADR's "seats bound to userId not socket.id" design, and which don't need to (e.g. a public spectator join).
- `docs/adr/` — skim for any ADR that states an authorization invariant (room/seat ownership, guest vs registered) so you can cite it instead of re-deriving it from scratch where one already exists.

## Design

Structure the document as:

1. **Actors** — a short enumerated list of every distinct actor category you found in the code (not a general one you assumed), with a one-line definition of each (e.g. "Seat owner: the session's `userId` matches `game.redId` or `game.blackId` for the target game").
2. **REST matrix** — one row per `(method, path)`, columns = every actor from step 1, cell = Allow/Deny/Partial (with a short note), plus a column naming the exact guard/check/line that enforces it (e.g. "`SessionGuard` + `GamesService.submitMove`'s seat check at games.service.ts:NN").
3. **Socket.IO matrix** — same shape, one row per event name (both client→server subscribed events and server→client emitted events, since emitted events can leak state to the wrong listener if room membership isn't scoped correctly — check how Socket.IO rooms are joined/scoped for this).
4. **Findings** — a plain list of anything you noticed that looks inconsistent, under-enforced, or relies on an assumption not actually checked in code (empty list is a fine, honest outcome if you genuinely found nothing — don't invent findings to pad this section, but don't skip noting something real because it feels minor).

Write in English (this is an internal engineering doc, not user-facing content).
