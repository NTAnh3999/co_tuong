# Brief: T7.10 — Enforce room/game membership on `room:join`/`game:join`/`game:sync`

## Goal

Fix a real authorization gap documented in `docs/security/authorization-matrix.md` (T7.1) and independently confirmed by the orchestrator against the real source: `apps/api/src/modules/games/game.gateway.ts`'s `room:join`, `game:join`, and `game:sync` Socket.IO handlers let ANY authenticated session (guest or registered) join an arbitrary room or game by a guessed or known id, with no check that the caller is actually a member/player of that room/game — they then receive that room's/game's live broadcasts (`room:state`, `game:state`, `game:move:accepted`, `game:finished`) forever, for as long as the socket stays connected. This is a confidentiality gap: a stranger who learns or guesses a room/game id can silently watch two other people's private match.

There is no documented "spectator" feature anywhere in `docs/spec/v1.0/`. The one place the word "spectator" appears in the codebase is a client-side RTL test title (`apps/web/app/game/[id]/page.test.tsx`), which only checks that the game page renders non-interactively when the current user resolves to neither red nor black — a defensive rendering choice for an edge case, not evidence of an intended public-viewing feature. Treat unauthorized join as a bug to close, not a feature to preserve. If you find a genuine, deliberate reason elsewhere in the code or contracts that a non-member must be allowed to join a room/game socket channel, stop and say so in QUESTIONS rather than guessing.

- Do not weaken or remove the ALREADY-correct membership check in `game:join` (lines 93-100) that gates `joinedGames`/presence tracking on `color !== null` — that part is right; the bug is that `client.join()` and `client.emit('game:state', ...)` run UNCONDITIONALLY above/after it, regardless of `color`.

## Design

For each of the three handlers:

1. **`room:join`**: before `client.join(parsed.data.roomId)`, fetch the room snapshot and check the caller (`client.data.user!.id`) appears in `snapshot.members`. If not, do not join the Socket.IO room and do not emit `room:state` with the room's real data — emit a rejection instead (reuse/extend the existing event-naming convention; something like `room:join:rejected` with a `reason` field, or whatever you determine is the most consistent name after reading the existing contracts). If the caller IS a member, behavior is unchanged from today.
2. **`game:join`**: you already compute `color` correctly. Move the `client.join(...)` and the "membership granted" `client.emit('game:state', snapshot)` so they only happen when `color !== null`; when `color === null`, emit a rejection instead of the real game state, and do not join the Socket.IO room (so the caller never receives this game's future broadcasts either).
3. **`game:sync`**: this one currently has no membership check at all before returning `game:state`. Use the same `playerColor()` helper already used by `game:move`/`game:resign`/etc. to check membership before emitting; reject otherwise.

Keep the fix minimal and consistent with the existing code's own style (the file already has a clear "resolve color, branch on null" idiom in four other handlers — follow it, don't introduce a new abstraction for three handlers when the file already has the pattern).

## Required tests

In `game.gateway.test.ts`, for each of the three handlers add a test titled with the `ROOM-02` prefix proving: (1) a real member/player can still join and receives real state (no regression), and (2) a non-member/non-player's join attempt is rejected, does NOT receive the room's/game's real snapshot, and does NOT subsequently receive a broadcast sent to that room (e.g. have a member make a move afterward and assert the non-member's socket received no `game:move:accepted`/`game:state` for it).
