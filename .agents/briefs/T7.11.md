# Brief: T7.11 — Fix: joining player can get stuck on `/room/[code]`, never redirected to `/game/[id]`

## Goal

A real, reproducible bug found while verifying T7.4's resilience suite: when the SECOND player joins a room right as it fills (triggering the room→game transition), their browser tab can get permanently stuck on the `/room/[code]` waiting-room page — the room member list correctly shows both players, but the page never redirects to `/game/[id]`, and no error is shown. The FIRST player (the one already on the page before the second joins) always redirects correctly.

**Reproduction**: run `apps/web/e2e/resilience.spec.ts`'s third test ("clients resync and resume after the API process restarts") — it fails at the `createRoom()` helper's `await expect(blackPage).toHaveURL(/\/game\/[^/?]+/, ...)` assertion, with the black page's snapshot showing the normal waiting-room UI (room code, both players listed, no alert) rather than an error or the game board. This reproduced consistently across 3 separate runs against that test's own isolated, always-cold API+web dev-server pair.

**The same room-creation flow does NOT reproduce this** against the suite's long-lived, already-warm dev stack: `apps/web/e2e/multiplayer.spec.ts`'s equivalent `createRedRoom()` helper (nearly identical code) passed 6/6 times across repeated runs in the same session. So whatever is happening is real, but timing-dependent — something about a cold/fresh backend and/or a cold/fresh `next dev` instance makes a narrow race reliably visible that's otherwise rare enough to not show up in normal local development. **A cold/slow backend is exactly the condition after a real production deploy or crash-recovery restart**, so this is a legitimate resilience bug worth fixing, not just a test artifact — but confirm this reasoning yourself rather than taking it on faith.

## Read first

- `apps/web/app/room/[code]/page.tsx` in full — the component where the bug lives. Pay close attention to:
  - The `loadRoom()` effect (lines ~24-69): it does `getRoom(code)` (REST GET), decides whether to call `joinRoom(code)` (REST POST) based on `isMember`, then unconditionally `setRoom(snapshot)` and opens a socket (`onConnect: () => socketRef.current?.joinRoom(snapshot.roomId)`, `onRoomState: (nextRoom) => setRoom(nextRoom)`), guarded throughout by a local `active` flag set to `false` in the effect's cleanup.
  - The separate redirect effect (lines ~71-73): `if (room?.status === 'STARTED' && room.gameId !== null) router.push(...)` — purely reactive to the `room` state set by either of the above two paths (the REST snapshot or the socket's `room:state` catch-up).
- `apps/api/src/modules/rooms/rooms.service.ts`'s `joinRoom()` (confirmed, read it yourself to verify): the SAME REST call that adds the second member ALSO synchronously creates the game and marks the room `STARTED` with a `gameId`, all within that one call — `rooms.integration.test.ts` already asserts `joinRoom`'s own HTTP response includes `status: 'STARTED', gameId: expect.any(String)` once the room fills. So in the ordinary case, the joining player's own `joinRoom()` REST response should already carry the STARTED state — no race should be needed for THAT path alone.
- `apps/api/src/modules/games/game.gateway.ts`'s `room:join` handler (note: **T7.10, a separate task, is adding a membership check here — read its brief/diff if it has already landed, and make sure your fix is compatible with it rather than fighting it**): it re-reads the room fresh from the DB and `client.emit('room:state', snapshot)` on every socket join, specifically so a client that subscribes late still catches up to current state. This is supposed to be exactly the safety net that should rescue the scenario in the bullet above, if something upstream of it produced a stale `room` value — but it's not visibly rescuing it in the reproduction.
- Whether Next's default `reactStrictMode` is in effect for this app (check `apps/web/next.config.ts` — it is not explicitly set, so Next 15's own default applies; find out what that default actually is for the app directory and confirm whether React's dev-mode double-invocation of effects is actually happening here, rather than assuming). If it is, work out carefully whether `loadRoom()`'s `active`-flag guard actually has a gap: specifically, whether the FIRST (soon-torn-down) effect instance can still be the one whose `joinRoom()` POST reaches the server and succeeds (becoming the request that actually starts the game), while the SECOND (active) instance's own `getRoom()` call lands in the narrow window where the DB already shows the new member but a cold/slow backend hasn't yet finished the room's `STARTED` update that happens after the member-insert transaction commits (`rooms.service.ts` lines ~86-112, note the status-to-`STARTED` update happens via a SEPARATE non-transactional call AFTER the member-insert transaction that added the second member already committed and released its row lock) — in which case the second instance would see `isMember: true` (added by the first instance), skip its own `joinRoom()` call entirely (per the `if (!isMember)` branch), and `setRoom()` whatever stale, still-`WAITING` snapshot its own `getRoom()` returned, relying entirely on the socket's catch-up to correct it afterward.
- If that IS what's happening, work out why the socket's `room:state` catch-up isn't correcting it. Candidates to actually check, not assume: does the socket's `onConnect` fire reliably and promptly on a cold/slow dev server; does `createGameSocket`'s underlying Socket.IO client have its own reconnect/backoff delay that could matter here; is there any other reason the `room:join` emit might not reach this specific client (e.g. a stale `roomId` captured in a closure, or the socket connecting to the wrong namespace/origin under this specific test's dynamically-allocated `apiBaseUrl`). Add temporary `console.log`/debug instrumentation if needed to pin this down for real rather than theorizing further — this is a genuine, reproducible bug, not a flaky one; you should be able to get a definitive answer by actually running the repro and observing what happens, not just reading the code.
