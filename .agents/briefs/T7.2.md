# Brief: T7.2 — Production images (Next standalone, turbo prune + pnpm deploy, one-shot migrate, Caddy HTTPS)

## Goal

A production-shaped Docker Compose stack: minimal `api` and `web` images built via Turborepo's own documented pruning workflow, a safe one-shot DB migration on API container start, and a Caddy reverse proxy terminating HTTPS in front of both — reusing T5.6's already-shipped `pikafish-worker` image unchanged. This is infrastructure only; no application code changes beyond the one `next.config.ts` flag needed for a standalone build.

## Design

### `apps/api/Dockerfile`

Multi-stage, final stage based on `node:22-trixie-slim`, running as a non-root user (follow `services/pikafish-worker/Dockerfile`'s own non-root pattern). Builder stage produces a pruned/deployed subset of the workspace containing only `@xq/api` and its real dependencies (including workspace packages `@xq/shared-contracts`, `@xq/xiangqi-core`), then runs `apps/api`'s own `build` script. Runtime stage copies only what's needed to run: built `dist/`, the resulting `node_modules`, `prisma/schema.prisma` + `prisma/migrations/`, and `package.json` (needed for `prisma`'s CLI to resolve its own version/config at runtime). Entry point is `docker-entrypoint.sh`.

### `apps/api/docker-entrypoint.sh`

```sh
#!/bin/sh
set -eu
npx prisma migrate deploy
exec node dist/main.js
```
This IS the "one-shot migrate" — `prisma migrate deploy` is safe to run on every container start (it's idempotent: already-applied migrations are skipped), so no separate migration container/job is needed. If the container restarts mid-migration and comes back up, the next start's `migrate deploy` either completes cleanly or fails loudly (non-zero exit, container doesn't reach `node dist/main.js`) rather than silently serving against a half-migrated schema — confirm this is really how `prisma migrate deploy` behaves (check Prisma's own docs/CLI help if unsure) rather than assuming it.

### `apps/web/Dockerfile`

Multi-stage, final stage based on `node:22-trixie-slim`, non-root. Builder stage installs the pruned/deployed `@xq/web` subset (same strategy as the api image), runs `next build` (which with `output: 'standalone'` set emits `.next/standalone` — a self-contained `server.js` plus only the `node_modules` it actually needs, no full workspace install required in the runtime stage). Runtime stage copies `.next/standalone`, `.next/static` (into the right relative path for `server.js` to find it — check Next's own standalone-output docs on the exact folder layout, don't guess), and `public/`. Entry: `node server.js`, listening on `$PORT` (default 3000).

### `infrastructure/docker/Caddyfile`

Terminates HTTPS for one public domain (placeholder: use a `{$DOMAIN}` Caddy env-substitution, and document that the operator sets `DOMAIN` and an ACME contact email via env/compose). Routes:
- `/api/*` and the Socket.IO path (check `apps/api/src/main.ts` for the actual Socket.IO path/namespace Nest registers, don't assume `/socket.io/` without checking) → the `api` service.
- everything else → the `web` service.

Caddy's automatic HTTPS (Let's Encrypt via built-in ACME) needs no extra config beyond a real domain in production; document that a placeholder/staging domain won't get a real cert and that's expected in any non-production run of this compose file.

### `infrastructure/docker/docker-compose.prod.yml`

Services: `postgres` (prod-shaped — no `xq_test` init, a named volume, **no published port** — only reachable on the compose network), `api` (your new image; `depends_on: postgres: condition: service_healthy`; env for `DATABASE_URL`, `PIKAFISH_WORKER_URL`, `WEB_ORIGIN`, `PORT`; no published port), `web` (your new image; env for whatever `NEXT_PUBLIC_API_BASE_URL`-equivalent the app needs — check how the web app currently gets its API base URL in dev, e.g. `apps/web/.env.example` if one exists; no published port), `pikafish-worker` (reused from T5.6 exactly as the dev compose configures it, CPU/memory limits intact, no published port), `caddy` (official `caddy:2-alpine` image, publishes `80:80` and `443:443` only, mounts the `Caddyfile` and a named volume for its certificate data). **Only Caddy's ports are published to the host** — state this explicitly as the point of the design (defense in depth: nothing else is reachable except through the proxy).
