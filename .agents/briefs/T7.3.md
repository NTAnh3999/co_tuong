## Design

### `backup.sh`

- POSIX shell (`#!/usr/bin/env bash`, `set -euo pipefail`). Reads connection info from env vars (`DATABASE_URL`, or the discrete `PGHOST`/`PGPORT`/`PGUSER`/`PGPASSWORD`/`PGDATABASE` vars `pg_dump` already understands natively — prefer relying on `psql`/`pg_dump`'s own env-var conventions over inventing your own var names).
- Produces a timestamped, compressed custom-format dump (`pg_dump -Fc`) to a configurable output directory (default `./backups`, overridable via an arg or env var).
- Exits non-zero with a clear stderr message on any failure (missing env var, `pg_dump` failure) — this script may run unattended from a cron/CI job, so silent partial failure is the one thing it must never do.

### `restore.sh`

- Takes a backup file path as an argument. Refuses to run without an explicit `--yes`/confirmation flag (safety: restoring overwrites data) UNLESS a `FORCE=1` env var is set for non-interactive/CI drill use — your call on the exact flag name, document it in the runbook.
- Uses `pg_restore --clean --if-exists` (or equivalent) against the target database from the same env-var convention as `backup.sh`.

### `purge-stale-data.sql`

- A SQL script (not auto-run by anything) that deletes data past a reasonable retention window — your judgment on which tables/columns qualify (e.g. abandoned/unstarted `Game` rows past some age, expired guest sessions) based on what you actually find in `schema.prisma`. Parameterize the retention window as a SQL variable/comment at the top that an operator edits before running, not a hardcoded magic number buried in a `WHERE` clause. Guard every `DELETE` with a `WHERE` clause that cannot accidentally match everything (e.g. never a bare `DELETE FROM "Game";`).

### `docs/ops/backup-restore-runbook.md`

- Step-by-step: how to run a backup, how to verify it (e.g. `pg_restore --list` on the dump without actually restoring), how to run a full restore drill against a throwaway database (not prod), and a suggested cadence (e.g. "drill quarterly"). Write for an operator following it under pressure during a real incident — short, numbered, copy-pasteable commands, no prose padding.

### `docs/ops/alerting.md`

- A short reference of concrete things worth alerting on, grounded in what actually exists in this codebase (not generic infra advice): e.g. the Pikafish worker's `/health`/`/metrics` endpoint (from T5.1) going unhealthy, the bounded engine queue filling up, Postgres connection failures, elevated `GamesService`/`AiService` fallback-path usage (the capture-preferring random-move fallback from T5.3 firing often would mean the Pikafish worker is degraded even though games keep working) — read `apps/api/src/modules/ai/ai.service.ts` and the worker's `/health` route before writing this so the patterns you list are real log lines/metric names, not invented ones.
