# Brief: T7.4 — Resilience suite (latency injection, concurrent-tab-same-seat moves, mid-game API restart)

## Goal

Three specific resilience gaps, not already covered by the existing multiplayer E2E suite. Read `apps/web/e2e/multiplayer.spec.ts` FIRST — it already has, from an earlier milestone (T4.8): a full two-player create/join/play-to-checkmate flow, "reloading mid-game restores the position and turn" (a page reload mid-game), and "a dropped connection recovers and the player can move again" (`context.setOffline(true)`/`setOffline(false)`). **Do not re-implement any of those** — this task is additive, covering what that file genuinely does not:

1. **Latency injection** — not just offline/online toggling, but degraded-but-connected conditions (added round-trip delay), confirming the UI stays usable (clock/move submission don't break or double-submit) under slow network, not just that it recovers from a full outage.
2. **Concurrent-tab-same-seat moves** — two browser contexts authenticated as the SAME seat (not two different players), both attempting a move at once. `apps/api/src/modules/games/game.gateway.test.ts` already has a server-side unit test for this exact property ("serializes simultaneous same-version submissions and persists one move row (SYNC-01)") — this task proves the SAME property end-to-end through two real browsers and real sockets, which is a materially stronger test than the existing unit-level one, not a duplicate of it.
3. **Mid-game API restart** — killing and restarting the actual NestJS API *process* mid-game (not a client-side network blip, which is already covered), then confirming a connected client's existing reconnect/resync path (the `connectionStatus: 'disconnected'` state + `game:sync` resync already implemented in `apps/web/src/features/game/controller/online-game-controller.ts`) actually recovers once the real backend comes back.

## Design

### 1. Latency injection

Use Playwright's CDP network-condition emulation (`page.context().route()` with an added delay on matching requests, or `CDPSession.send('Network.emulateNetworkConditions', ...)` for a Chromium project) to add meaningful round-trip latency (e.g. 300-800ms) to the API/socket traffic for one player mid-game, then: submit a move, confirm it still completes (no double-submission, no stuck "pending" UI state, the move eventually reflects on both players' boards), and confirm the clock (if running) doesn't desync or jump incorrectly because of the delay. Keep the induced latency bounded and the test's own timeout generous enough that this isn't flaky from normal CI variance.

### 2. Concurrent-tab-same-seat moves

Two browser contexts, BOTH holding the session cookie for the SAME guest user (reuse one `context.request.post('/sessions/guest', ...)` call's resulting cookie in both contexts — check how Playwright contexts can share or be given the same storage state, e.g. `browser.newContext({ storageState: ... })` from one context's `storageState()`), both navigated to the same in-progress game as the same seat. Fire a move attempt from BOTH pages at nearly the same time (e.g. `Promise.all` on both click sequences) for the same `expectedVersion`. Assert: exactly one move is ultimately accepted and reflected on both tabs' boards (they should converge, since both tabs are the same logical player and both receive the same `game:state` broadcast), and no error/crash occurs on either tab from the rejected attempt — a rejected submission from one of this player's own tabs should resolve gracefully (whatever the existing UI already does for `game:move:rejected`, don't invent new UI for this, just assert the existing behavior holds).

### 3. Mid-game API restart

Spawn the real API as a child process yourself (build it first if needed — reuse the existing `pnpm --filter @xq/api build && pnpm --filter @xq/api start` pattern from `.github/workflows/ci.yml`'s E2E job, which you should read for the exact health-check-polling pattern to reuse rather than inventing a new one), against a real test database (same `xq_test`-style setup that job uses — you'll need Postgres reachable; if you don't have Docker/network access in your sandbox to actually run this, write the spec correctly and say plainly in KNOWN GAPS that you could not execute it yourself, which is expected and fine). Get two players into a live game, play a few moves to confirm it's really live, then kill the API child process (SIGTERM, wait for exit), wait a moment, start a new API child process on the same port against the same database, and confirm: the connected clients' UI reflects the disconnect (reconnect banner or equivalent, using whatever the app already shows — don't invent new UI), and once the new process is up and the client's socket reconnects, play resumes correctly (a subsequent move from either player succeeds and is visible to both) without requiring a manual page reload. If the real app does NOT recover without a reload under this specific scenario, that is a genuine, valuable finding — report it precisely in KNOWN GAPS/QUESTIONS rather than papering over it by adding a reload to make the test pass, since that would hide a real resilience gap instead of proving/disproving it.
