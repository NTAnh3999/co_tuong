## Design

### `.github/workflows/ci.yml` — on `push`/`pull_request`

Two jobs:

**`build-test`**: checkout, pnpm setup (match the pinned `packageManager` version in root `package.json`), Node 22, `pnpm install --frozen-lockfile`, then `pnpm turbo run build lint typecheck test`. Run `packages/xiangqi-core`'s `test:coverage` specifically (not just `test`) so its thresholds actually gate the job — a threshold failure must fail this job. For every OTHER package, running `test` (not `--coverage`) is fine; don't force coverage collection where no threshold exists to check it against.

**`e2e`**: needs a real Postgres (service container, `postgres:17-alpine`, with health check, env matching `apps/api/.env.example`'s conventions) and a real running API:
1. Checkout, pnpm/Node setup, `pnpm install --frozen-lockfile`, `pnpm turbo run build --filter=@xq/api --filter=@xq/web` (and their dependencies).
2. Create the test database (`CREATE DATABASE xq_test;`, mirroring `infrastructure/docker/init.sql`) and run `prisma migrate deploy` against it.
3. Start the api server in the background against that database, wait for `GET /api/v1/health` to respond 200 before proceeding (a short polling loop, not a fixed sleep).
4. Install Playwright's browsers (`pnpm --filter @xq/web exec playwright install --with-deps chromium`; decide whether the mobile-webkit project is worth the extra `webkit` browser install cost in CI, or whether to run only `desktop-chromium` in CI and note that tradeoff in KNOWN GAPS — your call).
5. Run `pnpm --filter @xq/web exec playwright test`, with `NEXT_PUBLIC_API_BASE_URL` pointed at the api server just started.
6. Upload the Playwright HTML report as a build artifact on failure (`actions/upload-artifact`, `if: failure()`).

### The missing puzzle/replay E2E spec (`apps/web/e2e/puzzles-and-replay.spec.ts`)

`.agents/PLAN.md`'s own M6 gate line says "puzzle+replay E2E green," and its Verification section lists "E2E: ... puzzles/replay (M6)" — but no M6 task was ever assigned to write it (M6's task table has `T6.5`/`T6.8` for the web controllers/pages, each gated only by RTL-level `@xq/web` vitest tests). This is a real gap in the plan, not something to silently skip. Write one real Playwright spec, modeled on `local-game-checkmate.spec.ts`'s style (direct page interaction, real assertions on rendered state), covering:
- Solve a real puzzle end-to-end through the actual UI: create a guest session (same `request.post` pattern `multiplayer.spec.ts` uses), seed or pick a real puzzle reachable through the live content endpoints (check what `GET /puzzles` actually returns in this environment — if `packages/content`'s seed script hasn't been run against the CI's fresh `xq_test` database, there will be zero puzzles to test against; you need to also run `content:seed` — check `packages/content`'s actual script name — against the test database as part of this job's setup, or the E2E Playwright job entirely, whichever you land on, and say clearly which approach you took), click through to a `/puzzles/[id]` page, play the known solution moves on the real board, and assert the solved state renders.
- Replay a finished game: this needs a finished game to exist in the test DB to replay — the simplest real path is to actually play one to completion through `/play/local` or two-context `/play/online` first (reusing `local-game-checkmate.spec.ts`'s own known checkmate move list is the least-error-prone option, since it's already a verified real mate sequence), then navigate to `/history`/`/history/[id]` and assert the replay stepper shows the correct position at a couple of plies.

If seeding real content into the E2E job's test database turns out to be more involved than fits this task's time budget, it is fully acceptable to scope this spec down to ONLY the replay half (which needs no pre-existing content, just a game played through the UI) and leave the puzzle half as a clearly stated KNOWN GAP with the exact reason — do not fabricate a fake/hardcoded puzzle fixture directly in the test that bypasses the real `GET /puzzles` flow just to make the test pass, since that would stop testing anything real.

### `.github/workflows/nightly.yml` — on `schedule` (pick a reasonable cron, e.g. daily at a low-traffic UTC hour) + `workflow_dispatch` (manual re-run)

1. Checkout, pnpm/Node setup, `pnpm install --frozen-lockfile`.
2. Download the same pinned Pikafish Linux release `services/pikafish-worker/Dockerfile` already trusts, verify its checksum the same way, extract it, `chmod +x`, set `PIKAFISH_PATH` to its path.
3. Run `pnpm turbo run build --filter=@xq/xiangqi-core --filter=@xq/pikafish-worker` then the live tests with `PIKAFISH_PATH` set: `oracle.live.test.ts` (now including your new depth-4 case) and `multipv.live.test.ts`.
4. Fail the job loudly on any mismatch — this is the whole point of the job (catching silent drift between the pure engine and the real engine over time).
