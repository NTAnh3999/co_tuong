## Design

### `accessibility.spec.ts`

For each route (grouping ones that need no live data vs. ones that need a seeded game/puzzle/history entry), navigate to it and run `new AxeBuilder({ page }).analyze()`, asserting `violations` is empty (or, if you find a real, justifiable exception for a specific rule on a specific route, `.disableRules([...])` with a comment explaining exactly why — e.g. a known false positive against this exact markup, cited against axe's own docs, not just "test fails otherwise").

For the 320px overflow check: set the viewport to width 320 (`page.setViewportSize({ width: 320, height: ... })`) for each route and assert `document.documentElement.scrollWidth <= document.documentElement.clientWidth` (no horizontal overflow) via `page.evaluate(...)`.

For the ≥44px tap target check: for each route's genuinely interactive elements (buttons, links, and — critically — `Board2D`'s individual clickable squares on any route that renders an interactive board), assert each one's bounding box (`boundingBox()`) is at least 44x44 CSS pixels. Don't check every single element on every page generically; target the real interactive surface, especially the board, which is the one place this project's own UX doc already calls out as the highest-risk area for small tap targets on a 9x10 grid.

## Required tests

The `accessibility.spec.ts` file itself, covering every route listed above, with real assertions (not `test.skip`) for at least: zero axe violations, no 320px horizontal overflow, and ≥44px tap targets on the board and primary action buttons. Fix whatever these genuinely find; don't report a finding and leave it unfixed unless it's something you're explicitly told is out of scope above (dependency additions) or something you have a specific, stated reason not to touch (say so in KNOWN GAPS).
