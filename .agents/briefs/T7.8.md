# Brief: T7.8 — Baseline perf measurement (room-join/move-accept p95, reconnect success, worker CPU)

## Goal

A real, repeatable measurement script that records current performance numbers against the real running stack — room-join latency, move-accept latency, reconnect success rate, and Pikafish worker CPU under load. **Baseline only — there is no SLA to pass or fail against.** This task produces numbers for the historical record (something future work can compare against), not a gate.

## Acceptance-criteria IDs

AI-02

## Read first

- `apps/api/src/modules/rooms/rooms.controller.ts` (`POST /rooms`, `POST /rooms/:code/join`) and `apps/api/src/modules/ai/ai.service.ts` (`createAiGame`, the engine-move round trip) — the two real operations you're timing. Room-join and move-accept are plain REST calls; you do not need a browser or Socket.IO client for the "accept" half of either measurement — `GamesService.submitMove`'s own acceptance is already synchronous within the REST/gateway call, so a direct HTTP timing measurement is a real and sufficient proxy, not a simplification that loses the signal. If you believe otherwise after reading the code, say so in KNOWN GAPS rather than silently picking a design that doesn't actually measure what this task asks for.
- `services/pikafish-worker/src/server.ts`'s `GET /metrics` (fields from `PoolStats`: `totalRequests`, `totalTimeouts`, `totalErrors`, `totalRespawns`, `queueLength`) — sample this before and after a load burst for the worker CPU/load signal; there is no separate CPU metric exposed by the worker itself, so for actual CPU% you'll need `docker stats` against the running `xq_pikafish_worker_dev` container (or your own container name) during the burst — check if `docker` is available in your sandbox; if not, say so in KNOWN GAPS and design the script so the orchestrator can run it and get real CPU numbers.
- `docs/ops/alerting.md` (T7.3, already landed) — it already names the worker's real field names and the AI fallback log lines; reuse that vocabulary rather than inventing new metric names.
- "Reconnect success" — reuse the existing client reconnect path already covered by `apps/web/e2e/multiplayer.spec.ts`'s "a dropped connection recovers and the player can move again" test; for THIS task, measure it as a simple success RATE over N repeated disconnect/reconnect cycles against a real running game (does the client resync successfully every time, and how long does resync take), not a new mechanism.
- `.agents/NOTES.md` — your sandbox has no Docker/network access, so you cannot run this measurement against a real stack yourself; design the script correctly, and say so plainly rather than fabricating numbers. **Do not write placeholder/fake numbers into any report file** — if you cannot run it, the report should not exist yet, or should clearly state "not yet run" rather than contain invented data.

## Design

### `scripts/perf-baseline.mjs`

A single Node script (ESM, `node scripts/perf-baseline.mjs`), configurable via env vars for the API base URL and worker URL (same convention as `.env.example`: default `http://localhost:3001/api/v1` and `http://localhost:4000`), that:

1. **Room-join latency**: creates N (e.g. 50) guest sessions, has each create a room (`POST /rooms`) and a second session join it (`POST /rooms/:code/join`), timing each call. Report p50/p95/p99 for both operations separately.
2. **Move-accept latency**: creates M (e.g. 50) AI games (`POST /games/ai`) and submits a sequence of legal moves to each via the REST move-submission path (check which endpoint actually accepts a move server-side — `GamesService.submitMove` is reached through the gateway in normal play, but confirm whether a REST path exists for this or whether you need a minimal Socket.IO client call here specifically for submitting the human move; if a real move submission genuinely requires a socket round trip and there's no REST equivalent, say so and use a plain `socket.io-client` call — it's already a devDependency of `apps/api` and `services/pikafish-worker`, check if it's reachable from a root-level script without becoming a new dependency of the ROOT `package.json`; if it would require adding one, don't — document the limitation in KNOWN GAPS instead and measure what you can measure without it, e.g. just the AI-game-creation latency as a partial proxy). Report p50/p95/p99.
3. **Reconnect success rate**: this one genuinely needs a browser (reconnect is socket-level, client-side state). If you don't have Playwright/browser access in your own execution context for this script, don't fake it — document in `perf-baseline.md` that this metric requires a browser-driven measurement and point at `apps/web/e2e/multiplayer.spec.ts`'s existing offline/reconnect test as the qualitative proof point, with a note that a quantitative N-cycle success-rate measurement is a KNOWN GAP for the orchestrator to run separately if wanted.
4. **Worker load sampling**: before and after firing a burst of concurrent AI move requests (reuse the games from step 2), sample `GET http://localhost:4000/metrics` and report the delta in `totalRequests`/`totalTimeouts`/`totalErrors`/`totalRespawns`/`queueLength`. If `docker` is available, also capture `docker stats --no-stream <worker-container-name>` before/during/after for a real CPU% number.

Print a clear, readable summary to stdout AND write the same numbers into `docs/ops/perf-baseline.md` with a timestamp and the exact command used, so a future re-run's report is easy to diff against this one.
